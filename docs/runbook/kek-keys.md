# Файл ключей TOTP: создание, права, проверка (TZ §8.4, `ADR-014` п. 5, `T-103`)

Раздел про один файл — `/etc/tbot/keys/kek.json`. Он не похож на остальные секреты площадки:
значение имеет закрытый JSON-формат, лежит вне каталога секретов, читается процессом внутри
контейнера, и без него привязка TOTP невозможна физически. Ошибки здесь двух видов: «файл есть, но
не читается» (чинится на месте) и «значение потеряно» (не чинится ничем, кроме резервной копии).

## 1. Что это за файл и чем он не является

KEK (key-encryption-key) — связка ключей: JSON с полями `format_version`, `active_version`,
`keys[] = {version, key}`, где `key` — канонический base64 ровно 32 байт (AES-256). Каждый ключ
записи (`credentials.token_cipher`, `totp_enrollments.secret_enc`) шифруется собственным DEK, а DEK
зашифрован этим KEK'ом и лежит внутри конверта `TBE1` — то есть строка сама говорит, какой версией
ключей она зашифрована (`ADR-014` п. 1–4).

Чем этот файл **не** является:

- **не ротация.** Вторая версия ключа и перешифрование строк — `T-107` (`make rotate-keys`: бэкап до
  операции, журнал, идемпотентность). Инструмент этого раздела создаёт ровно одну версию;
- **не бэкап.** Обязанность резервной копии названа в §8 ниже; её реализация — `T-702`;
- **не шифрование секрета.** §8.4 требует хранения ключа вне базы и вне образа, а не шифрования самого
  файла;
- **не секрет `secrets-setup.sh`.** Тот скрипт умеет писать **строку** в `/etc/tbot/secrets` и
  проверять её форму; JSON с версиями ключей в эту модель не помещается, поэтому у файла отдельный
  инструмент — `deploy/vps/keys_setup.py`.

Цена подмены понятий конкретна: компрометация этого файла вскрывает **все** привязки сразу
(`ADR-014`), а его потеря делает их невосстановимыми — пароль пользователя и дамп базы при этом
останутся в порядке.

## 2. Кто вносит значение

Решение заказчика от 2026-11-21 (ask `05f7f262-0c56-41e6-9959-12aac2a45edb`, `ADR-014` «Решения
заказчика» п. 2): значение **генерирует сам инструмент**, агент запускает его с пустым вводом. Это
режим (2) `ADR-004` (машиногенерируемое значение), а не режим (1) «только заказчик».

Значение не должно появляться ни в stdout, ни в stderr, ни в аргументах процесса, ни в журнале CI,
ни в чате, ни в git. Инструмент наружу отдаёт только метаданные: версии ключей, активную версию,
длину ключа, режим и владельца файла. Тот же запрет действует для диагностики: `describe_key_ring`
печатает `версии [1], активная 1`, а не ключи.

## 3. Площадка: команды

```bash
cd /opt/tbot
sudo python3 deploy/vps/keys_setup.py            # создание по пути из TZ §8.4
sudo python3 deploy/vps/keys_setup.py --check    # форма, режим, владелец, каталог — без содержимого
sudo python3 deploy/vps/keys_setup.py --remed    # привести права, не касаясь значений
```

Порядок относительно деплоя важен: файл обязан существовать **до** `run --rm migrate` и до старта
`web`, иначе привязка появится позже, а отказ будет выглядеть как «панель не работает».

Что нужно знать про флаги:

- **перезапись** существующего файла — только `--force --yes` и только в терминале, с двумя
  подтверждениями. В неинтерактивном прогоне (`stdin` не терминал) инструмент отказывает, и это
  намеренно: значение, записанное поверх, означает, что привязки, зашифрованные прежним значением,
  больше не читаются. Никакой `--yes` их не вернёт;
- `--path <файл>` — прогон не по боевому пути (dev-копия, диагностика, CI);
- `--expect-owner any` — отменить проверку владельца `0:10001` для прогонов без root; норма
  возвращается значением по умолчанию;
- зависимостей нет: скрипт написан только на стандартной библиотеке и запускается системным
  `python3`. `cryptography` на хосте не нужна, поэтому числа формата продублированы из
  `packages/common/crypto.py`; равенство держит контракт
  `tests/contract/test_vps_artifacts.py::test_константы_файла_ключей_совпадают_с_модулем_криптографии`.
  Ровно из-за дублирования менять их можно только вместе: расхождение даёт «файл создан, приложение
  его не принимает».

## 4. Норма прав: почему не `0400` и почему не `644`

| Объект | Норма | Чем держится |
| --- | --- | --- |
| каталог `/etc/tbot/keys` | `0700 root:root` | `keys_setup.py` ставит сам; `--check` сверяет |
| файл `kek.json` | `0640 root:gid 10001` | `keys_setup.py` (требование ровно этого режима), `ADR-005` |

Почему группа `10001`: файл монтируется в контейнер (`§5`), bind-маунт приносит хозяйские права, а
процесс в образе работает под `uid=gid=10001` (`deploy/Dockerfile: USER 10001:10001`). Буква §8.4
(«`0400`, владелец — пользователь сервиса») при этой схеме запуска даёт нечитаемый ключ — ровно тот
дефект, который `ADR-005` разбирал на `db_url` (`PermissionError: /run/secrets/db_url` при зелёном
`--check`). Отклонение от буквы §8.4 оформлено `ADR-014` п. 5, TZ как контракт заказчика не
переписывается.

Почему нельзя «проще — `644`»: приложение проверяет права само, и отвергает **любые** биты шире
`0640` (`packages.common.crypto.kek_file_mode_error`, красное правило §8.4). Файл с `644` читается
процессом, но не проходит проверку связки ключей: `KeyRingUnusableError`. Отсюда практическое
следствие для dev-стенда и CI: доступ процессу контейнера выдаётся **группой** `10001`, а не
ослаблением режима (см. §6).

Два уровня нормы расходятся осознанно: приложение снисходительно к `0400` (буква §8.4), а инструмент
площадки требует ровно `0640 root:gid 10001` (выбранный вариант монтируемого секрета). Проверка
`--check` при `0600` красная, хотя приложение такой файл приняло бы: для площадки `0600` означает
«файл читает только root, состав — нет».

Доказательство DAC на живой ВМ (одна команда, содержимое не печатается):

```bash
sudo setpriv --reuid=10001 --regid=10001 --clear-groups \
  test -r /etc/tbot/keys/kek.json && echo READ_OK || echo READ_DENIED
```

Внимание: каталог `/etc/tbot/keys` закрыт (`0700`), и `test -r` упрётся в отказ каталога, а не в
биты файла. Составу это не мешает — bind-маунт файла делает демон от root, а процесс внутри
контейнера видит точку монтирования, а не хозяйский путь. Поэтому проверять надо либо точку
монтирования внутри контейнера:

```bash
sudo docker compose -f deploy/compose.yaml -f deploy/compose.prod.yaml --env-file deploy/tbot.prod.env \
  exec -T -u 10001:10001 web python3 -c "import pathlib; print(len(pathlib.Path('/run/secrets/kek_file').read_bytes()))"
```

либо снимок файла в каталоге с битом входа (`0711`) — именно так делает проба DAC в job
`prod-config` (§6).

## 5. Как файл попадает в контейнер

Боевой состав (`deploy/compose.prod.yaml`, поверх базового `deploy/compose.yaml`):

- секрет верхнего уровня `kek_file` с `file: /etc/tbot/keys/kek.json`;
- у сервиса `web`: `secrets: [db_url, kek_file]` и `TBOT_KEK_FILE=/run/secrets/kek_file`.

Три решения, зафиксированные контрактами:

1. **Только `web`.** Привязку TOTP делает панель (`R4c`); `engine`, `jobs`, `migrate`, `tgbot` и
   `postgres` ключевой материал не читают. Лишний KEK у процесса — та же цена, что лишний токен:
   компрометация вскрывает все привязки.
2. **Путь вне `/etc/tbot/secrets`.** Его называет сам TZ §8.4, поэтому это единственное разрешение на
   исключение из политики «все секреты площадки в `SECRETS_ROOT`». Исключение закрыто перечнем
   `ALLOWED_SECRET_PATHS` в `scripts/prod_compose_check.py`: файл ключей нельзя ни перенести в
   каталог секретов (тогда права на него определял бы скрипт, который о нём не знает), ни добавить
   новый секрет «по ходу дела».
3. **Только механизм `secrets:`, никогда `volumes:`.** Том не задаёт прав, раскрывает составу
   хозяйский путь и — при монтировании каталога — соседние файлы. Проверка:
   `test_файл_ключей_входит_в_состав_как_файловый_секрет_а_не_как_tom`.

Путь внутри контейнера задаёт compose переменной `TBOT_KEK_FILE`: настройка `Settings.kek_file` по
умолчанию указывает на хозяйский путь из §8.4, которого внутри контейнера нет. Расхождение пути
переменной и точки монтирования секрета ловит
`test_путь_файла_ключей_в_контейнере_задаёт_compose_a_не_настройка`.

## 6. Dev-стенд и CI: что именно доказывают прогоны

Dev-копия — `deploy/secrets/kek.json`. Её создаёт **тот же инструмент**, а не `printf`: формат JSON с
версиями ключей принимает только парсер приложения, поэтому «просто файл» дал бы зелёный разбор
состава и красное чтение ключей.

```bash
python3 deploy/vps/keys_setup.py --path deploy/secrets/kek.json --expect-owner any
sudo chgrp 10001 deploy/secrets/kek.json     # доступ процессу контейнера — группой, режим остаётся 0640
```

`chmod 644`, как делают dev-секреты строкового вида, для файла ключей означает красный шаг:
приложение отвергает режим шире `0640` (§4).

- job `compose-smoke` читает файл **изнутри контейнера `web`** — путь берётся из
  `load_settings().kek_file`, связка разбирается `describe_key_ring`, наружу выходят только
  метаданные. Это отдельный шаг именно потому, что «секрет смонтирован» и «секрет читается процессом
  состава» — разные утверждения (история с `db_url`, `ADR-005`).
- job `prod-config` исполняет инструмент под root по настоящему пути: создание, `--check`,
  **негативная** проба (`chmod 600` → `--check` обязан покраснеть), `--remed` (права чинятся,
  значения не меняются), проба DAC через `setpriv --reuid=10001 --regid=10001 --clear-groups` —
  чтение при `640 root:gid 10001` и отказ при `600 root:root`. До этого среза половина `ADR-005`
  про «нужна группа контейнера» проверялась только замерами на живой ВМ.
- POSIX-половина поведения инструмента (режимы, каталог `0700`, владелец, `--remed`) на dev-машине
  с Windows не исполняется вовсе — её исполняет только CI.

Что прогоны **не** доказывают: что файл существует на площадке. Для площадки — команды §3 и
проверка §7.

## 7. Диагностика отказов

| Симптом | Причина | Что делать |
| --- | --- | --- |
| `KeyRingUnusableError`, в тексте нет файла | файла ключей нет на площадке или он не смонтирован | `§3` (создание), затем `--check`; проверить, что файл был до `run --rm migrate` |
| `права файла 0644 дают доступ за пределами 0640` | режим шире политики §8.4 | `--remed`, затем повторить команду чтения из контейнера (§4) |
| `PermissionError: /run/secrets/kek_file` | на хосте `0600 root:root` или группа не `10001` | `--remed`; сверить `stat -c '%a %u:%g' /etc/tbot/keys/kek.json` с нормой §4 |
| `format_version: ожидалось 1, получено …`, «неизвестные поля документа» | файл правили руками или переносили через редактор с автозаменой | восстановить из резервной копии (§8), затем `--check` |
| отказ перезаписи без `--force` | штатное поведение: значения уже боевые | не обходить; если файл нужен новый — сначала копия (§8) |
| привязки перестали расшифровываться после `--force` | значение KEK заменено | восстановить прежний файл из копии; нового пути нет — привязки теряются |

Проверка всегда идёт от окружения к содержимому: есть файл → права → разбор формы. Поэтому текст
отказа отвечает на вопрос «что делать», а не «что не так в JSON».

## 8. Резервная копия и восстановление

Без этого файла все привязки TOTP невосстановимы, поэтому копия обязательна (`ADR-002`). Реализация
резервного копирования площадки — отдельная задача `T-702`; до неё копия делается руками: снять
файл вне каталога репозитория, права `600 root:root`, в git, в compose и в `docker run -e` он не
попадает ни при каких обстоятельствах.

Восстановление:

```bash
sudo install -d -m 700 -o root -g root /etc/tbot/keys
# положить файл из копии (не пересоздавать: пересоздание = новое значение = потерянные привязки)
sudo python3 deploy/vps/keys_setup.py --check
sudo python3 deploy/vps/keys_setup.py --remed
sudo docker compose -f deploy/compose.yaml -f deploy/compose.prod.yaml --env-file deploy/tbot.prod.env \
  up -d web
```

Контроль: `describe_key_ring` изнутри контейнера `web` (§4) — он печатает версии и активную версию,
и этого достаточно, чтобы понять, что восстановился именно прежний файл.

Ротация (`T-107`) появится отдельно: формат уже содержит `version` и `active_version`, конверт
самонесущий, поэтому добавление второй версии не ломает чтение строк, зашифрованных первой.
