# Runbook: секрет Bot API — размещение, проверка, ротация

Назначение: чтобы токен Telegram не попадал ни в чат с агентом, ни в git, ни в логи, ни в
аргументы командной строки. Применяется к любому токену Bot API в проекте.

## 0. Правило, из которого всё остальное

Токен, показанный в переписке, в скриншоте или в выводе команды, считается
скомпрометированным с момента публикации. Использовать его в работе нельзя, даже «только
для проверки»: проверка таким токеном добавляет его ещё в одну копию (history shell, логи,
конфиг на сервере). Порядок всегда один: **отозвать → выпустить новый → разместить в секрете
→ проверить**.

Чем грозит утечка токена: держатель получает возможность отправлять сообщения от имени бота
всем вашим чатам, читать сообщения, куда бот добавлен, менять webhook (перехватывая новые
сообщения), менять описание/аватар. Для проекта это равенство компрометации канала
управления торговлей.

## 1. Отзыв и выпуск нового

1. В диалоге с `@BotFather`: `/mybots` → выбрать бота → **Bot Settings / API HTTP
   Interface** (в русском интерфейсе — «Токен») → **Revoke** → получить новый.
2. Старый токен перестаёт работать немедленно; проверьте, что старые интеграции (если
   были) переведены на новый.
3. Если компрометация реальна (токен был у посторонних): после отзыва проверьте
   `getWebhookInfo` (нет ли чужого webhook), `deleteWebhook`, а также список чатов, куда
   добавлен бот.

## 2. Куда класть токен на площадке

Тестовый и рабочий контуры используют один и тот же порядок: файл секрета вне дерева
репозитория, права `600`, владелец — пользователь сервисов.

```
/etc/tbot/secrets/telegram_token      # одна строка с токеном, без комментариев
```

- в контейнер попадает как том или через `_FILE`-механизм конфигурации
  (`TBOT_TG_TOKEN_FILE=/etc/tbot/secrets/telegram_token`);
- **нельзя**: `docker run -e TBOT_TG_TOKEN=<токен>` (виден в `docker inspect`),
  аргумент CLI, `echo <токен> > file` (остаётся в shell-history), `.env` в дереве репо;
- в `.env` допустимо только в неизменяемом виде вне git и только если этот файл не
  копируется в артефакты сборки (проверяется `git check-ignore` + `gitleaks` в CI).

## 3. Проверка без раскрытия значения

Все проверки читают секрет из файла, значение в вывод не попадает:

```bash
TOKEN=$(cat /etc/tbot/secrets/telegram_token)
curl -sS -m 20 "https://api.telegram.org/bot${TOKEN}/getMe" | jq '.ok, .result.username'
```

Ожидаемый признак успеха — `"ok": true` и имя бота. При проверке через туннель — тот же
запрос с `--proxy socks5h://127.0.0.1:10800` (`runbook/telegram-egress-proxy.md`);
дополнительно фиксируется, какой IP видит Telegram.

В логах приложение обязано печатать только замаскированную форму
(`<digits>…<last4>`), см. `docs/tz/08 §8.7`.

## 4. Ротация по плану и вне плана

- плановая: раз в 180 суток или при смене оператора канала — процесс тот же, что в §1–2;
- внеплановая: подозрение на утечку, уход пользователя, компрометация узла;
- при ротации обновляется `tg_token_age_days{user="__bot__"}` (TZ §12.5) и запись в
  `docs/acceptance/tg-egress.md` с датой и именем бота (значение токена — нигде).

## 5. Настройки самого бота под наши сценарии

- `/setprivacy` → **ENABLE** (значения по умолчанию достаточно: сценарии TZ работают в
  личных диалогах, групповые чаты в модели нет);
- `/setdescription` и `/setabouttext` — не должны содержать слов «торговля», «биржа»,
  «брокер», данных о площадке: описание видит любой, кто знает имя бота (TZ §15.1);
- `/deletewebhook` перед первым запуском сервиса (и как шаг аварийного восстановления);
- `/setcommands` — список команд приложения (для приёмки `AC-telegram-*`).

## 6. Что можно передавать в переписку

Можно: имя бота (`@…`), числовой `chat_id`, имя пользователя/теги, пути к файлам секретов,
тексты ошибок без значений. Нельзя: токен, значения TOTP/резервных кодов, пароли, полные
`ss://`/`vless://` URI, значения `password`/`id` из конфигов Xray. Если секрет всё-таки
попал в переписку — он ротируется, а инцидент фиксируется здесь и в `docs/SECURITY-log.md`.
