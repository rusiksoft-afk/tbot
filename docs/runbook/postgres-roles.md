# Роли и права базы данных (`deploy/postgres/roles.sql`)

Задача `T-009`, требование `REQ-identity-04` и критерий `AC-identity-04` (ТЗ §4.1). Файл прав
лежит в репозитории, страница объясняет порядок: сначала миграции, потом права, потом
переключение приложения на роль приложения.

Модель ролей и то, почему пароль роли приложения общий с `db_password`, закреплены решением
заказчика в `docs/adr/ADR-006-db-app-role-shared-password.md`: менять её молча (разные пароли,
второй DSN-секрет, отзыв `CREATE`) нельзя — только новым ADR.

## 1. Почему у приложения отдельная роль

`REQ-identity-04` формулируется правами базы: «права БД приложения не дают `UPDATE`/`DELETE`
на `audit_log`». В PostgreSQL у владельца таблицы права неявные — `REVOKE` у владельца их не
отнимает. Значит, пока приложение входит той же ролью, что владеет таблицами, append-only
не выполняется физически, сколько бы `REVOKE` ни стояло в файле.

Отсюда две роли:

| Роль | Кто ходит | Что умеет |
| --- | --- | --- |
| `tbot` (владелец схемы, её создаёт образ postgres: `POSTGRES_USER`) | административные команды, `roles.sql`, runbook | владеет объектами схемы, полный DML, `ALTER`/`DROP` по чужим объектам |
| `tbot_app` (создаёт `roles.sql`) | `web`, `engine`, `jobs` **и `migrate`** (решение заказчика, §5.1) | DML в схеме `public` + право `CREATE` на схему (эго и делают ревизии Alembic); на `audit_log` — только `SELECT` + `INSERT`, и журнал принадлежит владельцу схемы |

Роль приложения создаётся `NOLOGIN` и без пароля: войти в неё нельзя, пока шаг переключения
(§5) явно не выдаст пароль и `LOGIN`. Повторный запуск `roles.sql` право входа не отзывает и
не добавляет.

Триггер «запретить любую правку журнала» не делается намеренно: критерий `AC-identity-04`
требует **найти** изменённую вручную копию дампа по цепочке хэшей (`make audit-verify`, задача
`T-109`), а не сделать правку невозможной. Триггер скрыл бы от проверки именно эту половину.

## 2. Что именно делает файл

```
DO $guard$ … IF current_user = 'tbot_app' THEN RAISE EXCEPTION …  -- п. 0: файл идёт владелец схемы
CREATE ROLE tbot_app NOLOGIN                       -- один раз (DO-блок по pg_roles)
ALTER ROLE tbot_app NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS
GRANT USAGE ON SCHEMA public TO tbot_app            -- пользоваться схемой
REVOKE CREATE ON SCHEMA public FROM tbot_app       -- но не создавать в ней объекты (`ADR-018`)
REVOKE CREATE ON SCHEMA public FROM PUBLIC         -- но не любой вход в базу
ALTER TABLE audit_log OWNER TO CURRENT_USER        -- п. 2.1: журнал принадлежит владельцу схемы
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO tbot_app
GRANT SELECT, INSERT ON TABLE audit_log TO tbot_app
REVOKE UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER ON TABLE audit_log FROM tbot_app
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO tbot_app
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT USAGE ON SEQUENCES TO tbot_app
GRANT tbot_app TO CURRENT_USER                     -- чтобы проверить права через SET ROLE
```

Возврат владения журналом и точечные отзывы появились по решению заказчика от 2026-11-21
(ask `8d2be9bb`, вариант Б). Право `CREATE` на схему тогда выдавалось именно потому, что
миграции шли ролью приложения. С 2026-11-22 оно **отозвано**: `alembic` ходит ролью-
владельцем схемы (`ADR-018`, ask `c7a6830e-9722-491d-9dbf-c8b291d3e84d`), потому что ревизии
правят таблицы, созданные другой ролью, и под ролью приложения такой DDL отказывает
(`42501 must be owner of table sessions` — реальный сбой деплоя 2026-11-22). Отзыв в файле
прав обязателен, а не косметичен: на площадке право уже выдано, а файл исполняется повторно.
Компенсирующий контроль журнала — §5.1, роль миграций — §5.4.

`TRUNCATE`, `REFERENCES` и `TRIGGER` отзываются, потому что журнал нельзя ни очистить пачкой,
ни сделать целью внешних ключей из новых таблиц, ни обвесить триггерами, меняющими правило
«дописали — и больше не трогают».

Реестр «только дописываемых» таблиц живёт в одном месте — `APPEND_ONLY_TABLES`
(`packages/storage/base.py`). Соответствие перечня `REVOKE` в SQL-файле проверяет
`tests/contract/test_db_roles.py`: если в реестр добавили таблицу и забыли `REVOKE`
(или наоборот), проверка падает до коммита.

Права на последовательности приложению не выдаются. Единственная счётная колонка схемы —
`audit_log.id`, и она `GENERATED BY DEFAULT AS IDENTITY`: у identity-колонки PostgreSQL
проверяет право `INSERT` на таблицу, а не на последовательность. Если бы колонка была
`serial` (default `nextval()`), вставка под ролью приложения упала бы с `42501`, и пришлось бы
выдавать `USAGE`/`UPDATE` на последовательность — то есть приложению стало бы доступно
движение счётчика журнала. Различие закреплено проверкой
`test_счётчик_журнала_выдаёт_база_без_прав_на_последовательность`.

## 3. Применение на площадке

Порядок жёсткий: сначала миграции, потом права. До ревизии `0002` таблицы `audit_log` нет, и
`REVOKE` по несуществующей таблице падает.

```bash
# Пути — абсолютные и под sudo: /opt/tbot имеет режим 750 root:root, и под rusiksoft в него
# нельзя войти (замер на площадке: `cd /opt/tbot` → Permission denied, а перенаправление
# `< /opt/tbot/deploy/postgres/roles.sql` в шелле не-root отвечает Permission denied ещё до
# обращения к базе — его тоже надо выполнять внутри `sudo sh -c`).
COMPOSE="sudo docker compose -f /opt/tbot/deploy/compose.yaml   -f /opt/tbot/deploy/compose.prod.yaml --env-file /opt/tbot/deploy/tbot.prod.env"
$COMPOSE run --rm migrate                        # alembic upgrade head
sudo sh -c 'docker exec -i tbot-postgres-1 psql -U tbot -d tbot -v ON_ERROR_STOP=1 -q -f -   < /opt/tbot/deploy/postgres/roles.sql'
```

Файл идемпотентен, его повторяют после каждой ревизии, которая добавляет таблицу
(`ALTER DEFAULT PRIVILEGES` покрывает только таблицы текущего владельца — исключение для
журнала выдаётся явно).

## 4. Проверка прав (сразу после применения)

Три запроса, которые отвечают на вопрос «работает ли append-only», а не «вывесили ли права»:

```bash
$COMPOSE exec -T postgres psql -X -U tbot -d tbot <<'SQL'
SELECT rolname, rolcanlogin, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = 'tbot_app';
SELECT has_table_privilege('tbot_app', 'audit_log', 'insert') AS insert_ok,
       has_table_privilege('tbot_app', 'audit_log', 'update') AS update_ok,
       has_table_privilege('tbot_app', 'audit_log', 'delete') AS delete_ok,
       has_table_privilege('tbot_app', 'users',     'update') AS users_update_ok;
SET ROLE tbot_app;
UPDATE audit_log SET action = 'proba' WHERE id IN (SELECT id FROM audit_log LIMIT 1);
SQL
```

Ожидаемое: `insert_ok = t`, `update_ok = f`, `delete_ok = f`, `users_update_ok = t`, и
`UPDATE audit_log` → `ERROR: permission denied for table audit_log`. Отказ по правам имеет
`SQLSTATE 42501`; другие коды (`42P01` «нет таблицы», `42703` «нет столбца») означают, что
проверяется не то.

Точное поведение на живой базе закреплено тестами `tests/integration/test_postgres_roles.py`
(CI job `migrations`; локально группа пропускается, потому что на dev-машине нет PostgreSQL):
вставка в журнал проходит, `UPDATE`/`DELETE`/`TRUNCATE` дают `42501`, обычный DML на `users`
доступен, права кластера отсутствуют, роль приложения не может ни создать таблицу, ни
`ALTER TABLE`, новая таблица получает DML автоматически, повторный запуск файла безопасен.

## 5. Переключение приложения на `tbot_app`

**Прежде чем делать этот шаг — прочитать §5.1: в текущем составе он ломает миграции.** Шага нет
в плане приёмки `T-009` именно по этой причине; права роли при этом созданы и проверены (§3, §4).

Без шага `REQ-identity-04` на площадке не выполняется: приложение ходит ролью-владельцем. Шаг
меняет пользователя в секрете `db_url`, поэтому согласуется с заказчиком (значение
машинно-генерируемое, режим 2 ADR-004 — его пересобирает сам скрипт, агент его не видит).

```bash
# 1) Роль обязана получить пароль и LOGIN до перезапуска сервисов, иначе приложение отвалится с
#    `password authentication failed for user "tbot_app"`. Значение берётся из смонтированного
#    секрета внутри контейнера и не попадает в argv (в `ps` видно только текст команды).
#    Замер 2026-11-22 13:07 UTC: прежняя форма с `printf ... %L` в ЭТОМ контейнере нерабочая —
#    `/bin/sh` образа `postgres:16.4` это dash, а `%L` расширение bash. Ответ:
#    `sh: 1: printf: %L: invalid directive`, дальше psql получает обрывок
#    `ALTER ROLE tbot_app PASSWORD ` и отвечает `syntax error at end of input`; код возврата при
#    этом у конвейера нулевой (последнее звено — psql с empty input), то есть дефект тихий.
#    Рабочая форма: SQL собирается на хосте (значение уже прошло проверку формы скрипта —
#    `[A-Za-z0-9._~-]{16,64}`, кавычка внутрь значения попасть не может), файл 600 root, подаётся
#    в psql по stdin и уничтожается сразу.
sudo python3 - <<'PY'
import pathlib
v = pathlib.Path('/etc/tbot/secrets/db_password').read_text().strip()
assert 16 <= len(v) <= 64 and all(c.isalnum() or c in '._~-' for c in v), 'нестандартная форма — ALTER не выполняется'
pathlib.Path('/root/role-password.sql').write_text(
    f"ALTER ROLE tbot_app PASSWORD '{v}';\nALTER ROLE tbot_app LOGIN;\n"
    f"ALTER ROLE tbot PASSWORD '{v}';\n")
pathlib.Path('/root/role-password.sql').chmod(0o600)
PY
sudo cat /root/role-password.sql | $COMPOSE exec -T postgres psql -q -X -v ON_ERROR_STOP=1 -U tbot -d tbot
sudo shred -u /root/role-password.sql
#    Пароль обязан получить и `tbot` (роль-владельцем, она же роль-мигратор по `ADR-018`): файл
#    `db_password` — общий для обеих ролей (`ADR-006`), поэтому ротация обязана применять его к
#    обеим, иначе путь миграций отвалится с `password authentication failed for user "tbot"`.
#    Проверка «значение действительно сменилось»: значения не печатаются, смотрим только
#    отпечатки SCRAM-верификаторов (первые 12 знаков sha256 от хеша):
$COMPOSE exec -T postgres psql -qX -U tbot -d tbot -c "select rolname, rolcanlogin, rolsuper, left(encode(sha256(rolpassword::bytea),'hex'),12) as verif12 from pg_authid where rolname in ('tbot','tbot_app') order by 1" < /dev/null
#    Грабля в самой проверке: `left(sha256(...),12)` не работает (`sha256` отдаёт `bytea`,
#    `ERROR: function left(bytea, integer) does not exist`) — нужен `encode(...,'hex')`.

# 2) Пересобрать `db_url` с новым пользователем (значение не показывается). Форма запуска —
#    `--only`, а НЕ позиционные имена: замер на площадке 2026-11-21 01:08 UTC,
#    `secrets-setup.sh db_password db_url` отвечает `неизвестный аргумент: db_password` и не
#    делает ничего. `--force` обязателен: под sudo без терминала скрипт файлы не пишет.
#    `db_password` в список не включать — DSN собирается из уже лежащего значения, скрипт
#    читает файл сам; лишний перезапуск пароля владельца не нужен (значение фиксируется в томе
#    `pgdata` при `initdb`).
sudo TBOT_DB_USER=tbot_app bash /opt/tbot/deploy/vps/secrets-setup.sh --only db_url --force

# 3) Форма значений.
sudo bash /opt/tbot/deploy/vps/secrets-setup.sh --check

# 4) Перезапуск сервисов приложения (списком сервисов, не всего состава).
#    ВАЖНО: `up -d` контейнер НЕ пересоздаёт, если состав не менялся — путь секрета тот же,
#    hash конфигурации тот же. Замер 2026-11-21: после пересборки `db_url` `up -d web` дал
#    `Container tbot-web-1 Started` без пересоздания, и процесс продолжал держать прежний DSN.
#    Смена содержимого файла секрета требует `restart` (или `up -d --force-recreate`).
$COMPOSE restart web engine jobs

# 5) Под кем ходит процесс. Две пробы, обе измеримые:
#    (а) конфиг внутри контейнера — разбор DSN из смонтированного файла (значение не печатается);
$COMPOSE exec -T web python -c "import urllib.parse, pathlib; print(urllib.parse.urlparse(pathlib.Path('/run/secrets/db_url').read_text().strip()).username)"
#    (б) серверное доказательство: временная авторизация в журнале Postgres. `log_connections`
#    — уровень postmaster, возвращается тем же RESET; окно включения — секунды.
$COMPOSE exec -T postgres psql -U tbot -d tbot -q   -c "ALTER SYSTEM SET log_connections = on" -c "select pg_reload_conf()"
curl -sS -m 10 -o /dev/null -w '%{http_code}
' https://tbot.rusiksoft.ru/readyz
sudo docker logs --since 60s tbot-postgres-1 2>&1 | grep 'connection authorized' | tail -3
$COMPOSE exec -T postgres psql -U tbot -d tbot -q   -c "ALTER SYSTEM RESET log_connections" -c "select pg_reload_conf()"
```

Ожидаемое: в (а) — `tbot_app`; в (б) — строки вида
`tbot_app@tbot LOG:  connection authorized: user=tbot_app database=tbot` (административные
`psql`-сессии при этом дают `user=tbot`). Поллинг `pg_stat_activity` для этого не годится:
соединение пробы `/readyz` живёт меньше миллисекунды и при выборке раз в 0,1 с не попадает
(замер 2026-11-21: 40 параллельных запросов + `\watch 0.1` — ни одного попадания).

Проверка прав «в бою» — тем же путём, что и приложение (образ, секрет, `psycopg_dsn`):

```bash
$COMPOSE exec -T web python - <<'PY'
import psycopg
from packages.common.config import load_settings
from packages.common.db import psycopg_dsn

with psycopg.connect(psycopg_dsn(load_settings().db_url.get_secret_value())) as c:
    print("роль:", c.execute("select current_user").fetchone()[0])
    for name, stmt in (("UPDATE", "UPDATE audit_log SET action='x' WHERE id IN (SELECT id FROM audit_log LIMIT 1)"),
                       ("DELETE", "DELETE FROM audit_log WHERE id IN (SELECT id FROM audit_log LIMIT 1)"),
                       ("TRUNCATE", "TRUNCATE audit_log")):
        c.execute("SAVEPOINT p")
        try:
            c.execute(stmt)
            print(name, "audit_log: РАЗРЕШЁН")
        except psycopg.Error as exc:
            print(name, "audit_log: sqlstate =", exc.sqlstate)
        c.execute("ROLLBACK TO SAVEPOINT p")
    print("строк журнала:", c.execute("select count(*) from audit_log").fetchone()[0])
PY
```

Значение `import engine_from_settings` в прежней редакции runbook не существует: в
`packages/common/db.py` — `sqlalchemy_url()`/`psycopg_dsn()`, а приложение (`apps/web/main.py`)
работает с psycopg напрямую. Грабля намеренно оставлена текстом: пробы обязано запускать тем же
путём доступа к базе, которым ходит процесс.

Ещё одна грабля площадки: внутри `bash -s <<HEREDOC` команда `docker exec -i …` **съедает
остаток скрипта** (stdin тот же поток) — скрипт обрывается без ошибки. Для команд без stdin
пишутся без `-i` (или с `< /dev/null`).

Ожидаемое в последней строке — `tbot_app`, а не `tbot`. Дальше проверка §4 должна дать тот же
набор прав уже «в бою», а `web` — отвечать 200 через Caddy.

`run --rm migrate` после переключения работает, потому что роль приложения получила `CREATE` на
схему (§5.1): миграция и приложение — одна роль. Отсюда порядок обязательный: сначала
применить `roles.sql` (§3), и только потом переключать DSN. И наоборот, если `roles.sql`
перезапускают после новой ревизии, делать это надо ролью-владельцем: под ролью приложения
файл прерывается на п. 0.

Репетиция команды п. 2 безопасна и проверяется до переключения: замер 2026-11-21 01:08 UTC —
`TBOT_DB_USER=tbot … --only db_url --force` (пользователь по умолчанию) даёт побайтово тот же
файл (93 байта, изменился только `mtime`), `--check` зелёный, `run --rm migrate` — `rc=0`.
То есть команду можно прогнать до шага переключения и убедиться, что она ничего не ломает.

Гигиена переключения: в п. 1 пароль `tbot_app` совпадает со значением `db_password` (оно же —
пароль роли `tbot`, зафиксированный в томе `pgdata` при `initdb`). Работать будет, но два входа
с одним значением — лишний путь: зная DSN приложения, получают доступ владельца схемы. Правильный
вариант — отдельный секрет `db_app_password` (режим 2 ADR-004: значение генерирует скрипт), тогда
`db_url` собирается с ним, а `db_password` остаётся паролем владельца. Это меняет перечень
секретов: файлы `/etc/tbot/secrets/*`, `SECRET_NAMES`/`MOUNTED_NAMES` в
`deploy/vps/secrets-setup.sh`, проверки `scripts/deploy_check.py`, ожидания
`tests/unit/test_deploy_check_secrets.py`, секреты состава в `deploy/compose.yaml` и
`deploy/compose.prod.yaml`, и ADR-005. Решение — за заказчиком (`docs/HANDOFF.md §4`).

### 5.1 `migrate` монтирует тот же секрет `db_url`: решение — вариант Б

> **Заменено `ADR-018` (2026-11-22).** Секрет остаётся тот же и второй DSN не вводится —
> это часть `ADR-006` в силе. Изменилось только то, **какая роль** берётся из этого
> секрета для `migrate`: `TBOT_MIGRATION_DB_USER` (§5.4). Раздел ниже оставлен без правок,
> потому что это запись решения и его цены на 2026-11-21.

Замер на площадке 2026-11-21 01:00 UTC (`SET ROLE tbot_app` после применения `roles.sql`):

```
CREATE TABLE под ролью приложения: отказ SQLSTATE=42501 (permission denied for schema public)
ALTER TABLE audit_log:              отказ SQLSTATE=42501
```

Секрет `db_url` смонтирован четырём сервисам — `web`, `engine`, `jobs` и `migrate`, у которого
`command: ["alembic", "upgrade", "head"]` (`deploy/compose.yaml`). Поэтому перевод `db_url` на
роль приложения переводит на неё и миграции, а без права `CREATE` на схему первая же ревизия
(`T-101…T-106` создают таблицы) упала бы на `CREATE TABLE`.

**Решение заказчика от 2026-11-21 (ask `8d2be9bb`): вариант Б — выдать роли приложения `CREATE`
на `public`, миграции остаются ролью приложения.** Пароль роли при этом общий с `db_password`
(ответ там же) — см. «граница» ниже.

Оформление решения, альтернативы и принятые риски — `docs/adr/ADR-006-db-app-role-shared-password.md`.

Что это стоит и чем компенсируется:

| Риск | Компенсирующий контроль |
| --- | --- |
| Приложение создаёт объекты в схеме (таблицу-двойник, лишнюю таблицу) | `REVOKE CREATE ON SCHEMA public FROM PUBLIC` остаётся: право есть только у роли приложения и у владельца базы; чужие объекты приложение не трогает — `ALTER TABLE`/`DROP TABLE`/`CREATE INDEX`/смена владельца по таблице схемы дают `42501` (проверка `test_приложение_не_правит_чужие_объекты`) |
| Таблицу следующей ревизии создаёт приложение ⇒ оно становится её владельцем, а у владельца `REVOKE` не работает | п. 2.1 `roles.sql` возвращает владение каждой таблице реестра `APPEND_ONLY_TABLES` текущему владельцу схемы; проверка `test_журнал_возвращается_владельцу_схемы` моделирует передачу журнала приложению и возвращение прав. Новая таблица журнала = имя в реестр + `ALTER TABLE … OWNER TO CURRENT_USER` + `REVOKE` (перечни сверяет контрактный тест) |
| `roles.sql`, запущенный ролью приложения, передал бы владение журналу самому приложению | п. 0 файла прерывает запуск под ролью приложения (`RAISE EXCEPTION`) — контрактная проверка наличие отказа на месте. Замер до переноса guard'а в начало: файл спотыкался только о `ALTER ROLE` в п. 1 (`permission denied to alter role`), то есть правило и так не нарушалось, но сообщение вводило в заблуждение |
| Общий пароль `tbot_app` и `tbot`: процесс, знающий свой DSN, знает и пароль роли-владельца, то есть может войти владельцем и править журнал | **не закрыто по решению заказчика.** Отзыв прав остаётся политикой; обнаружение — цепочка хэшей и `make audit-verify` (T-109). Жёсткая граница потребовала бы отдельных паролей и двух DSN-секретов (вариант А) |
| Приложение с правом `CREATE` может выдать права на **свои** таблицы другой роли | своих таблиц приложение не создаёт в боевом коде: DDL делает `alembic` ревизиями из git, каждая ревизия проходит CI и `migrations` job; прав на `GRANT` по чужим объектам у приложения нет (выдавать права может только владелец объекта) |

Практическое правило для следующей ревизии с новой таблицей журнала: добавить имя в
`APPEND_ONLY_TABLES` (`packages/storage/base.py`), добавить `ALTER TABLE … OWNER TO CURRENT_USER`
в п. 2.1 и `REVOKE` в п. 4 `roles.sql`, затем применить файл на площадке — он идемпотентен.

### 5.4 Роль миграций (`ADR-018`, 2026-11-22)

Нового секрета нет: `migrate` получает переменную `TBOT_MIGRATION_DB_USER` в
`deploy/compose.yaml` (у `web`, `engine`, `jobs` и `tgbot` её нет), а `migrations/env.py`
меняет **имя пользователя** в адресе из `db_url`, сохраняя пароль
(`packages.common.db.migration_url`). Проверка, что роль действительно та же, что и владелец
таблиц:

```bash
# кто владеет таблицами
sudo docker exec tbot-postgres-1 psql -U tbot -d tbot -c \
  "select tablename, tableowner from pg_tables where schemaname='public' order by 2,1"
# применяет ли миграции именно эта роль
sudo docker compose -f /opt/tbot/deploy/compose.yaml \
  -f /opt/tbot/deploy/compose.prod.yaml \
  --env-file /opt/tbot/deploy/tbot.prod.env run --rm migrate alembic current
```

Без переменной поведение прежнее: роль берётся из `db_url`. Так работают CI-job `миграции`
и dev-команда `make migrate`, где роль в адресе уже владелец схемы.

## 6. Откат шага 5

```bash
$COMPOSE exec -T postgres psql -X -v ON_ERROR_STOP=1 -U tbot -d tbot   -c 'ALTER ROLE tbot_app NOLOGIN'
sudo bash /opt/tbot/deploy/vps/secrets-setup.sh --only db_url --force   # TBOT_DB_USER по умолчанию = tbot
$COMPOSE restart web engine jobs      # restart, а не up -d: см. п. 4 §5
```

Данные при этом не меняются: меняются только учётная запись в DSN и право входа роли
приложения. `roles.sql` трогать не нужно — он не отзывает и не выдаёт `LOGIN`.

## 7. Чего здесь делать нельзя

- Не выдавать роли приложения прав на последовательности (см. §2) и не переводить
  `audit_log.id` в `serial`.
- Не делать `GRANT ALL` и не выдавать права роли `PUBLIC` — перечень прав должен быть явным,
  иначе `test_права_не_выдаются_публично_и_не_оптом` падает, а на площадке права перестают
  читаться инспекцией.
- Не вешать триггер «запретить UPDATE/DELETE» на журнал (см. §1) и не оставлять таблицы реестра
  append-only во владении роли приложения: у владельца отзыв прав не действует. `roles.sql`
  возвращает владение каждой таблице реестра (п. 2.1) и отказывается работать, если его запускает
  роль приложения; `test_владелец_журнала_не_роль_приложения` и
  `test_журнал_возвращается_владельцу_схемы` сторожат оба варианта.
- Не добавлять пароли и другие значения в `deploy/postgres/roles.sql`: контракт
  `test_в_файле_прав_нет_секретов` ловит `PASSWORD`/`IDENTIFIED BY`, а ADR-004 отводит
  значения в `deploy/vps/secrets-setup.sh`.
