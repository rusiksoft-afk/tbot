# Runbook: сеть прод-ВМ (Yandex Cloud) — входящие 80/443, доступ, откат

Объект: ВМ `fv48ibn5ff3ff5gd0e3v` (`compute-vm-2-4-74-ssd-1795094860175`), публичный
`153.51.172.30`, приватный `10.130.0.21/24`. Домен `tbot.rusiksoft.ru` уже указывает на неё.
Статус на 2026-11-19: снаружи открыт только `22`; `80/443/8443` не подключаются, при этом на
хосте `ufw` выключен, а `iptables` — политики ACCEPT. Значит фильтрация идёт в **группе
безопасности облака**, и её нужно править (T-708).

## 0. Правила безопасности процедуры (обязательно)

1. **Не отключать и не переписывать правило 22, пока не добавлено новое.** Иначе теряется
   доступ к ВМ посреди работы.
2. Перед любыми изменениями — сохранить текущее состояние (пункт 1) в файл
   `docs/acceptance/sg-before-<дата>.txt`: список SG инстанса и их правила.
3. Изменения применяются **дополнением** (создать новую SG и добавить её к интерфейсу),
   а не редактированием существующей. Откат = убрать добавленную SG с интерфейса.
4. Синтаксис команд CLI зависит от версии: перед применением каждой команды печатаем
   `yc <команда> --help` и сверяем флаги. Если команда не находится — делаем в веб-консоли
   (Cloud Console → Виртуальные сети → Группа безопасности), результат тот же.
5. После каждого шага — проверка доступа (пункт 4), и только затем следующий шаг.

## 2. Создание SG с нужными ingress-правилами

Цель: `TCP/22`, `TCP/80` и `TCP/443`, egress без ограничений. Публичный `0.0.0.0/0` на 80/443
dопустим, потому что собственный allowlist и 2FA работают на уровне приложения (TZ §8.5);
если нужен более жёсткий периметр — вместо `0.0.0.0/0` подсети заказчика, а публичный доступ
только через узел B.

> **Решение заказчика (2026-11-19): порт 22 оставляем открытым для всех (`0.0.0.0/0`)**,
> сужение источников — позже, отдельно. Компенсирующие слои обязательны: вход только по
> ключу (парольная аутентификация в `sshd_config` выключена: `PasswordAuthentication no`,
> `PermitRootLogin no`), `ufw default deny incoming` с разрешением 22/80/443, `fail2ban` на
> 22 и 443 (TZ §8.3). Основание для пересмотра: когда заработает запасной канал входа
> `yc compute ssh`, 22 можно сузить до статических источников без риска потерять доступ.

```bash
# id сети берём из /tmp/vm.json (networkInterfaces[].networkId)
yc vpc security-group create \
  --name tbot-web-2026-11-19 \
  --network-id <NETWORK_ID> \
  --description "tbot: 22 (по решению заказчика — для всех) + 80/443"

# правила (имена sg-... берём из вывода create)
yc vpc security-group add-rule <SG_ID> --type ingress --name ssh \
  --protocol tcp --port-range 22 --allow-cidr 0.0.0.0/0

yc vpc security-group add-rule <SG_ID> --type ingress --name http \
  --protocol tcp --port-range 80 --allow-cidr 0.0.0.0/0

yc vpc security-group add-rule <SG_ID> --type ingress --name https \
  --protocol tcp --port-range 443 --allow-cidr 0.0.0.0/0

# проверка правил
yc vpc security-group list <SG_ID>
```

Примечание по именам/флагам: в разных версиях CLI вместо `--allow-cidr` используется
`--allow-predefined-name`/`--allow-security-group`, а `add-rule` допускает
`--rule-file <yaml>`. Если флаги не совпадают — `yc vpc security-group add-rule --help`
или YAML-файл правила + веб-консоль.

## 3. Привязка SG к интерфейсу (не открепляя старую)

```bash

yc compute instance update-interface fv48ibn5ff3ff5gd0e3v \
  --network-id <NETWORK_ID> \
  --security-group-ids <EXISTING_SG_ID>,<NEW_SG_ID>

# если update-interface отсутствует в вашей версии CLI — используется
# `yc compute instance update ... --network-interface ...` (см. --help)
# или веб-консоль: Инстанс → Сеть и облачные ресурсы → Изменить → группы безопасности
```

Итог: к интерфейсу привязаны обе SG (старая даёт прежние правила, новая — 80/443).
Права в SG объединяются (логическое ИЛИ по ingress), поэтому старую SG не открепляем.

## 5. Дальше по порядку (после открытия портов)

1. `ufw default deny incoming` + `ufw allow 22`, `ufw allow 80`, `ufw allow 443`, `ufw enable`
   (второй слой после облачного; не глушит доступ, если правила совпадают).
2. `fail2ban` на `22` и `443` (TZ §8.3).
3. Caddy: сертификат Let's Encrypt на `tbot.rusiksoft.ru` (HTTP-01 или TLS-ALPN-01), редирект
   80→443, HSTS (T-713).
4. Проверка: `curl -I https://tbot.rusiksoft.ru/healthz` + тест, что к портам БД/метрик
   снаружи доступа нет.

## 6. Откат


Признак успешного отката: поведение портов вернулось к записанному в

## 7. Если доступ к облаку получить не удастся (запасной вариант)

Проблема: панель требует входящих 443 на прод. Если правила SG применить невозможно, есть
вариант без входящих портов на проде: **публичное лицо на узле B**
(`rusiksoft.ru` = `176.32.39.234`, где 80/443 открыты), а прод-ВМ устанавливает с узлом B
исходящий туннель (прод → B:443, замер связности — 21 мс, `docs/research/03 §3.7`), и узел B
транслирует входящие соединения на локальный порт прода. Тогда:
- DNS `tbot.rusiksoft.ru` переключается на IP узла B;
- сертификат выпускается на узле B (или через DNS-01 на проде);
- прод по-прежнему не принимает входящие соединения вообще.

Минусы этого варианта (обязательно учесть при решении): периметр и отказоустойчивность
панели становятся зависимыми от узла B, на котором уже работает другое сервисное ПО;
появляется дополнительное требование изоляции (отдельный ретранслятор-контейнер, mTLS,
отсутствие доступа узла B к БД и токенам). Вариант регистрируется отдельным решением (ADR)
и не применяется молча: он меняет модель угроз (TZ §8.5).
