# Секреты площадки: кто и как кладёт значения (TZ §14.3, `T-712`, `ADR-003`)

Документ отвечает на три вопроса: какие файлы обязаны существовать на `153.51.172.30`, кто вводит
значения и как убедиться, что всё готово, **не показывая содержимое** — ни в чат, ни в логи, ни в git.

## 1. Набор файлов

Каталог площадки — `/etc/tbot/secrets`, режим каталога `700`, владелец `root:root`. Режим файлов
зависит от класса (§2.1): `640` и группа с `gid 10001` у тех, что compose монтирует в контейнеры,
`600` у тех, что читает только хост.

| Файл | Кто читает | Что это |
| --- | --- | --- |
| `db_password` | `postgres` (через `POSTGRES_PASSWORD_FILE`), пароль внутри `db_url` | пароль учётной записи `tbot` |
| `db_url` | `migrate`, `web`, `engine`, `jobs` | DSN `postgresql+psycopg://tbot:***@postgres:5432/tbot` |
| `telegram_token` | `tgbot` (в контейнере монтируется как секрет `tg_bot_token`) | токен Bot API |
| `telegram_socks_pass` | `tgbot` (в контейнере — `tg_socks_password`) | пароль SOCKS5 входа туннеля, создан в `T-714` |
| `ghcr_token` | только хост: `docker login ghcr.io` | read-only токен GitHub на `ghcr.io` (runbook `ghcr-pull.md §3`) |

Имена файлов задаёт `deploy/compose.prod.yaml` в секции `secrets:`: имя файла ≠ имя секрета внутри
контейнера, и это разные вещи. **Нельзя** создавать в `/etc/tbot/secrets` файлы с именами из
конфигурации (`tg_bot_token`, `tg_socks_password`) «чтобы проверка прошла»: compose читает пути из
своей секции, а лишние файлы с токеном — лишний компромат на диске.

Пароль в `db_url` и содержимое `db_password` обязаны совпадать: расхождение выглядит как
`password authentication failed` при первом коннекте `web`, и ищется обычно сутки, потому что
оба файла на вид целые.

Шестой файл состава — `/etc/tbot/keys/kek.json`, файл ключей TOTP (`ADR-014` п. 5). Он не лежит
в `/etc/tbot/secrets`, и это единственное исключение из политики «все секреты площадки в одном
каталоге»: путь называет сам TZ §8.4. Права у него того же класса, что у монтируемых (§2.1), но
создаёт и чинит его не `secrets-setup.sh`, а отдельный инструмент `deploy/vps/keys_setup.py`:
значение — не строка, а JSON с версиями ключей, и скрипт ввода таких значений не описывает. Запуск,
нормы прав, диагностика отказов и резервная копия — `docs/runbook/kek-keys.md`.

## 2. Кто вводит значения

Только заказчик, в своей SSH-сессии. Агент значения не запрашивает, не печатает, не передаёт и не
сохраняет: стоп-лист `AGENTS.md` и TZ §8.4.

```bash
ssh -i ~/.ssh/tbot/<ключ> rusiksoft@153.51.172.30
cd /opt/tbot && sudo git pull --ff-only          # клон под root: git-операции только через sudo
sudo bash /opt/tbot/deploy/vps/secrets-setup.sh
sudo bash /opt/tbot/deploy/vps/secrets-setup.sh --check
```

**Кто именно запускает скрипт — три режима (`docs/adr/ADR-004`, решение заказчика от 2026-11-20).**
Все три идут через этот скрипт, и ни один не печатает значение:

1. значение выдаёт внешняя система (`telegram_token`, `ghcr_token`, далее `tinkoff_*`) — его
   создают и вводят в интерактивном прогоне только заказчик; агент его не генерирует, не просит
   строкой в чате и не доставляет из чужих файлов без явного решения заказчика;
2. значение генерирует сама площадка (`db_password` = `openssl rand -hex 24`, собираемый из него
   `db_url`, при пересборке туннеля — `telegram_socks_pass`): агент вправе запустить скрипт с
   пустым вводом — `printf '\n' | sudo bash /opt/tbot/deploy/vps/secrets-setup.sh --force --only
   db_password db_url`, — значение нигде не показывается;
3. значение уже есть у оператора (файл на dev-машине): агент проливает его в stdin того же
   скрипта — `ssh … 'sudo bash … --force --only telegram_token' < файл`, — не печатая и не
   сохраняя копии на ВМ (временные файлы после прогона удаляются). Такое значение считается
   скомпрометированным и подлежит ротации: `docs/runbook/telegram-token.md`.

Замер 2026-11-20 14:52 UTC (режимы 2 и 3): `--check` = 4 `OK` из 5 — `db_password` 48 байт,
`db_url` 93 байта, `telegram_token` 46 байт, `telegram_socks_pass` 24 байта; FAIL только у
`ghcr_token` (режим 1, значение создаёт заказчик). Во всех случаях в выводе — только имя, размер
и права файла.

Значения кладут из клонированного репозитория, а не из копии в `/tmp`: копия разъезжается с
репозиторием. Замер 2026-11-20: `/tmp/secrets-setup.sh` с sha256 `89005d59…3370b` — версия **до**
проверки формы значений, она принимает любую строку и молча пишет её. Актуальное содержимое файла в
репозитории (после правки заголовка по ADR-004 от 2026-11-20, только комментарии) — sha256
`5499b186…f7f35`; до той правки — `b8266865…9191f`; сверка на площадке:
`sudo sha256sum /opt/tbot/deploy/vps/secrets-setup.sh`.

Скрипт (`deploy/vps/secrets-setup.sh`) делает ровно то, что требуется контрактом:

- требует root (иначе владелец файла — пользователь, а compose читает файл от имени демона);
- отключает историю оболочки на время работы (`set +o history`);
- спрашивает каждое значение в скрытом режиме (`IFS= read -r -s`): `-s` — без эха, `-r` — обратный
  слэш в пароле не съедается, `IFS=` — ведущие и замыкающие пробелы не обрезаются;
- проверяет **форму значения до записи**: при несоответствии просит повторить (не больше трёх
  попыток, дальше — прямой вопрос «записать несмотря на форму?» с ответом по умолчанию «нет»). В
  вывод уходят только имя, длина и подсказка формата — значение не печатается ни целиком, ни
  частями;
- `db_password` можно не придумывать: пустой ввод = генерация `openssl rand -hex 24`. Если пароль
  уже лежит на площадке, пустой ввод сохраняет его **только если он по форме**; иначе скрипт
  говорит «лежащее значение не по форме — генерируется новое». На площадке 2026-11-20 в этом файле
  лежала фраза с пробелами, и наивный Enter сохранил бы нерабочую пару файлов;
- `db_url` не спрашивается: он собирается из параметров состава (пользователь `tbot`, хост-имя
  сервиса `postgres`, порт `5432`, база `tbot`) и того же `db_password`, поэтому пара файлов не
  может разойтись. Для внешней базы есть явный `TBOT_DB_URL`, и он тоже проходит проверку формы;
- пишет через `printf '%s'` — без завершающего перевода строки;
- ставит `root:root` и `600`, каталогу — `700`;
- при существующем файле спрашивает подтверждение перезаписи; без терминала (неинтерактивный
  прогон) писать отказывается, пока не передан `--force`;
- `--only ghcr_token telegram_token` — перезалить отдельные значения, не трогая пароль базы и DSN;
- обнуляет переменные со значениями (`unset val`, `probe=""`) сразу после использования;
- в конце печатает команду проверки и полный список файлов, которые потребует состав.

Значения не попадают: ни в `ps aux` (нет argv), ни в историю (`read` — встроенная команда, и
история на время выключена), ни в вывод терминала (`-s`), ни в файл кроме самого секрета.

## 2.1 Права файлов: почему «всем 600» ломает запуск (ADR-005)

Каталог `/etc/tbot/secrets` — `700 root:root`. Права файлов делятся на два класса, и это не
косметика: у файлов первого класса `600` делает секрет нечитаемым для того, кто обязан его прочесть.

| Класс | Файлы | Режим и владелец | Кто читает |
|---|---|---|---|
| монтируемые составом | `db_password`, `db_url`, `telegram_token`, `telegram_socks_pass` | `640` и группа с `gid 10001` | процесс контейнера (`deploy/Dockerfile`: `USER 10001:10001`) |
| хозяйский | `ghcr_token` | `600 root:root` | `docker login --password-stdin` под root (`docs/runbook/ghcr-pull.md`) |

Замеры на площадке 2026-11-20 (compose 2.40.3): bind-маунт файлового секрета сохраняет хозяйские
права, поэтому `600 root:root` внутри контейнера выглядит как `-rw------- 1 root root`, процесс —
`uid=10001(tbot)`, а `test -r` даёт `NOT_READABLE`; тот же файл в `640` с группой `10001` даёт
`READABLE`. Поправить это на стороне compose нельзя: `uid`/`gid`/`mode` у file-секретов отвергает
парсер (`secrets.db_url additional properties 'uid', 'gid', 'mode' not allowed`). Учётной записи с
uid или gid 10001 на хосте нет (`getent group 10001` и `getent passwd 10001` пусты), поэтому доступ
«по группе» не равен доступу локального пользователя: «мир» по-прежнему не читает ничего, а имена
файлов скрыты каталогом `700`.

Права ставит скрипт (`apply_policy`), а не оператор. Если файлы уже лежат с другими правами —

```bash
sudo bash /opt/tbot/deploy/vps/secrets-setup.sh --remed   # только права, значения не тронуты
sudo bash /opt/tbot/deploy/vps/secrets-setup.sh --check
```

`--remed` нужен ровно потому, что перезаписывать значения нельзя: пароль базы при `initdb` оседает в
tome `pgdata` (перегенерация = новый том и потеря данных), а внешние токены при повторном вводе
считаются скомпрометированными (ADR-004). Проверка «файл примонтирован и читается» изнутри
контейнера — отдельная задача T-715; сейчас её вручную делают так, как описано в
`docs/adr/ADR-005-secret-file-modes-for-container-readability.md` (замеры с `test -r`, значения не
печатаются).

Файл ключей (`/etc/tbot/keys/kek.json`) относится к классу «монтируемые составом» по правам, но не
ведом этому скрипту: у значения закрытый JSON-формат с версиями ключей, а `secrets-setup.sh` умеет
писать строку и проверять её форму. Норму прав для него ставит и сверяет
`deploy/vps/keys_setup.py` — там же `--check` и `--remed`. Практическое следствие: зелёный `--check`
этого скрипта говорит только про пять файлов каталога, и «всё готово» не означает, что файл ключей на
месте; он проверяется отдельной командой (`docs/runbook/kek-keys.md §3`). Каталог `/etc/tbot/keys` —
`0700 root:root`. Проба DAC от uid/gid процесса в образе (чтение при `640 root:gid 10001` и отказ при
`600 root:root`) исполняется в CI; до 2026-11-22 эта половина `ADR-005` проверялась только замерами
на живой ВМ.

## 3. Проверка готовности без содержимого

```bash
sudo bash /opt/tbot/deploy/vps/secrets-setup.sh --check
```

Вывод — имя, размер в байтах, режим, владелец и вердикт формы. Содержимое не печатается и не
уходит в подпроцессы: файл читается встроенным механизмом оболочки (`$(<файл)`), переменная
`probe` объявлена `local` и обнуляется на обеих ветках. Проверяются **все пять** файлов состава,
включая `telegram_socks_pass`, который создаёт настройка туннеля Telegram (T-714): молчать про
пятый файл `--check` больше не может — за это отвечает
`test_состав_требует_пять_файлов_и_все_пять_видны_в_диагностике`.

Зелёный вывод выглядит так (размеры зависят от значений):

```
OK:   db_password: 48 байт, 600, root:root
OK:   db_url: 93 байт, 600, root:root
OK:   ghcr_token: 40 байт, 600, root:root
OK:   telegram_token: 45 байт, 600, root:root
OK:   telegram_socks_pass: 22 байт, 600, root:root
готово: все файлы состава на месте и по форме
```

На что похожи неисправности:

| Признак | Причина и что делать |
| --- | --- |
| `FAIL: нет файла: …/ghcr_token` | токен GHCR не выпущен или не записан: `docker pull` даст `unauthorized` |
| `FAIL: <имя>: значение не по форме (N байт)` | в файле не то значение. Новый скрипт ввода такую строку уже не примет, а ранее записанную надо перезалить: `--only <имя>` |
| размер на 1 больше ожидаемого | дописан перевод строки: токен и DSN не проходят авторизацию |
| `FAIL: … 644` или `владелец rusiksoft:…` | файл правил человек от своей учётки: перепустить скрипт для этого имени |
| `WARN: режим каталога … = 750` | каталог создан вручную: состав это не ломает (демон читает от root), но видно, что файл создавали в обход скрипта. После запуска скрипта каталог становится `700` |

Агент имеет право запускать **только** `--check` (и смотреть `sudo ls -l /etc/tbot/secrets`).
Запускать ввод значений вместо заказчика — нельзя.

Замер 2026-11-20 (утро): в каталоге `telegram_socks_pass` (24 байта) и `telegram_socks_user`
(5 байт), оба `600 root:root`; четырёх файлов набора нет → четыре `FAIL: нет файла`, `exit 1`.

Замер 2026-11-20 (после того, как файлы появились): права и размеры корректны, но проверка формы
даёт четыре отказа:

```
FAIL: db_password: значение не по форме (154 байт) — ожидалось: пароль базы: 16–64 символа …
FAIL: db_url: значение не по форме (11 байт) — ожидалось: postgresql+psycopg://…
FAIL: ghcr_token: значение не по форме (11 байт) — ожидалось: token GitHub …
FAIL: нет файла: /etc/tbot/secrets/telegram_token
OK:   telegram_socks_pass: 24 байт, 600, root:root
```

Смысл этого вывода: «файлы есть, права правильные, значения не те». Проверка наличия и прав о
значении не говорит ровным счётом ничего, а последствия наступают на деплое: `pull` не
авторизуется, `migrate` не подключается. Отдельная проверка `ghcr_token` против `ghcr.io`: обмен
токена в `https://ghcr.io/token?scope=repository:rusiksoft-afk/tbot-web:pull` на лежащем значении
ответил `401 Unauthorized`.

Репетиция нового скрипта на самой площадке (временный каталог, фиктивные значения, `sudo`, Linux):
значения не по форме отклонены и не записаны; пустой ввод `db_password` при лежащем некондиционном
пароле породил новый (48 байт); собранный `db_url` — 93 байта; `--check` в итоге дал пять `OK` и
код 0. Тот же набор проверок исполняет CI (job `prod-config`): тело шага прогнано на ВМ отдельно,
код 0.

## 4. CI-контракт

Job `prod-config` в `.github/workflows/ci.yml` прогоняет скрипт на фиктивных значениях под `sudo`
во временном каталоге (`TBOT_SECRETS_SETUP_DIR`) и проверяет:

- отказ по форме: три попытки на значение плюс `n` → **ни одного** записанного файла;
- штатный прогон: пустой ввод `db_password` = генерация (48 байт), `db_url` собран (93 байта),
  `ghcr_token` 40 байт, `telegram_token` 45 байт, режим `600`, владелец `root:root`;
- совпадение пары: пароль из `db_password` встречается внутри `db_url`, а длина `db_url` равна
  длине пароля плюс 45 — в вывод идут только `DSN_SHAPE`/`DSN_MATCH` и длины;
- `--check`: четыре `OK` плюс отдельный `FAIL` на файле туннеля, каталог `700`;
- негативную пробу: после `chmod 644` режим `--check` обязан вернуть ненулевой код;
- неинтерактивность: прогон идёт с `--force`, потому что без терминала скрипт писать не должен.

Фиктивный токен бота собирается прямо в прогоне из частей (двоеточие — из `chr(58)`): строка вида
`<цифры>:<35 символов>` в файле workflow была бы неотличима от настоящего токена, и её запрещает
`tests/contract/test_no_forbidden_references.py`.

Статическая половина — `tests/contract/test_vps_artifacts.py`: имена файлов сверяются с
`deploy/compose.prod.yaml`; обращения к переменным со значениями (`val`, `probe`,
`existing_password`, `db_password_value`) разрешены только в перечисленных строках **кода**
(комментарии из проверки исключены: мутация `set +o history` → `:` раньше проходила незамеченной,
потому что та же строка есть в шапке скрипта); проверка формы обязана вызываться до записи файла;
режим `--check` обязан оставаться только чтением — без `chmod`, `chown`, `install` и `read`.

Машинная проверка на площадке, независимая от скрипта ввода, — `make deploy-check`
(`scripts/deploy_check.py`): проверки `secret_files` (имена, режим, владелец) и `secret_shapes`
(форма значений, выводятся только имя, длина и вердикт). Имена файлов для боевого контура берутся
из `deploy/compose.prod.yaml`, а не из имён конфигурации контейнера: `tg_bot_token` и
`tg_socks_password` — это имена **внутри** контейнера, на хосте таких файлов быть не должно
(`docs/runbook/stand-deploy.md §8`).

Рядом в том же job стоит прогон файла ключей: `sudo python3 deploy/vps/keys_setup.py` по
настоящему пути, затем `--check`, затем сломанный режим (`chmod 600`) с требованием красного
`--check`, затем `--remed`, и в конце проба DAC (`setpriv --reuid=10001 --regid=10001
--clear-groups`): `640 root:gid 10001` читается, `600 root:root` — нет. Файл создаётся до разбора
состава: compose раннёра (v5.1.3) требует, чтобы файловые секреты уже лежали на месте, а compose
площадки (2.40.3) — нет (`docs/runbook/stand-deploy.md §3`). Фиктивное значение генерирует сам
инструмент; боевых ключей в CI нет, наружу ходят только версии и длины. На dev-стенде
(job `compose-smoke`) тот же инструмент создаёт `deploy/secrets/kek.json`, а читает его изнутри
контейнера `web`: «смонтировано» и «читается процессом состава» — разные утверждения (урок
`ADR-005`). Оба шага держат контракты `tests/contract/test_ci_workflows.py`.

## 4.1 Что именно должно лежать в каждом файле

Формы ниже — контракт, который скрипт проверяет сам (функция `shape_ok`) и который повторяет
`scripts/deploy_check.py`. Проверка всегда идёт по длине и булевым сопоставлениям: разбирать и
печатать поля значения нельзя — если значение окажется числом или иначе безобидным набором, оно
всё равно утечёт в журнал сессии.

| Файл | Что это | Формат | Подмена, которую реально наблюдали |
| --- | --- | --- | --- |
| `db_password` | пароль учётной записи `tbot` в базе; генерируется скриптом по пустому вводу | 16–64 символа из `A-Za-z0-9._~-`: он ещё и внутри `db_url`, поэтому спецсимволы и пробелы ломают DSN | фраза с пробелами и пунктуацией, 154 байта |
| `db_url` | строка подключения к базе; собирается скриптом из `db_password` и параметров состава | `postgresql+psycopg://tbot:<тот же пароль>@postgres:5432/tbot` — хост обязано звать `postgres` (имя сервиса), база и пользователь `tbot` | 11 цифр вместо DSN, схема отсутствует |
| `ghcr_token` | personal access token GitHub для `docker login ghcr.io` | fine-grained PAT `github_pat_` + 22 и более символов `[A-Za-z0-9_]`, либо классический `gh[pousr]_` + 36 и более, либо прежний hex-40. Права на `tbot`: Contents Read-only и Packages Read-only | 11 символов: обмен в `ghcr.io/token` отвечает `401 Unauthorized` |
| `telegram_token` | токен бота из @BotFather | `<цифры>:<35 символов [A-Za-z0-9_-]>` | файл не создан |
| `telegram_socks_pass` | пароль SOCKS-входа туннеля Telegram (T-714); создаётся не этим скриптом | 8–128 символов без пробелов | — |

Отдельная причина испорченных значений, о которой надо помнить заказчику: вставка (paste)
многострочного текста в интерактивный `read` разбирается как несколько прочтений — одно значение
съедается частично, остаток уходит в следующий вопрос. Признак: подряд два файла одинаковой
подозрительной длины. Безопасный способ — по одному значению на вопрос, с клавиатуры; для
`ghcr_token` есть неинтерактивный путь из `docs/runbook/ghcr-pull.md §3` (значение по stdin
SSH-канала в `sudo tee`).

## 5. Ротация и компрометация

- Токен Bot API: отзыв через BotFather и перезапись файла — процедура и последствия для webhook в
  `docs/runbook/telegram-token.md`.
- `ghcr_token`: отзывается в настройках GitHub, выпускается новый с тем же объёмом прав
  (read-only на packages), файл перезаписывается скриптом.
- Пароль БД: менять в обе стороны одновременно (`ALTER ROLE … PASSWORD` и `db_password` + `db_url`),
  иначе `web` отвалится на следующем пуле соединений; дамп перед этим обязателен (`ADR-002`).
- Если значение всё-таки попало в чат, issue, лог или командную строку — оно считается
  скомпрометированным и ротируется в тот же день; факт попадания в лог CI удаляется вместе с
  прогоном, но это не отмена ротации.
