# Ежедневная проверка цепочки хэшей журнала (`integrity-check`, TZ §8.7)

Раздел нужен оператору площадки: в нём объяснено, что именно проверяется, где читать результат и
что делать при вердикте «нарушено». Задача заведена срезом `R3.2` задачи `T-109`
(`docs/adr/ADR-025-audit-log-hash-chain.md` п. 7 и п. 9 с поправками
`docs/adr/ADR-026-integrity-check-jobs.md`); ручная команда `make audit-verify` —
срез `R3.1` той же задачи, её коды возврата — `ADR-025` п. 7, порядок запуска на площадке — §3 этого
раздела.

Проверка нужна потому, что журнал `audit_log` append-only только по правам базы: роль приложения
(`tbot_app`) имеет на неё `SELECT` и `INSERT`, а роль-владелец схемы правку сделать может
(`ADR-006`, `ADR-018`). Обнаружение — цепочка хэшей: каждая строка хранит `hash_prev`
предшественницы и собственный `hash`, поэтому правка и вырез строки видны по пересчёту, а не по
совести процесса, который писал строку (`AC-identity-04`).

## 1. Что проверяется и чего проверка не делает

Ежедневная задача `integrity-check` процесса `jobs` (§8.7 «сверка цепочки хэшей аудита, проверка
свободных мест») делает два дела и делает их в одном порядке: **сначала читает журнал и выносит
вердикт, потом дописывает строку о проверке**.

* **разбор цепочки** — пересчёт `hash` каждой строки по её колонкам и сверка `hash_prev` с `hash`
  предыдущей строки в порядке `id`. Четыре кода находок: `content_mismatch` (строку правили),
  `broken_link` (разрыв, вставка или вырез), `duplicate_parent` (развилка — две строки ссылаются на
  одного предка), `missing_prefix` (у первой строки выборки есть `hash_prev` — начало не прочитано).
  Вердикт меняют первые три; `missing_prefix` — пометка, а не находка: она норма после служебной
  уборки журнала по §2.8 и у любой ограниченной выборки;
* **свободное место** — замер по корню файловой системы процесса и две метрики (§12.2, §12.4:
  `tbot_disk_free_bytes`, `tbot_disk_total_bytes`). Пороги §12.4 (`< 15 %` — warn, `< 8 %` — crit)
  относятся к алертам, а не к журналу: нового имени события в закрытом реестре §8.7 задача не
  заводила, след нехватки места — метрика и уровень логирования;
* **строка о прогоне пишется при каждом запуске**, а не только при находке. Иначе «проверка не
  запускалась» неотличима от «цепочка целая»: счётчик прогонов читается числом строк
  `integrity.audit_chain` за период.

Чего проверка не делает: не чинит журнал (правок и удалений строк нет ни у проверяющего кода, ни у
процесса), не проверяет секреты в логах и не отправляет уведомлений администраторам — рассылка
поверх таблицы-переходника относится к другому срезу (`T-116`, `T-408`).

## 2. Штатный ход: задача поднимается сама

Задача входит в реестр процесса `jobs` (`apps/jobs/main.py`, `apps/jobs/integrity.py`): интервал —
сутки, первая попытка сразу после старта процесса. Отдельной команды площадки в штатном режиме нет:
`jobs` поднят — проверка идёт.

| Что проверить | Чем |
| --- | --- |
| задача объявлена и у неё есть исполнитель | `$COMPOSE exec jobs python -m packages.common.health_probe --url http://127.0.0.1:9103/readyz` → в проверке `job_executors` перечислены исполнители (`rate_bucket_purge`, `integrity-check`) |
| прогон исполнялся | `$COMPOSE logs --since 26h jobs` → `job_done` с `job="integrity-check"` и текстом итога; при находке — `integrity_chain_findings`; при отказе задачи — `job_failed` |
| строки проверки лежат в журнале | запрос из §4 |
| свободное место | `$COMPOSE exec jobs python -c "import urllib.request as u; print(u.urlopen('http://127.0.0.1:9103/metrics').read().decode())" \| grep tbot_disk_` |

Порт health'а процесса `jobs` — `9103` (`TBOT_JOBS_HEALTH_PORT`), слушатель внутри контейнера
(`127.0.0.1`), наружу он не публикуется: наружу выходит только TLS-край `caddy`.

## 3. Временный порядок, пока `jobs` на площадке не поднят (`T-714`)

На живой ВМ поднимались `postgres`, `web`, `migrate` и `caddy`; `jobs`, `engine` и `tgbot` — нет
(приёмка `docs/acceptance/prod-deploy-t112-first-account.md`). Значит ежедневная задача там ещё не
идёт, и остаток дня без проверки закрывается ручной командой из того же кода разбора:

```bash
# /opt/tbot — 750 root:root: форма — sudo и абсолютные пути (замер 2026-11-23, протокол
# docs/acceptance/prod-deploy-t112-first-account.md §7). Вывод compose run в неинтерактивном
# канале теряется: он пишется в файл, код берётся из $?
COMPOSE="sudo docker compose -f /opt/tbot/deploy/compose.yaml -f /opt/tbot/deploy/compose.prod.yaml --env-file /opt/tbot/deploy/tbot.prod.env"
cd /opt/tbot && sudo git -C /opt/tbot -c core.sshCommand="ssh -i /root/.ssh/tbot_deploy_key_20261122 -o IdentitiesOnly=yes" pull --ff-only
$COMPOSE run --rm -v /opt/tbot/scripts:/srv/tbot/scripts:ro web python3 scripts/audit_verify.py \
  < /dev/null > /tmp/audit-verify.txt 2>&1; rc=$?; cat /tmp/audit-verify.txt; echo "rc=$rc"; sudo rm -f /tmp/audit-verify.txt
```

Тот же путь, что у завода первой учётной записи (`stand-deploy §12`): `scripts/` в образ не входит
(`deploy/Dockerfile` их не копирует), поэтому каталог монтируется read-only, а адрес базы и права
роли приложения берутся из состава (`/run/secrets/db_url`, роль `tbot_app` — `SELECT` на
`audit_log`).

Три вещи про временный порядок:

* **периодичность выбирает оператор.** Агент на площадке планировщик не заводит: `cron`-запись или
  systemd-таймер — действие на боевой машине, оно отдельное решение (`ADR-003`). Ориентир §8.7 —
  не реже одного раза в сутки;
* **ручной прогон ничего не пишет в журнал** (`ADR-025` п. 7): строку `integrity.audit_chain`
  создаёт только задача `jobs`. Двойных строк и расхождения счётчиков между ручным и автоматическим
  прогоном не появляется — разбор один и тот же (`packages/storage/audit_store.py`), меняются только
  границы выборки;
* **после подъёма `jobs` ручной прогон остаётся** инструментом разбора инцидента: он нужен, чтобы
  проверить копию дампа и ограниченный интервал `id`.

Коды возврата ручной команды (`ADR-025` п. 7): `0` — находок нет; `1` — находки есть
(`content_mismatch`, `broken_link`, `duplicate_parent`); `2` — неверная выборка (пустой интервал,
`--from-id` больше `--to-id`); `3` — база недоступна или схема не развёрнута; `4` — прочее.
Отдельный смысл у кода `3`: сломанный проверяющий не должен выглядеть как корректный журнал.

## 4. Как читать результат

Строка проверки: `action = 'integrity.audit_chain'`, `actor IS NULL` (актор — не учётная запись,
поправка `ADR-026` п. 2), `entity = 'audit_log'`, `entity_id` пустой. Идентификатор прогона лежит в
`details ->> 'run_id'`, вердикт — в `details ->> 'verdict'`: `intact`, `empty` (журнал пуст) или
`findings`.

```sql
-- последние строки проверки: вердикт и счётчики по четырём кодам
select id, at, details ->> 'verdict'          as verdict,
       (details ->> 'rows')::int              as rows,
       (details ->> 'content_mismatch')::int  as edited,
       (details ->> 'broken_link')::int       as broken,
       (details ->> 'duplicate_parent')::int  as forked,
       (details ->> 'missing_prefix')::int    as no_head,
       details -> 'issue_row_ids'             as issue_rows,
       details ->> 'disk_free_percent'        as disk_percent,
       details ->> 'disk_state'               as disk_state,
       details ->> 'run_id'                   as run_id
  from audit_log
 where action = 'integrity.audit_chain'
 order by id desc
 limit 14;

-- число прогонов за последние 7 суток: «0» означает, что проверка не запускалась,
-- и это не то же самое, что «цепочка целая»
select count(*) from audit_log
 where action = 'integrity.audit_chain' and at > now() - interval '7 days';
```

Считать нужно и то, и другое: строка с вердиктом `intact` ничего не говорит о том, что прогонов было
семь.

Ручная команда печатает вердикт словами: `вердикт: цепочка цела; код 0`,
`вердикт: цепочка нарушена — находок N (коды); код 1`, плюс строки `missing_prefix` без изменения
вердикта.

## 5. Находка: что делать и чего не делать

1. **Не править и не удалять строки журнала.** Правка — именно то, что цепочка обязана обнаружить;
   исправленная строка теряет доказательство, а вторая строка о проверке этого не скроет.
2. **Зафиксировать состояние:** имена находок, `issue_row_ids`, интервал `id` из строки проверки
   (`from_id`/`to_id`), дата и время строки. Дальше разбор идёт по копии дампа, а не по живой базе.
3. **Разобрать копию дампа интервалом:** `scripts/audit_verify.py --from-id N --to-id M` (или
   `--since`/`--until`). Ограниченная выборка обязана показать `missing_prefix` пометкой — это не
   находка.
4. **Сопоставить с внешними следами:** `job_failed` в журнале процесса, `integrity_chain_findings`,
   изменения `deploy/tbot.prod.env` и дайджестов, `journalctl -u ssh` (кто входил на ВМ).
   Развилка (`duplicate_parent`) на живой базе создать не должен страж
   `ix_audit_log_hash_prev_linked` (ревизия `0007`) — её наличие означает запись в обход протокола
   добавления или сборку дампа из двух копий.
5. **Дальше — разбор инцидента (§13 техзадания), а не точечная правка.** Если подделка подтверждена,
   восстановительный путь — образ предыдущей версии и дамп (`ADR-002`), а ротация значений —
   `docs/runbook/secret-rotation.md`.

## 6. Свободное место

Задача выкладывает `tbot_disk_free_bytes{app}` и `tbot_disk_total_bytes{app}`; пороги §12.4 —
`< 15 %` (warn) и `< 8 %` (crit) свободного. Внутри контейнера корень смонтирован read-only поверх
диска ВМ, поэтому цифры описывают диск машины, а не «слои контейнера». Про резервные копии и потолок
места — `ADR-002` (дампы в `/var/backups/tbot` на том же диске).
