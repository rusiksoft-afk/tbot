## 7. Наблюдения и грабли среза (вносить в будущие прогоны)

1. **`docker compose exec -T` съедает stdin скрипта.** В неинтерактивном heredoc
   `ssh 'bash -s' <<EOF` первый же `exec -T psql` забирает остаток сценария как stdin контейнера —
   последующие команды молча не выполняются (вывод обрывается без ошибки). Форма защиты: `< /dev/null`
   к каждому `exec` (или все запросы одним `psql` с несколькими `-c`).
2. **Вывод `docker compose run` в том же канале теряется**, если его не перенаправить в файл:
   первый черновой прогон дал пустой хвост. Форма:
   `$C run … > /tmp/f.txt 2>&1; rc=$?; cat /tmp/f.txt` (файл — с `sudo rm` после).
3. **`/opt/tbot` — `750 root:root`:** и `cd`, и `grep`/`ls`/`sha256sum` по путям внутри — только
   через `sudo`. Строка `cd /opt/tbot` в `runbook stand-deploy §12` работает лишь в root-сессии;
   для `rusiksoft` — вариант с абсолютными путями (правка ранбука внесена этим же срезом).
4. **Значение пароля существует только в терминале оператора.** Это не формальность: у скрипта нет
   второго показа, файла и журнала, а смены пароля без полного сеанса нет (`ADR-012`). Потеря
   значения до первого входа — только архивирование ролью-владельцем схемы и повторный завод с
   другим логином (`runbook stand-deploy §12`, последний resort).
5. **Повторять шаг 2 «чтобы убедиться» нельзя** — это не ритуал, а нарушение правила «ровно один
   раз». Проверка отказа делается прогоном без `--yes` (он всё равно упирается в гейт, rc=`4`).

## 8. Дефект, найденный при первой попытке входа (2026-11-23, 03:17–03:21 UTC)

**Симптом.** Оператор под `rusiksoft` не может войти: `POST /login` из браузера отвечает
`403` с телом `{"status":"forbidden","detail":"запрос отклонён"}`.

**Журнал `web`.** Пять событий по числу попыток:

```json
{"event": "csrf_rejected", "path": "/login", "detail": "Origin='https://tbot.rusiksoft.ru'", "level": "warning", "ts": "2026-11-23T03:17:48.88Z"}
```
(одинаковые `detail` во всех пяти; `ts` — 03:17:48, 03:18:05, 03:19:34, 03:20:40, 03:21:01)

Отказ поднимает `ensure_same_origin` (`apps/web/security/csrf.py:146`), ответ формирует общий
обработчик `CsrfRejected` (`apps/web/main.py:203–215`) — причина только в журнале процесса, в
ответе её нет (`ADR-008`).

**Причина.** Процесс `web` считает, что запрос пришёл по схеме `http`, хотя наружу он отдаётся по
`https`. `_request_origin` (`csrf.py:191`) строит источник из `request.url`, то есть из
ASGI-схемы. Uvicorn (`0.32.1` в образе) подменяет схему по `X-Forwarded-Proto` **только если адрес
пира входит в `forwarded_allow_ips`**, а значения нигде нет: `apps/web/main.py:416` вызывает
`uvicorn.run(…)` без этого параметра, по умолчанию — `127.0.0.1`. Пир — контейнер `caddy`
(сеть `tbot_tbot-public`, подсеть `172.28.4.0/24`, участники `tbot-web-1` и `tbot-caddy-1`),
поэтому заголовок игнорируется: `request.url.scheme = "http"`, нормализованный источник
`http://tbot.rusiksoft.ru`, а браузер приносит `https://tbot.rusiksoft.ru` → отказ.

**Замер-дифференциал с dev-машины** (пустая форма, значения не передавались; `400` = страница
входа с объяснением «пустая форма», то есть проверка источника пройдена):

| проба | код | вывод |
|---|---|---|
| `POST /login` + `Origin: https://tbot.rusiksoft.ru` | `403` | CSRF-отказ — тот же, что видит браузер оператора |
| `POST /login` + `Origin: http://tbot.rusiksoft.ru` | `400` | источник принят, разбор формы |
| `POST /login` без `Origin` | `400` | проверка источника пропущена (нет `Origin`, нет `Sec-Fetch-Site`), разбор формы |

Значит расхождение именно по **схеме**, а не по хосту. При этом `X-Forwarded-Proto: https` до
upstream доходит — это измерено ещё в приёмке TLS (`docs/acceptance/tls-edge.md`, пункт 10 таблицы;
`Caddyfile` ставит `header_up X-Forwarded-Proto {scheme}`, `deploy/caddy/Caddyfile:124`).
Дополнительная проба из контейнера `caddy` прямо к `web:8080` с браузерным `Origin` тоже даёт `403`
(пира `127.0.0.1` там нет — свой пир), что подтверждает: дело в доверии к заголовку, а не в Caddy.

**Границы дефекта.**
1. Браузеры со `Sec-Fetch-Site: same-origin` проходят первую проверку `ensure_same_origin`, но
   падают на второй: **вход из браузера в бою невозможен ни под какой учётной записью**.
   Интеграционные тесты этого не видят: `TestClient` ходит по `http://testserver`, и `Origin`
   либо отсутствует, либо согласован по схеме.
2. Раньше дефект не всплывал, потому что аутентифицированной части §9 не было: в `users` было
   0 строк, браузерных POST на `main`-ветке не выполнялись (`R7b` проверял только
   неаутентифицированный контур).
3. Счётчики частоты такие отказы **не расходуют**: `ensure_same_origin` стоит в `POST /login`
   раньше `enforce_scope(LOGIN_IP_SCOPE)` (`apps/web/routes/login.py:210` против `:222`), и замер
   это подтверждает — `rate_buckets`: `login_ip` 3 строки, `max_attempts = 2`, и эти 2 единицы
   соответствуют двум моим пробам, дошедшим до лимитера (`Origin: http…` и без `Origin`). Пять
   CSRF-отказов оператора счётчику ничего не добавили, блокировки нет.
4. На `sessions.ip`, окна перебора и `X-Forwarded-For` дефект не влияет: их приложение считает
   самостоятельно по правому элементу цепочки (`apps/web/security/clients.py`, `ADR-007`,
   `ADR-009`) — отдельный, уже принятый контур доверия.

**Варианты починки (решение заказчика, `docs/HANDOFF.md §2`).**
- (а) **Доверять заголовки от пира-прокси**: задать `forwarded_allow_ips` для сервиса `web`
  (env `FORWARDED_ALLOW_IPS`). Требует детерминированного адреса пира: подсеть `tbot-public`
  сейчас назначена Docker'ом (`172.28.4.0/24`) и после пересоздания сети может измениться,
  значит нужен явный `ipam` в `deploy/compose.yaml` + проверка состава (`prod_compose_check.py`,
  `test_compose_prod_contract.py`). Побочный эффект uvicorn: он же переставит `scope["client"]`
  из `X-Forwarded-For` по правилу «первый недоверенный», то есть появится второй контур разбора
  адреса, отличный от принятого в `ADR-007`/`ADR-009`.
- (б) **Прикладной разбор схемы в одной точке**: `ensure_same_origin` учитывает
  `X-Forwarded-Proto`, который перезаписывает наш Caddy (`header_up`), по образцу `clients.py`
  (правило «правый элемент, добавленный нашим прокси»), с оффлайн- и живыми проверками и `ADR-024`.
  Топология и compose не меняются; область изменения — только сравнение источника.
- Общая для обоих цена: новый деплой-цикл с пересъёмкой дайджестов парой «прогон → коммит»,
  и повторная проверка наружным прогоном (`POST /login` + браузерный `Origin` обязан дать `400`
  вместо `403`), после чего уже выполняется аутентифицированная половина §9.
