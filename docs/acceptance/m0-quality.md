# Приёмка M0: качество кода и что именно проверяет CI

Дата: 2026-11-19. Область: каркас репозитория (`apps/*`, `packages/common/*`, конфигурация,
миграции, compose, CI). Инфраструктурная часть M0 (площадка, туннель) — в
`docs/acceptance/tg-egress.md` и `docs/research/03-prod-yandex-cloud-conformance.md`.

> Числа ниже зафиксированы 2026-11-19 и с тех пор выросли (212 тестов, покрытие 95.07%, mypy —
> 48 файлов, первый полностью зелёный прогон CI вместе с `compose-smoke` и `pip-audit`).
> Актуальный срез и приёмка T-005/T-008 — `docs/acceptance/m0-stand.md`. Инвентаризация
> подавлений (§2, базовый уровень 14) по-прежнему актуальна: подавлений не добавлялось.

## 1. Что считается зелёным

Локальный прогон (dev-машина, Windows, Python 3.12.0, `.venv`):

| Гейт | Команда | Результат |
|---|---|---|
| Формат | `ruff format --check .` | чисто |
| Линтеры | `ruff check .` | All checks passed |
| Типы | `mypy .` (`--strict`) | no issues found, 44 файла |
| Тесты | `pytest -m "not live_api and not e2e"` | 183 passed |
| Покрытие | `pytest --cov` | **94.95%** (порог 80%) |
| Секреты | `gitleaks detect` (CI) | job `secret-scan` |
| Миграции | `alembic upgrade → downgrade → upgrade` (CI) | job `migrations` |
| Стенд | `docker compose up --wait` + `/healthz`, `/readyz`, запрет egress у БД (CI) | job `compose-smoke` |

Docker на dev-машине отсутствует, поэтому реальная проверка контейнеров выполняется только в CI
(`compose-smoke`), а локально — контрактные тесты на `deploy/compose*.yaml`
(`tests/integration/test_compose_contract.py`).

## 2. Инвентаризация подавлений проверок (базовый уровень CI = 14)

Правило проекта: число подавлений не растёт без явного решения заказчика; рост фиксируется
job'ом `quality / suppress-growth` (`SUPPRESSION_BASELINE`).

| # | Место | Подачавление | Почему |
|---|---|---|---|
| 1–2 | `packages/common/config.py:207-208` | `noqa: ARG003` | Состав аргументов `settings_customise_sources` определён библиотекой: pydantic-settings вызывает её по именам параметров, переименование «для линтера» сломает загрузку конфигурации. Неиспользуемые источники (`dotenv`, `file_secret`) намеренно не возвращаются — секреты читаются только из `secrets_dir` |
| 3–4 | `apps/engine/main.py:61,120` | `pragma: no cover` | `run()` и `__main__`: обработчики сигналов, цикл heartbeat, остановка. Проверяются job'ом `compose-smoke` (реальный процесс в контейнере), а не юнит-тестом с подменой `signal.signal` |
| 5–6 | `apps/jobs/main.py:73,121` | `pragma: no cover` | То же для `jobs`; реестр задач и проверки готовности покрыты тестами |
| 7–8 | `apps/tgbot/main.py:170,254` | `pragma: no cover` | То же для `tgbot`; `probe_transport`, `probe_egress_exit`, проверки готовности покрыты тестами с подставным HTTP-клиентом (`tests/unit/test_tgbot_transport.py`) |
| 9–10 | `apps/web/main.py:127,154` | `pragma: no cover` | Запуск `uvicorn`; само приложение (`create_app`, маршруты, `/readyz`) покрыто интеграционными тестами через `TestClient` |
| 11–12 | `scripts/dev.py:16,42` | `nosec B404`, `nosec B603` | Bandit ругается на сам факт наличия `subprocess` в dev-обёртке команд. Вызовы идут со `shell=False`, argv берутся из реестра команд этого же файла, пользовательский ввод в них не попадает |
| 13–14 | `scripts/deploy_check.py:22,130` | `nosec B404`, `nosec B603` | То же для скрипта проверки площадки: фиксированные аргументы (`timedatectl show …`, `df`, `free`). Замечание B607 (частичный путь исполняемого файла) **не подавлено, а исправлено**: путь берётся из `shutil.which` и передаётся абсолютным |

Число подавлений закреплено тестом `test_ci_workflows.py::test_базовый_уровень_подавлений_совпадает_с_фактом`:
если в дереве появляется новая строка с `noqa`/`type: ignore`/`pragma: no cover`, а базовый
уровень в workflow не обновлён — тест красный (и наоборот: занизить уровень не получится).

Ничего не «заглушено»: в коде нет `TODO`-реализаций, которые притворяются работой, нет
отключённых тестов, нет `assert True`. Пустые исполнители задач в `JOB_REGISTRY` явно помечены
как отсутствующие, и `/readyz` это показывает (проверка `job_executors` возвращает неготовность).

## 3. Что осталось непокрытым (осознанно)

Непокрытые строки (22 из 631) — это:

- `apps/tgbot/main.py:60-63, 104-105, 127-128, 141, 146-147, 157` — ветки `_client` без прокси,
  ветки разбора ответа Bot API при нестандартном теле, defensive-ветки;
- `apps/web/main.py:54` — ветка «база не вернула результат» (драйвер отвечает так только при
  странном сервере);
- `packages/common/config.py:137, 237, 292-293, 328` — валидаторы, срабатывающие на боевых
  настройках, и ветка «файл секрета пуст»;
- `packages/common/health_probe.py:33`, `packages/common/ids.py:72`,
  `packages/common/logging.py:206-207` — защитные ветки (неподдерживаемый адрес, слишком
  длинный ключ, вспомогательная функция контекста).

Все они — страховки от неожиданного ввода, а не «нереализованная логика».

## 4. Требования, которые M0 не принимает

- Боевой контур (`contour=production`) по-прежнему отказывается запускаться в `engine`
  (`contour_guard`) до вехи M3 — это ожидаемое поведение каркаса, а не готовность.
- Детерминированный исходящий IP для Telegram не настроен: на узле B нет двух правил
  маршрутизации для выделенного пользователя (см. `docs/acceptance/tg-egress.md`, проверка 9).
  Пока это так, канал управления считается «работает, но не принят».
- Прод-площадка не подготовлена (T-011 на паузе заказчика): swap, `ufw`, `fail2ban`, Docker,
  корень НУЦ в доверии — не установлены. `scripts/deploy_check.py` это честно показывает.
