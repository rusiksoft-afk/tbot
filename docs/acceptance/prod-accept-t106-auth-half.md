# Приёмка аутентифицированной половины §9: маршруты выполняет оператор, след разбирает агент (2026-11-23)

Раздел продолжает отложенную половину §9 протокола `docs/acceptance/prod-deploy-t106-adr018.md`
(п. 9 того файла перечисляет, что сознательно не проверялось) и начинается там, где остановался
§9.7 протокола `docs/acceptance/prod-deploy-t112-first-account.md` (первый вход и привязка
2-го фактора).

Что принимается этим срезом:

1. `GET /profile/sessions` — список живых сеансов, отзыв одного (`POST /profile/sessions/{id}/revoke`)
   и немедленное отражение отзыва; отказные ветки (`чужой`, `кривой`, `уже завершившийся` `id` —
   один `404`);
2. `POST /logout` и повторный вход паролем + кодом 2FA;
3. расход резервного кода (сценарий «нет телефона») и состояние остатков;
4. матрица ролей в натуре на двух приглашённых записях (`operator`, `viewer`, церемония
   приглашений `ADR-020`, одобрение `ADR-021`) и «одинаковый `404` на чужой и несуществовавший
   объект» (`ADR-017`);
5. лимиты §8.3 в натуре: `429`, бан адреса, `/locked`.

Режим — по решению заказчика (ask `86c4bc1f-1633-471b-85e4-0fd5b3ce7d3f`): маршрут в браузере
выполняет **оператор**, агент разбирает серверный след. Пароль завода, пароли приглашённых, коды
TOTP, секрет привязки, резервные коды и значения сеансовых куки в канал агента не попадают и
агентом не проверяются (`ADR-004`); адрес браузера оператора при разборе маскируется. Код
приложения в этом срезе не меняется, дайджесты не переснимаются.

## 3. Что выяснилось до измерений: четыре вещи о самой измеряемости

1. **Лестница `viewer ⊂ operator ⊂ admin` в текущем наборе маршрутов в натуре неразличима.**
   Уровней допуска в веб-слое два: `CONSOLE_TIER = viewer` и `ADMIN_TIER = admin`
   (`packages/identity/authorization.py:81,84`), маршрута с требованием `operator` нет ни одного
   (`ROUTE_POLICY` в `tests/integration/test_web_role_matrix.py`, проверка
   `assert CONSOLE_TIER == ROLE_VIEWER` и `ADMIN_TIER == ROLE_ADMIN` на строках 822 и 826).
   Значит в браузере различимы ровно два класса ответов: страницы «любой роли» (`/profile/*`) и
   отказ `403` на разделах `TIER_ADMIN`. Само наследование ролей остаётся доменным фактом
   (`ROLE_LADDER`, `ROLE_RANK`) и становится проверяемым в UI только с маршрутами M1.
2. **Кнопки выхода и навигации в каркасе M0 нет.** `grep logout apps/web/templates/*.html` — пусто,
   `base.html` навигации не содержит. Поэтому все адреса фазы A оператор вводит адресной строкой,
   а `POST /logout` выполняется из консоли разработчика на странице `/profile/sessions`:
   `fetch('/logout',{method:'manual',headers:{'X-CSRF-Token': …из meta…}})`. Значение куки при этом
   у оператора и не передаётся (`ADR-004`).
3. **Расход резервного кода запускает обязательство, которое сейчас нечем исполнить** — см. §4.
4. **Отказ `429` не оставляет события в журнале приложения.** За 25 минут проб при шести отказах
   по источнику в журнале ровно 6 записей `csrf_rejected`; ни одной записи на частотный отказ и ни
   одной записи с кодом состояния нет вовсе (журнала «на запрос» в слое нет). Единственный
   серверный след `429` — строки `rate_buckets`. Отдельно: `/metrics` содержит только
   `tbot_build_info` и метрику egress-адресов, счётчика ответов по кодам там нет. Запись журнала о
   `429` — перенос на `T-109` (`ADR-009`), это не новый пропуск.

## 4. Решение заказчика по фазе резервного кода и следствие для порядка

Вопрос был поставлен так: расход кода необратим, пачка у единственного живого `admin` одна (10), а
обязательство перевыпуска (`recovery_state`, `RECOVERY_REGENERATION_WINDOW` = 7 суток с момента
последнего расхода) при неисполнении закрывает `POST /totp` (`GRACE_EXPIRED_DETAIL`). Исполнить
обязательство сейчас негде: кнопки «выпустить ещё коды» на `/profile/security` нет (остаток
`T-104`), повторная привязка даёт `409` («первичная привязка не служит перепривязкой»,
`POST /mfa-enroll/start`), маршрута «сброс привязки» в разделе администрирования нет — это §9.3
п. 6, то есть открытая `T-106`. Для `rusiksoft` дедлайн наступил бы ≈ 2026-11-30 04:5x UTC, после
чего каждый вход стоил бы один резервный код, а при исчерпании кодов учётная запись стала бы
недостижима через UI.

Принят вариант (3): **расход измеряется на приглашённой (второстепенной) учётной записи**, пачка
администратора остаётся нетронутой (10/10). Следствие, которое пришлось учесть: фазу нельзя
откладывать в конец среза, потому что по итогам приёмки приглашённые записи переводятся в
`archived` (`CLOSED_STATES` закрывает вход, `login_closed_reason` отвечает как при неверном
пароле) — резервный путь для них закроется вместе с входом. Порядок среза:

```text
A сеансы и /logout
B приглашения (operator, viewer) → приём ссылки → привязка 2FA → одобрение → матрица ролей
  → расход одного резервного кода на viewer → архив обеих записей
C лимиты §8.3 (кроме бана адреса — см. §6.4)
финал: «Отозвать все сеансы» в окне администратора и итоговый снимок
```

## 5. Уточнение наблюдения §1.58 п. 7: что именно расходует бакет `login_ip`

Сет 1 — шесть `POST /login` с пустой формой, но с отказом по источнику (с адреса агента,
учётных записей пробы не касаются):

```text
2 × Origin: https://evil.example      → 403
2 × Origin: http://tbot.rusiksoft.ru  → 403
2 × Sec-Fetch-Site: cross-site        → 403
rate_buckets (scope login_ip) за окно: 0 записей — бакет не тронут
журнал web: ровно 6 записей csrf_rejected (detail: Origin/Sec-Fetch-Site), traceback/exception — 0
```

Канон наблюдения: **отказ по источнику на `/login` счётчик частоты не расходует**, пустая форма при
своём источнике — расходует (см. сет 2 в §6.1). Комментарий `apps/web/security/rate_limit.py:75–77`
(«и пустая форма, и отказ CSRF стоят обращения») для `/login` неверен в части отказа CSRF:
`ensure_same_origin` (`apps/web/routes/login.py:210`) стоит раньше
`enforce_scope(LOGIN_IP_SCOPE)` (`:222`). Порядок проверок — требование `ADR-008` («отказ токена не
должен стоить обращений в базу и расходовать лимит жертвы»), так что правится комментарий, а не
код; отдельной правки в этом срезе нет, `T-117` её не касается.

## 6. Лимиты §8.3 в натуре

### 6.1 Предел частоты по адресу (`login_ip` = 10/мин) — измерено

Сет 2 — двенадцать `POST /login` с пустой формой и своим источником (`Origin: https://…`,
`Sec-Fetch-Site: same-origin`), старт в чистом окне:

```text
запросы #1…#10  → 400 (пустая форма)
запрос  #11     → 429 Too Many Requests, Retry-After: 49, в теле ссылка /locked?reason=rate
запросы #12–#13 → 429 (тот же отказ)
rate_buckets:   login_ip, окно 05:21:00+00, window_seconds 60, attempts = 13
                (совпадает с числом POST, прошедших проверку источника: счётчик
                увеличивается и на отказе по частоте — окно растёт, а не замирает)
во время отказа: GET /login → 200, GET / → 200 (страница входа остаётся доступной)
users=1 (не изменилось), sessions: живых сеансов не появилось, пробы аутентификацию не выполняли
```

`Retry-After: 49` совпадает с началом следующего окна: `retry_after_seconds(window_end, now)`,
окно — `05:22:00+00` (`ADR-007`: начало окна выравнивает приложение).

### 6.2 Страница `/locked` — измерено

```text
GET /locked?reason=rate     → 200; заголовок «Вход заблокирован», текст
                               «С этого адреса было слишком много попыток входа за короткое время.
                                Предел держится на адресе, а не на учётной записи: повторите позже.»
                               + ссылка «Перейти на страницу входа» (/login)
GET /locked?reason=attempts → 200 (объяснение по попыткам учётной записи)
GET /locked                 → 200; GET /locked?reason=revoked → 200 (неизвестная причина не даёт
                               отказа: страница состояния не читает текст из параметра запроса,
                               объяснение берётся из закрытого набора кодов)
```

### 6.3 Отказ по источнику и частота — не одно и то же

Шесть отказов §5 (по источнику) не добавили в окно ни одной попытки, двенадцать запросов §6.1 (по
частоте) добавили тринадцать. Различие принципиально для §8.3: источник решает «принимать ли
запрос», частота — «сколько запросов принято».

### 6.4 Бан адреса (`ip_ban`: 3 неудачи за 5 минут) — отложен в конец среза

Причина переноса, обнаруженная при подготовке проб: адрес браузера оператора и адрес проб агента
лежат в **одном /16 провайдера** (`5.158.0.0/16`), точные адреса различаются
(сравнение `bucket_key` окна `login_ip` с `sessions.ip` последней записи — `false`). Ключ бакета
`ip_ban` — точный адрес, поэтому бан адрес агента оператора не затронет, но при CGNAT-ротации
адрес может совпасть, а бан (§8.2, `IP_BAN_DURATION`) закрывает `POST /login`, `POST /totp` и
резервный путь на срок до `window_start + 300 c + 15 мин` ≈ 20 минут. Уже выданный сеанс бан не
отзывает (охрана маршрутов бан не проверяет), но новый вход стал бы невозможен посреди фазы A/B.

Поэтому промер бана выполняется последним — после того как все браузерные входы сделаны, — и
содержит три замера: (1) три неудачи по **несуществующему** логину → строка `ip_ban`
(`window_seconds = 300`, `attempts = 3`) и `429` с `reason=rate` на третьем запросе; (2) четвёртый
запрос → `429` по активному бану (проверка `ban_until` идёт до счётчика частоты и до Argon2id), а
`GET /login` остаётся `200`; (3) отложенная повторная проба не ранее чем через 20 минут — `401`,
то есть бан отпускает сам, без ручных правок. Учётные записи при этом не затрагиваются вовсе:
неудача по несуществующему логину не двигает `users.failed_attempts` (`register_login_failure`
вызывается только для найденной строки), а окно адреса считается — это и есть требование §8.2
«3 неудачные попытки с одного IP».

### 7.1 Принято в натуре

1. **Список**: строки только живые (`revoked_at is null and expires_at > now()`); свой вход помечен
   `текущий сеанс`; «Последняя активность» — `last_seen_at` в МСК; user-agent печатается побайтово
   (111 символов = `length(user_agent)` в базе); адрес входа показан владельцу (§1.59 п. 7 — своя
   пара адрес/сеанс), при этом в списке нет ни `token_hash`, ни срока годности строки.
2. **Две живые строки одновременно** наблюдались дважды: `b1c2`+`26dd` (07:34:06/07:35:14) и
   `2bde`+`8ca3` (07:45:13/07:54:03). Разделяющее условие явно: отдельное хранилище куки даёт
   `InPrivate` или другой браузер, обычная новая вкладка того же браузера — нет.
3. **Отзыв другой строки из своего списка**: `b1c2` → `revoked_at 07:37:15` (живых осталось 1),
   `8ca3` → `revoked_at 07:56:40`. Оба отзыва — из другого хранилища, счётчик `mutation_user` по
   одной мутации на отзыв (окна 07:37 и 07:56).
4. **Немедленное отражение отзыва для другого держателя**: в окне отозванного входа
   `/profile/sessions` отдаёт страницу «Сеанс завершён — Этот сеанс отозван. Если вы его не
   отзывали, смените пароль и посмотрите список устройств.» с кнопкой «Войти заново». Это исход
   `reason=revoked`, который выдаёт охрана маршрута по найденной по куке отозванной строке
   (`security/sessions.py:355`), а не ручная навигация оператора.
5. **Различие «билета нет» и «билет отозван»**: в окне, откуда уже отзывали свой текущий вход
   (кука снята `_revoke_finished`), `/profile/sessions` даёт тихий редирект на `/login` — форма
   «Вход в консоль», страницы состояния нет; в окне с живым билетом на отозванной строке — страница
   состояния с причиной. Оба наблюлись: различие состояний «билета нет» / «билет есть, но отозван»
   в UI разное, как и задумано (`security/sessions.py:344`).
6. **Отзыв текущего входа** (`current_ended=True`) — трижды: `d5a0` 07:27:49, `de14` 07:31:43,
   `26dd` 07:42:56; каждый раз браузер оказывался на `/session-expired?reason=revoked`, а кука
   снималась. Страница подтверждения своего отзыва называет объект и отношение: «Отношение к вам:
   текущий сеанс» и предупреждение `REVOKE_CURRENT_WARNING` («Это тот же сеанс, с которого вы
   подтверждаете отзыв…») — `apps/web/routes/sessions.py:322–333`.
7. **`GET` ничего не меняет**: страница подтверждения отдаётся обычным `GET`ом (`200`, HTML) и не
   отзывает сеанс; в базе счётчиков мутаций на неё нет. Различия «уже отозван», «не тот формат»,
   «не вам» страница подтверждения не показывает.
8. **Отказные ветки — одно тело на четыре основания**. Оператор из окна с живым входом получил
   одинаковый ответ на: вымышленный `00000000-0000-0000-0000-000000000000`, неразбираемый
   `not-a-uuid`, завершившийся по сроку `01a206e0-…0b53`, уже отозванный `01a20753-…b1c2` —
   `{"status":"not_found","detail":"живого сеанса с таким идентификатором нет"}`. Контроль
   «свой живой `id` даёт страницу подтверждения, а не `404`» — пункт 7. Код состояния в браузере
   не сверялся (вкладка не показывает), по обработчику это `404` (`_session_gone`); намеренность
   единого ответа — §8.8 и `ADR-017` п. 4.
9. **Idle-завершение**: `df20`, `0b53`, `5eb7` дошли до `expires_at` без отзыва; в окне оператора
   была страница «Вы долго не действовали, и сеанс завершился. Войдите заново — стратегии и отчёты
   на месте.» (`reason=idle`) с кнопкой «Войти заново». Продление окна активностью подтверждено:
   у живой строки `expires_at` всегда `last_seen_at` + 30 минут (например `2bde`: активность
   07:51:45 ⇒ срок 08:21:45).
10. **Разметка причины на странице состояния** (пробы агента, `curl` без входа): `idle`, `revoked`,
    `expired` — свои абзацы; `attempts` и `rate` — текст страницы блокировки учётной записи;
    `csrf` — про повторную отправку формы; `malformed` — про исправление адреса (с последующей
    чисткой куки); произвольное, пустое и отсутствующее `reason` — общий абзац «Сеанс был
    завершён…». Параметр в страницу не подставляется: `<script>`-проба и `?reason=zzz` дали общий
    абзац, сценария на странице нет.

### 7.2 Не закрыто в фазе A

- **`POST /logout` в натуре не измерен**: ни один запрос к приложению не дошёл. Причина — ошибка
  агента в первом сниппете (`method:'manual'` вместо `redirect:'manual'`: `fetch` послал метод
  `MANUAL`, маршрут `POST /logout` не совпал; по базе видно отсутствие мутаций на выход).
  Повторяется исправленным сниппетом. Пока пункт закрыт только прогонами: выход отзывает строку
  записью, а не только стирает билет (`apps/web/routes/login.py:420–436`).
- **`revoke-all`** намеренно оставлен последним шагом среза: он заодно убирает живые входы и
  закрывает пункт без лишнего обряда входа.
- **Страница подтверждения для чужого сеанса** в натуре не переснята (переснята только для своего,
  п. 6). Ожидаемое предупреждение для другого устройства: «Сеанс будет отозван немедленно:
  с перечисленного устройства вход придётся выполнять заново. Отменить отзыв задним числом
  нельзя.» (`apps/web/routes/sessions.py:326–329`). Сами два отзыва чужих строк базой подтверждены
  (п. 3), поэтому расхождение касается только текста подтверждения.

### 7.2.1 Почему `logout` в поле не «нажимается»: у маршрута нет элемента управления

В сборке `web` ни один шаблон не ссылается на `/logout`: `grep -rn logout apps/web/templates/` —
ноль совпадений. Маршрут есть (`routes/sessions.py:264`, уровень допуска `TIER_SESSION`, строка
матрицы `test_web_role_matrix.py:206`), кнопки и ссылки нет: раздел профиля и шапка консоли —
веха M1. Значит полевая проверка `POST /logout` невозможна без подстановки запроса (Console либо
HTTP-клиент) — это свойство сборки, а не пропуск приёмки. Пункт закрывается либо подстановкой
запроса оператором с чтением `revoked_at` по базе, либо признан покрытым прогоном
`test_выход_отзывает_сессию_и_стирает_куку`.

Для сравнения: `POST /profile/sessions/revoke-all` остаётся полевым — ссылка на него отдаётся
на странице списка (`routes/sessions.py:107`), то есть элемент управления есть.

### 7.3 Находка: «последняя активность» отозванной строки перестёртывается

На 5 из 5 отозванных строк `last_seen_at == revoked_at`: `UPDATE` отзыва поднимает колонку
`last_seen_at` через общий `onupdate=now()` (`packages/storage/models/session.py`). Реальная
последняя активность отозванной строки читается по `expires_at − 30 минут` (например `8ca3`:
`expires_at 08:26:31` ⇒ активность 07:56:31, а `revoked_at` и `last_seen_at` — 07:56:40). Правок
в этом срезе нет: на допуск, отзыв и срок годности поведение не влияет, страдает только отображение
времени. Для `T-109` вывод зафиксирован: в журнале «последнюю активность» отозванной записи нельзя
брать из `last_seen_at`, иначе у всех отозванных записей она будет равна самому отзыву. Правку делает
`T-109`/`T-102` по решению заказчика.

### 7.4 Половина механики бана адреса получена случайно

В 07:35 UTC оператор один раз ошибся паролем — и бакет `ip_ban` появился сразу с `attempts=1`
(`window_seconds=300`). То есть окно заводится с первой неудачи, а решение о бане принимается на
пороге 3 (`IP_BAN_THRESHOLD=3`) — механика подтверждена наблюдением, сам бан не сработал: единичная
неудача оператора не слилась с пробами агента (адреса разные, §6.4). Остаток — осознанный промер
бана в конце среза.
