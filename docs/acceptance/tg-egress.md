## 3. Главный незакрытый пункт: ротация исходящего IP

Два замера подряд дали два разных города (NL, затем SE) при одном и том же пользователе:
выбор делает балансировщик на узле B. Следствия для проекта:

- Bot API видит разные IP одного и того же бота, причём из диапазонов CDN/публичных прокси;
  это типичный триггер анти-злоупотреблений Telegram (троттлинг, редкие `429`, внезапные
  отказы) и мешает разбору инцидентов;
- правило на узле B обязательно: `{ "user": ["<имя пользователя tbot>"], "outboundTag": "<конкретный exit>" }`
  и запрет приватных/внутренних адресов для этого пользователя;
- после добавления правила — повторить проверки 2–4 и 9, зафиксировать IP, который видит
  Telegram, и добавить его в мониторинг (`tg_egress_exit_ip`, TZ §10.7, §12.5).

## 4. Что делает приложение

Единственная точка входа для сервиса — `socks5h://<user>:<pass>@127.0.0.1:10800`, при этом
разрешение имени `api.telegram.org` обязано выполняться на стороне узла B (`socks5h`, а не
`socks5`): собственный DNS прод-площадки отдаёт недоступный `149.154.166.110`
(`docs/research/03 §3.4`). Проверка цепочки сертификата Telegram не отключается ни при каких
условиях; при несовпадении — алерт `tg_tls_mismatch` (TZ §12.5).

### 4.1 Дефект, найденный при запуске контейнера `tgbot` (2026-11-20 16:57 UTC)

Контейнер `tbot-tgbot-1` из закреплённого digest (набор от `d35f957`) не стартует: падает в
`httpx` на построении прокси-URL. Замеренная строка ошибки:
`ValueError: Unknown scheme for proxy URL URL('socks5h://tgbot:[secure]@host.docker.internal:10800')`.

Причина: `httpx` (пиннинг образа и dev-venv — 0.27.2) принимает в `Proxy(...)` только схемы
`http`, `https` и `socks5` (`httpx/_config.py`, `if url.scheme not in ("http", "https", "socks5")`),
хотя нижний слой `httpcore` проксирует и `socks5`, и `socks5h`. То есть контракт §4 в формулировке
`socks5h` не исполним через `httpx` в текущем пиннинге: приложение обязано строить URL со схемой
`socks5://`, а **удалённое разрешение имени проверять замером** (httpcore передаёт домен прокси,
предварительно не резолвя его; если на площадке выяснится, что резолвинг идёт локально, нужен
другой транспорт — иначе вернётся недоступный `149.154.166.110`).

Второй независимый слой того же дефекта: слушатель SOCKS на прод-ВМ поднят только на
`127.0.0.1:10800` (проверка 2 таблицы выше), а контейнер видит хост через
`host.docker.internal:host-gateway` (`deploy/compose.yaml §186-187`, есть) — то есть через адрес
моста Docker. Даже после замены схемы соединение не пройдёт, пока слушатель не будет привязан к
адресу шлюза моста (или пока `tgbot` не окажется в сетевом пространстве хоста). Привязка
`127.0.0.1` наружу не отдаёт: мостовой адрес не маршрутизируется вовне, а `ufw` его не пропускает;
аутентификация SOCKS (пользователь + пароль) сохраняется.

Что это меняет: работа входит в остаток `T-714` (три артефакта — код `apps/tgbot`, конфиг xray
клиента на прод-ВМ с правкой только через `python json load/dump`, и замер удалённого DNS после
первой же пересборки образа). По ходу замера отдельно подтверждено полезное: пароль SOCKS в логе
оказался замаскирован (`[secure]`), то есть маскирование `CREDENTIALED_URI_RE` работает и на
прокси-URL (`packages/common/config.py §50`).

## 5. Замечания по обновлению и воспроизводимости

- сверка пакета: у релизов Xray нет отдельного `.sha256`-ассета, а теле релиза в тот день не
  содержало дайджест в разбиваемом виде; поэтому закреплён SHA-256 скачанного файла, а при
  следующем обновлении дайджест сверяется вручную с официальной страницей релиза;
- особенности Xray 26.x, проверенные на площадке: в outbound VLESS пользователь задаётся в
  `settings.vnext[].users[]`; для SOCKS вход `accounts` — массив объектов
  `{"user":…,"pass":…}`; в правиле маршрутизации нет поля `tag` (используется `inboundTag`);
  проверка конфига — `xray -config <файл> -test` (в написании `xray test -config …` команда
  отсутствует);
- операционная ловушка: `pkill -f "<подстрока>"` на площадке убивает и собственный канал
  управления, если подстрока встречается в командной строке сессии; остановку выполнять по
  systemctl или `pkill -x xray`.

Проверка 10 переснята после перезаписи `telegram_token` (2026-11-20 17:33 UTC: 46 байт, `640`, `0:10001`,
`--check` зелёный) — тот же `getMe` через SOCKS даёт `"ok": true`, `id=9151321697`. **Не подтверждён
отзыв прежнего значения**: если сохранён тот же токен, а не новый выпуск BotFather, экспонирование
сохраняется — нужен `/revoke` и повторная запись файла. **Закрыто 2026-11-20:** подтверждено заказчиком (ask `5a45172e`), что сохранён новый выпуск BotFather, а прежний токен отозван через `/revoke`.
