# 11. История, бэктест, оптимизация

Бэктест — не «украшение»: без него параметры стратегий необоснованны, а решение о переходе в
`production` невозможно (см. `REQ-arch-06`). Требования ниже обязательны, потому что типовые
ошибки бэктеста (заглядывание вперёд, нереалистичное исполнение, игнор комиссий) делают
результат вредным, а не нейтральным.

## 11.1 Загрузчик истории (`jobs/history-loader`)

- Источники: `GetCandles` (боевой контур, read-only; при возможности — параллельно песочница
  для отладки кода загрузчика).
- Обязанности: разбиение диапазона на окна по `limit` с учётом ограничений интервала
  (см. `docs/tz/03 §3.7`), чекпойнты в `history_jobs`, идемпотентная запись (конфликт →
  обновление), дедупликация, паузы под бюджетом сервиса котировок (600/мин, запас 20%),
  обработка 429/5xx с backoff, журналирование пропусков (нет торгов, инструмент не торговался,
  сплит), проверка монотонности и связности (разрывы >1 свечи → запись в `history_gaps`).
- Набор интервалов по умолчанию для whitelist-инструментов: `1MIN` (24 мес.), `5MIN`, `15MIN`,
  `HOUR` (5 лет), `DAY` (6 лет), плюс `WEEK/MONTH` для долгосрочных оценок; 5сек/10сек/30сек —
  только по явному запросу (глубина API ограничена 200 минутами, хранить месяц).
- Манифест датасета (`datasets.manifest`): список `(uid, interval, from, to)`, число строк,
  контрольная сумма данных (SHA-256 от канонической сортировки), версия выгрузки, источник,
  наличие пропусков. Прогон бэктеста обязан ссылаться на датасет.

`REQ-backtest-01` Ни один прогон не может использовать данные вне датасета с манифестом;
повторный прогон на том же датасете и тех же параметрах обязан дать идентичные метрики и
набор сделок (тест воспроизводимости).

## 11.2 Событийный движок

- Порядок событий внутри бара строго определён и зафиксирован в тестах:
  `приход бара → расчёт индикаторов по закрытым барам → сигналы стратегии → заявки на след. бар →
  исполнение заявок по правилам модели → обновление позиции/кэша`.
- Заглядывание вперёд запрещено: на моменте `t` доступны только бары с
  `ts + interval ≤ t` и только `open/high/low/close/volume` текущего бара в той последовательности,
  которая задана моделью; `close` текущего бара недоступен для решения внутри бара
  (кроме явного режима `bar_close_assumption`, который запрещён для стратегий M1).
- Один код стратегии для бэктеста и боя (`REQ-arch-03`), движок предоставляет тот же
  `StrategyContext`.

### Модель исполнения (обязательна к настройке, пессимистична)

| Параметр | Default | Смысл |
|---|---|---|
| `fill_model.limit_touch` | `low≤price` (buy) / `high≥price` (sell) | условие исполнения лимитной заявки |
| `fill_model.queue_position` | `pessimistic` | исполняется только если объём бара ≥ объёма заявки; иначе — частичное |
| `fill_model.participation_cap` | 0.05 | максимум 5% объёма бара на одну заявку |
| `fill_model.market_slippage_bps` | 10 | проскальзывание рыночных заявок |
| `fill_model.gap_rule` | `worse_price` | гэп: исполнение по цене гэпа, а не по цене заявки |
| `commission.model` | `flat_bps` + `min_fee` (значения задаёт оператор) | API брокера комиссий не отдаёт |
| `commission.per_lot_fee` | 0 | для фьючерсов (веха M4) |
| `spread.from` | `orderbook` (если есть) / `constant_bps` | источник спреда |
| `corporate_actions` | `adjusted_prices` (опция `raw_prices`) | сплиты/дивиденды: как считаются цены |
| `dividends_reinvest` | `false` | учёт дивидендов/купона как денежный поток |
| `tax` | `off` (пометка «брокер — налоговый агент») | отдельная оценка налога — вне объёма |

- Инструменты, вышедшие из обращения (делистинг/блокировка), обязаны оставаться в датасете
  до даты прекращения торгов (защита от «выжившего»): движок обязан закрыть позицию по
  последней доступной цене с пометкой `forced_exit`.

### Метрики (обязательный набор)

Доходность: итоговая, CAGR, по месяцам; риск: максимальная просадка (глубина и длительность),
макс. просадка в днях восстановления, волатильность дневных доходностей, VaR95 (исторический),
Sharpe, Sortino, Calmar; сделочные: число сделок, win rate, средний профит/убыток, profit
factor, expectancy, средняя длительность позиции, максимальное число последовательных убытков,
средний проскальзывание vs план; устойчивость: оборот, доля времени в позиции, чувствительность
к `slippage_bps ±5` (обязательный «стресс-срез»); издержки: суммарные комиссии, доля издержек
в P&L-результате. Каждая метрика сохраняется в `backtest_metrics` с единицей и версией формулы.

`REQ-backtest-02` Метрики считаются по **одной** формуле, зафиксированной в модуле `backtest.metrics`
с юнит-тестами на эталонных рядах (в т.ч. вырожденные случаи: 0 сделок, 1 сделка, все убыточные).

## 11.3 Оптимизация и проверка устойчивости

- Методы: сетка, случайный поиск, опционально Bayesian/Optuna (решение через ADR; если
  выбирается — с явным лимитом итераций и бюджета времени).
- **Walk-forward обязателен**: минимум 5 окон «обучение → проверка» сдвигом вперёд;
  итоговая оценка стратегии — по совокупности out-of-sample окон, а не по ин-sample.
- Правило устойчивости параметров: результаты в соседних точках сетки не должны отличаться
  более чем на 30% (иначе параметры считаются переобученными, UI помечает такой прогон
  `FRAGILE`).
- Обязательный отчёт «что бы случилось»: 3 исторических стресс-периода (выбираются
  администратором, например периоды резких движений рынка) прогоняются автоматически для
  любой конфигурации, предложенной оптимизатором.
- Лимиты бюджета: максимум точек сетки на прогон (по умолчанию 200), максимум одновременных
  воркеров (2 на dev-сервере, 4 на проде), ограничение времени прогона (30 минут) и памяти;
  при превышении — задача падает с объяснением, а не «доживает как получится».

## 11.4 Прозрачность результата в UI

Карточка прогона обязана показывать: датасет (манифест + хэш), период, модель исполнения и
комиссий (значения!), параметры, метрики in-sample vs out-of-sample, график эквити с
заштрихованной просадкой, таблицу сделок (с причинами входа/выхода), распределение P&L по
сделкам, предупреждения (`FRAGILE`, `GAPS_IN_DATA`, `FORCED_EXITS`, `LOOKAHEAD_DISABLED`) и
постоянную плашку: «результат проверки на истории не гарантирует результат в реальной торговле».

`REQ-backtest-03` Прогон без указанных предупреждений не может быть использован как основание
для запуска в `production`: UI не даёт нажать «создать стратегию на основе прогона», если
есть незакрытые предупреждения (нужно явное подтверждение оператора с записью в `audit_log`).

## 11.5 Проверка «на живую»: paper-режим как второй фильтр

- Переход в `production` требует: ≥3 прогонов бэктеста (в разных периодах) + ≥10 торговых дней
  в `paper` (значения настраиваются администратором, но не ниже 1/3).
- Отчёт «paper vs backtest» за период: разница по среднему проскальзыванию, числу сделок,
  P&L; если расхождение > 25% по P&L при тех же параметрах — система помечает стратегию
  `SUSPECT_MISMATCH` и требует объяснения оператора.
