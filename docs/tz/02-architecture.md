# 02. Архитектура, процессы, контуры, контракты

## 2.1 Процессы (контейнеры)

| Процесс | Ответственность | Масштаб | Сеть наружу |
|---|---|---|---|
| `engine` | торговое ядро: `strategy-engine`, `risk-gate`, `order-executor`, `market-data`, `portfolio-sync` | 1 экземпляр (active), опционально 1 standby | T‑Invest API (gRPC), PostgreSQL |
| `web` | FastAPI-консоль (`web-auth`, `web-console`) | 1–2 экземпляра за Caddy | PostgreSQL |
| `tgbot` | `notifications` + `telegram-bot` | 1 экземпляр (long polling) | api.telegram.org, PostgreSQL |
| `jobs` | загрузчик истории, бэктест-воркеры, дайджесты, очистка/архив данных, бэкапы | 1 + N воркеров по задаче | T‑Invest API (read), PostgreSQL, объектное хранилище |
| `postgres` | база | 1 (плюс реплика/бэкап вне контейнера) | — |
| `caddy` | TLS, rate-limit, IP-allowlist | 1 | LE, 443 наружу |

Общий для всех `engine`/`web`/`tgbot`/`jobs`: один и тот же код конфигурации, один источник
констант риска (пакет `risk_gate`), одни и те же миграции. Никакой бизнес-логики в `web` или
`tgbot`: оба только вызывают сервисы пакетов.

`REQ-arch-01` Торговые вызовы выполняет **только** процесс `engine`. `web`, `tgbot`, `jobs`
не имеют в конфигурации токенов для записи и физически не соединяются с брокером для мутаций
(используют очередь команд → `engine`).
`AC-arch-01` Проверка: в compose-профиле `web/tgbot/jobs` отсутствуют переменные торговых
токенов; интеграционный тест «команда из UI → запись в таблицу `commands` → исполнение `engine`».

`REQ-arch-02` Все управляющие действия (старт/пауза/стоп стратегии, аварийное снятие заявок,
изменение параметров, отзыв токена) идут через единый `CommandService` с: проверкой роли,
требованием подтверждения (TOTP для критичных), записи в `audit_log` до исполнения, идемпотентным
`command_id`.
`AC-arch-02` Повтор команды с тем же `command_id` не приводит ко второму исполнению (тест).

## 2.2 Поток данных (канон)

```
[T-Invest API] --gRPC streams--> market-data --нормализованные события--> шина процесса
       ^                                                             |
       |                                     instrument-catalog <-----+
       |                                                             |
 portfolio-sync <---unary (read)                            strategy-engine
       |                                                             |
       v                                              торговое намерение (Intent)
   storage  <----------------------- risk-gate  <--------------------|
       |                                 |
       |                                 v (разрешено/отклонено + причина)
       +-----------------------> order-executor ---gRPC (write)--> [T-Invest API]
                                          |
                            события заявок |  позиции/портфель
                                          v
                     notifications --> telegram-bot / web-console
```

`REQ-arch-03` Стратегия общается с миром только через типизированный вход
(`MarketSnapshot`, `PortfolioSnapshot`, `StrategyContext`) и типизированный выход
(`Intent`, `CancelRequest`, `Nothing`, `Explanation`). Прямых импортов `broker_gateway` в
пакетах `strategy_*` быть не должно (проверяется тестом архитектуры / `import-linter`).
`AC-arch-03` Проверка: `import-linter` контракт в CI — слой `strategy_*` не импортирует
`broker_gateway`, `order_executor`, `storage`.

## 2.3 Модели намерения и исполнения (контракт)

```python
# packages/risk_gate/model.py  (упрощённо, поля обязательны/опциональны фиксируются в коде)
class Intent:
    intent_id: UUID              # клиентский ключ, сохраняется ДО сетевого вызова
    strategy_id: UUID
    instrument_uid: str
    side: Literal["buy", "sell"]
    quantity_lots: int           # только целые лоты
    order_type: Literal["limit", "market", "bestprice"]
    limit_price: Decimal | None  # уже нормализована к шагу инструмента
    price_type: Literal["point", "currency"]
    time_in_force: Literal["day", "fill_and_kill", "fill_or_kill"]
    reason: str                  # человекочитаемое обоснование + хэш правил
    allow_margin: bool           # согласованный флаг стратегии, см. docs/tz/06
    max_slippage_bps: int        # предельное отклонение цены исполнения
    expires_at: datetime | None  # UTC, время жизни намерения внутри системы
```

Решение `risk-gate`: `Approved(decision_id, risk_snapshot)` или `Denied(code, message,
risk_snapshot)`. Отказ обязан содержать код из перечня `docs/tz/06 §6.4`. Намерение и решение
пишутся в БД **до** обращения к брокеру (`REQ-arch-04`).

## 2.4 Контуры исполнения

| Контур | Куда идут заявки | Источник рыночных данных | Назначение |
|---|---|---|---|
| `sandbox` | песочница брокера (`sandbox-invest-public-api...`) | реальный рынок (read из боевого контура) + эмуляция исполнения брокера | проверка интеграции: контракты, состояния заявок, идемпотентность |
| `paper` | только внутренняя книга (`order_executor.paper`) | реальные котировки боевого контура | проверка стратегии: проскальзывание, комиссии, ликвидность, поведение при гэпах |
| `production` | боевой контур брокера | реальные котировки | торговля реальными деньгами |

`REQ-arch-05` Контур задаётся **на экземпляре стратегии** в конфигурации и фиксируется в БД при
создании; смена контура — отдельная операция с подтверждением TOTP и записью в audit log;
смена контура не меняет идентификатор стратегии и её историю.
`REQ-arch-06` Переход `paper → production` невозможен «автоматически по результатам»:
требуется явное действие оператора + валидация, что стратегия имеет ≥ N прогонов бэктеста и
≥ M дней в `paper` (значения N, M — конфигурация администратора, по умолчанию 3 и 10).
`REQ-arch-07` Один токен не используется одновременно для `sandbox` и боевого контура: у
песочницы отдельный токен и отдельная запись в `credentials` (разделение подтверждается тестом).
`AC-arch-07` Попытка отправить sandbox-заявку боевым токеном (или наоборот) даёт явную ошибку
контрагента и автосбой стратегии с алертом, а не «тихий» переход в другой контур.

## 2.5 Точки восстановления состояния

`engine` при старте выполняет `boot sequence` (регламент, обязателен):

1. загрузка конфигурации + проверка сертификата НУЦ/времени (NTP);
2. проверка токенов всех подключённых счетов (read-only), срок действия, права;
3. `portfolio-sync.sync_all()`: позиции, деньги, открытые заявки, стоп-заявки;
4. `order-executor.reconcile()`: сопоставление собственных незакрытых намерений/заявок с
   ответами брокера по клиентскому ключу; неизвестные заявки → изоляция инструмента
   (`quarantine`), торговля по нему блокируется до разбора оператором;
5. `market-data.resume_streams()`;
6. допуск стратегий к сигналам только после успешных шагов 1–5.

`REQ-arch-08` Если любой шаг boot sequence завершился неуспешно, стратегии не запускаются;
система остаётся в состоянии `DEGRADED`, в UI и Telegram — алерт с причиной.
`AC-arch-08` Сценарий: БД доступна, токен отозван → система в `DEGRADED`, сигналы не
формируются, открытые заявки не создаются; после подмены токена boot проходит заново.

## 2.6 Отказоустойчивость (что обязательно моделируется)

| Событие | Требуемое поведение |
|---|---|
| Обрыв gRPC-стрима котировок | автопереподключение с backoff (1,2,4,…,60 с + jitter), догрузка пропущенных свечей через `GetCandles`, метрика `stream_reconnects`, алерт при >3 за 5 мин |
| Обрыв стрима заявок/портфеля | то же + полный `reconcile()` перед следующими мутациями |
| Таймаут/разрыв при `PostOrder` | не создавать новый клиентский ключ; опрос `GetOrderState` по сохранённому ключу (`ORDER_ID_TYPE_REQUEST`), затем `GetOrders`; повтор только при доказательстве непринятия |
| Частичное исполнение | пересчёт остатка намерения, обновление таблицы уровней/позиции, события `order_partial_fill` |
| Рестарт `engine` при активных заявках | состояние восстанавливается из БД + сверки; дублирование уровней запрещено |
| Обрыв связи с брокером > T (по умолчанию 30 с) | новые сигналы стоп; опционально (настройка) — снятие собственных активных заявок |
| Отказ Postgres | `engine` переходит в `HALTED`, стримы закрыты, записи буферизуются кратко (≤60 с) и при восстановлении досылаются; при буферизации мутации запрещены |
| Отказ Telegram | уведомления складываются в очередь с ретраями; торговля не останавливается |
| Переход на летнее/зимнее время, смена расписания | расписание только из API (`TradingSchedules`), локальные «вечные» расписания запрещены |

## 2.7 Идентификаторы и время

- Внутренние id — UUIDv7 (упорядоченные по времени); клиентский ключ заявки = UUIDv4 в
  формате, удовлетворяющем требованию API (строка ≤36 символов).
- Всё время в системе — UTC (`timestamptz`), вывод в UI — МСК с явной подписью «МСК».
- Локальные часы сервера обязательны через chrony; расхождение >2 с → алерт и запрет TOTP
  (см. `docs/tz/08`).

## 2.8 Конфигурация

Три слоя: (1) неизменяемые константы продукта (в коде, с тестами); (2) конфигурация экземпляра
(`configs/tbot.yaml`: контуры, пути к ключам, адреса, бюджеты API, пороги алертов); (3)
пользовательские настройки (в БД: стратегии, лимиты в разрешённом диапазоне, уведомления).
Секреты — только из переменных окружения/файлов монтирования, никогда из YAML в git.
`REQ-config-01` Любая настройка риска вне допустимого диапазона (например, дневной убыток 50%)
отклоняется на валидации с указанием разрешённого диапазона; значения по умолчанию —
`docs/tz/06 §6.5`.
