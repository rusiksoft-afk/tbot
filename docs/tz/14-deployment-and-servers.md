# 14. Деплой, окружения, требования к серверам (с расчётом)

## 14.1 Окружения

| Окружение | Где | Назначение | Контуры брокера |
|---|---|---|---|
| dev (рабочая машина) | Windows/WSL или Linux, Docker Desktop | разработка, тесты, mock-брокер | mock + песочница (по желанию) |
| **приёмка и эксплуатация (одна ВМ)** | `153.51.172.30` (Yandex Cloud, Москва), домен `tbot.rusiksoft.ru` | интеграционная среда, приёмка, учения, демо, круглосуточная торговля | `sandbox` + `paper` + `production` (разрешение заказчика от 2026-11-20, `docs/adr/ADR-001`) |
| CI-стенд (одноразовый) | GitHub Actions, job `dev-стенд: сборка, готовность, изоляция базы` | автоматическая приёмка полного состава на чистом раннере | mock + песочница (боевого ключа в CI нет) |
| backup/restore stand | второй VPS или объектное хранилище + временный контейнер | восстановление из дампов, `restore-verify` | — |

Отдельной тестовой ВМ в проекте **нет**: раньше в этой таблице значился домашний сервер
`192.168.1.40`, по факту такой машины нет, и все ручные проверки делаются на рабочей ВМ.
Единственный воспроизводимый «нулевой» контур — CI job `compose-smoke` (`docs/acceptance/m0-stand.md`).
Последствия совмещения приёмки и боевого контура на одной машине — `docs/adr/ADR-001`.

Состав прод-сервера: `caddy` (443) → `web`; отдельно `engine`, `tgbot`, `jobs`, `postgres`;
все — docker compose v2, образы из GHCR по digest.

## 14.2 Требования к рабочей ВМ (приёмка и эксплуатация)

Замеры рабочей ВМ (2026-11-20, `docs/acceptance/prod-bootstrap.md §1`): Ubuntu 24.04.5 LTS,
x86_64, 2 vCPU, RAM 3.8 ГБ, диск 72 ГБ (свободно 65 ГБ), swap 4 ГБ и `vm.swappiness=10`
(выполнено 2026-11-20), `chrony` (смещение 0.001 с), Docker не установлен.
Подтверждать значения при подключении: `nproc`, `free -h`, `df -h /` — или целиком,
`python3 scripts/prod_bootstrap_check.py`.

Вывод: **для M0–M4 годится, для бэктестов и долгого хранения истории — впритык** (2 vCPU и
3.8 ГБ RAM). Обязательные ограничения (иначе упрёмся в 3.8 ГБ RAM и OOM-killer):

- PostgreSQL: `shared_buffers=256MB`, `effective_cache_size=768MB`, `work_mem=4MB`,
  `maintenance_work_mem=128MB`, `max_connections=60`; `wal_buffers` — авто (≈1/32
  `shared_buffers`). Фактические значения — `deploy/postgres/tbot.conf`, проверка —
  `make deploy-check`. Поднимать `shared_buffers` до 512 МБ (потолок по OQ-11) разрешено
  только по замерам RSS и попаданий в кэш, не «про запас».
- Swap 4 ГБ (файл) + `vm.swappiness=10` — **выполнено 2026-11-20**; проверяется тремя условиями:
  включён, объём достаточен, есть запись в `/etc/fstab` (без неё своп исчезает после
  перезагрузки, а тяжёлый процесс снова упирается в OOM-killer).
- Ретенция на этой машине: свечи 1 мин — **12 месяцев** + Parquet-архив (§14.9, OQ-11; целевые
  24 месяца из §4.12 на ней допустимы только с архивом), стакан — 30 дней и «сырые» снимки
  портфеля — 13 месяцев (§4.12). Прежние «3 месяца / 7 дней» были следствием 13 ГБ свободного
  места на несуществующем стенде, а не выбором политики. Локальные дампы — вне раздела с БД.
- Загрузчик истории: бюджет 120 запросов/мин и не более 5 инструментов; на рабочей ВМ — только
  по необходимости и окном вне торгов (совмещение с боевым контуром, ADR-001).
- Оптимизатор бэктеста: максимум 1 воркер, сетка ≤ 50 точек, `1MIN` интервал только для
  последних 6 месяцев, основной интервал для исследований — `5MIN/15MIN/HOUR`; тяжёлые
  оптимизации и walk-forward — на dev-машине.
- Контроль диска: алерт при >75% и >85% (уже в §12.4), `make vacuum-parts` (очистка партиций),
  `docker system prune` по расписанию. При нехватке места — отказ от лишних прогонов, а не от
  риск-лимитов.
- Учения, демо и массовые прогоны планируются окном вне торгов: приёмка и торговля идут на одной
  машине (§14.1, `docs/adr/ADR-001`).
- Порядок проверки машины: сначала `scripts/prod_bootstrap_check.py` (своп, время, доверие НУЦ,
  доступность контуров, ресурсы), затем `make deploy-check`.

## 14.3 Расчёт ресурсов под целевой масштаб (3 пользователя, ≤15 стратегий, ≤100 подписок)

**Данные** (детали и оценка объёмов — §4.12): 24 месяца хранения дают ~6–8 ГБ таблиц +
индексы; WAL при штатной работе 1–3 ГБ/мес, при массовой закачке истории — до 15–20 ГБ
(пачечная вставка `COPY`, отсюда меньший WAL). Итого рабочий диск: 25–35 ГБ за 2 года плюс
дампы (1,5×) и место под обновления образов.

**Память**: PostgreSQL (`shared_buffers` 1–1.5 ГБ + кэш страниц ОС ещё ~2 ГБ полезно) +
`engine` ~0.6–1.0 ГБ (100 подписок, 15 стратегий, буферы свечей) + `web` ~0.3–0.4 ГБ +
`tgbot` ~0.2 ГБ + `jobs`/бэктест-воркер 1.5–2.5 ГБ в пике + ОС ~0.3 ГБ ⇒
**8 ГБ** с запасом, **4 ГБ** — впритык (тогда один бэктест-воркер и `shared_buffers` 512 МБ).

**CPU**: торговое ядро однопоточное по сути (asyncio) — 1 ядро с запасом; индикаторы и
сверка дают всплески; оптимизатор — N воркеров. ⇒ **4 vCPU** для прод-сервера с бэктестами,
**2 vCPU** если исследования вынесены на другую машину.

**Диск**: обязательно NVMe/SSD (мелкие случайные чтения при расчёте индикаторов и выборках
свечей); HDD не допускается.

**Сеть**: достаточно 100–200 Мбит/с; трафик с брокером — десятки МБ/сут на 100 подписок
(стрим свечей 1 мин + периодические запросы). Критична **задержка**, а не ширина канала.

## 14.4 Конфигурации серверов

| Конфигурация | Ресурсы | Для чего | Ограничения |
|---|---|---|---|
| **минимальная** | 2 vCPU, 4 ГБ RAM, 60 ГБ NVMe, 1 IPv4, Ubuntu 24.04 | 1 пользователь, ≤5 стратегий, ≤30 подписок, бэктест редко | 1 бэктест-воркер; ретенция 1 мин — 12 мес.; без оптимизатора |
| **рекомендуемая (целевая)** | **4 vCPU, 8 ГБ RAM, 100 ГБ NVMe**, 1 IPv4, Ubuntu 24.04, Moscow DC | целевой масштаб (3 пользователя, ≤15 стратегий, ≤100 подписок), регулярные бэктесы, хранение 24 мес. | — |
| **расширенная** | 8 vCPU, 16 ГБ RAM, 200 ГБ NVMe + отдельный Postgres (или managed) + объектное хранилище | запас ×2 (30 стратегий, 200 подписок), несколько бэктест-воркеров, второй узел для «холодного» резерва | дороже; нужна реплика/отказоустойчивость |

Плюс к любой конфигурации:
- **бэкап-хранилище**: объект-хранилище в РФ или второй сервер, объём 1,5–2× БД (60–150 ГБ),
  шифрование до выгрузки, WORM/версионирование по возможности;
- **второй (дежурный) узел** — опционально для M7: холодный резерв с восстановленным дампом
  (RTO ≤2 ч обеспечивается и без него, поэтому не является обязательным);
- **мониторинг**: Prometheus + alertmanager внутри той же compose-сети (≈0.3 ГБ RAM) либо
  внешний статус-монитор; обязателен «canary»-проверка, что дайджест и алерты доходят.

## 14.5 Требования к размещению и провайдеру

1. **Юрисдикция и сеть**: сервер в РФ, московская площадка (минимальный RTT до инфраструктуры
   брокера/биржи), статический IPv4. Причины выбирать РФ: работа с сертификатом НУЦ Минцифры,
   предсказуемая доступность API брокера из российских сетей, требования к персональным данным
   (размещение/защита ПДн граждан РФ), а также то, что доступ к API из-за рубежа может быть
   нестабильным (проверить на этапе M1 тестом conformance: коннект с целевой точки).
2. **Архитектура x86_64** (не ARM): официальные колёса `grpcio`/`protobuf` и воспроизводимость
   сборок на всех машинах.
3. **Образ**: Ubuntu Server 24.04 LTS, только нужные пакеты; без панели провайдера;
   SSH-ключи, UFW default-deny, fail2ban, chrony (обязателен: TOTP и временные метки сделок),
   AppArmor в enforce, автоматические обновления безопасности (`unattended-upgrades`) с
   окном вне торгов и последующей проверкой `healthz`.
4. **Исходящий доступ** — только разрешённые адреса (§8.5); входящий — 443 и 22 (SSH — по
   возможности только из allowlist/VPN).
5 **Домен**: отдельный поддомен (не связанный с публичным сайтом), DNS в РФ/нейтральный,
   DNSSEC по возможности, Let's Encrypt с автопродлением; в UI и письмах — только HTTPS.
6. **Что не нужно**: публичный вход для Telegram (long polling), 80/25/110 порты, IPv6
   (полезен, но не обязателен), панель управления провайдера, «облачные» БД-сервисы с
   публичными эндпоинтами.

## 14.6 Состав и параметры контейнеров (прод)

```
caddy        restart always; limits 128M CPU 0.25; volumes: certs, Caddyfile
web          2 реплики максимум (иначе дубли сессий не нужны); limits mem 512M, cpus 1.0
engine       1 экземпляр; mem limit 1.5G, cpus 2.0; healthcheck /readyz; stop_grace_period 60s
tgbot        mem 256M, cpus 0.25
jobs         mem 3G (бэктест-воркер), cpus 3.0; заводится по задаче, не постоянно
postgres     mem 3G (shared_buffers 1G), cpus 2.0, shm_size 512M; volume на NVMe;
             pgbouncer опционален при >100 соединений
prometheus+alertmanager  mem 512M
```

Требования к запуску: не-root в контейнерах, `read_only` где возможно, tmpfs для секретов,
`no-new-privileges`, отдельные сети (`db` без egress, `app`, `edge`), healthcheck-зависимости,
`docker system prune` по расписанию, ротация логов (50 МБ × 10).

## 14.7 Порядок внедрения (M0 → M7) на серверах

1. **рабочая ВМ**: базовая подготовка (`scripts/prod_bootstrap_check.py` — своп, `chrony`,
   корень НУЦ, доступность контуров) → `git clone` → Docker Engine + compose из репозитариев
   дистрибутива → образы по digest → миграции → `seed-dev` → проверка `deploy-check` →
   подключение песочницы → учения §13.5. Тот же состав поднимается в CI (job `compose-smoke`)
   на чистом раннере — это воспроизводимая половина приёмки.
2. **prod-сервер**: базовая настройка (UFW/SSH/chrony/обновления) → установка Docker Engine +
   compose (пакеты из репозитория distro, не «get.docker.com»-скрипт) → pull образов по digest
   → KEK-файл (0400) → миграции → `deploy-check` → включение `engine` с `paper`
   → после приёмки — включение боевого контура на 1 инструменте с лимитами «минимум»
   (1 стратегия, 1 уровень, капитал 2%).
3. **Мониторинг и бэкапы** включаются **до** первого боевого запуска (иначе запуск не
   считается принятым).

## 14.8 Оценки «что почём» (без цен, только состав затрат)

Статья затрат на прод: VPS (рекомендуемая конфигурация) + бэкап-хранилище + домен +
(опционально) второй узел и внешний мониторинг. При отказе от бэктестов на проде
рекомендуемую конфигурацию можно понизить до минимальной и держать исследования на
рабочей машине — это единственный заметный источник экономии, который не влияет на
безопасность торговли.

## 14.9 Фактическая прод-площадка (зафиксирована 2026-11-19; замеры — `docs/research/03`)

**Что есть:** ВМ Yandex Cloud `compute-vm-2-4-74-ssd-…`, публичный `153.51.172.30`
(Москва, AS200350), приватный `10.130.0.21/24`; конфигурация **2 vCPU / 3.8 GiB / 72 ГБ SSD**
(занято 2.1 ГБ до подготовки и 6.3 ГБ после свопа, занято 9%); Ubuntu 24.04.5 LTS, x86_64,
ядро 6.8.0-149; `rusiksoft` с `sudo` без пароля; SSH по ключу; Docker не установлен; `chrony`
и корень НУЦ установлены, `swap` 4 ГиБ (2026-11-20, `docs/acceptance/prod-bootstrap.md`);
`ufw` выключен; слушаются 22 и `127.0.0.1:10800` (SOCKS туннеля Telegram); домен
`tbot.rusiksoft.ru` уже указывает на ВМ.

**Conformance-результат (важно):**
- T‑Invest API (бой и песочница) **доступны**: HTTP 401 на неавторизованные вызовы, HTTP/2 на
  443 работает; задержки REST **p50 29 мс / p95 54 мс / max 93 мс** (песочница p50 42 мс) —
  целевые метрики TZ §7.7 достигаются с запасом.
- TLS-цепочка брокера: `*.tbank.ru` ← `Russian Trusted Sub CA` ← `Russian Trusted Root CA`
  (Минцифры), срок до 2027-08-24. Стандартное хранилище Ubuntu корня **не содержало** →
  `Verify return code: 19`. Условие `REQ-broker-gateway-02` выполняется только после
  установки корневого сертификата (задача **T-709**): на хосте —
  `/usr/local/share/ca-certificates/ru-trusted-root-ca.crt` + `update-ca-certificates`, в образе —
  свой корневой сертификат и поддержка `SSL_TBANK_VERIFY=True`; CI обязан валиться, если доверия нет.
  **Выполнено 2026-11-20:** на хосте корень установлен, `curl` **без `-k`** на обеих точках
  (бой и песочница) отвечает `401 Authentication token is missing or invalid` при
  `Verify return code: 0`; в образе — с 2026-11-20 (CI job `broker-tls`, шаг `compose-smoke`).
  Протоколы: `docs/acceptance/prod-bootstrap.md §2`, `docs/acceptance/broker-tls.md`.
- **Telegram**: `api.telegram.org` (и `api1/api2/api4`, часть DC-IP) с ВМ **недоступны**,
  один DC-IP (`149.154.167.220:443`) доступен, внешнего IPv6 нет. Это блокирует требование
  TZ §10 до выбора схемы (см. OQ-12, варианты A/B/C/D в `docs/research/03 §3.4`).
- **Входящие 80/443** с внешней стороны не подключаются при отсутствии локальных фильтров —
  причина в группе безопасности Yandex Cloud; без её правки Caddy не получит сертификат
  (задача **T-708**, OQ-13). Проверено повторно 2026-11-20: снаружи `22` OPEN,
  `80/443/5432/8080/9101` — closed/filtered.

**Разница с целевой конфигурацией (TZ §14.4):** текущая ВМ = «минимальная»
(2 vCPU / 4 ГБ / 60–74 ГБ) при целевом масштабе 3 юзера / 15 стратегий / 100 подписок.
**Решение заказчика (OQ-11, 2026-11-19): конфигурацию пока не расширяем.** Значит ограничения
фиксируются как часть проекта, а не как временные:
- `swap` 4 ГБ + `vm.swappiness=10` — обязателен (swap отсутствовал, первый же тяжёлый процесс
  приводил к OOM) — задача **T-011**; **выполнено 2026-11-20**: `/swapfile` 4 ГиБ, запись
  `/swapfile none swap sw,pri=1 0 0` в `/etc/fstab`, `vm.swappiness=10` через
  `/etc/sysctl.d/99-tbot.conf`; проверка — `scripts/prod_bootstrap_check.py`;
- Postgres: `shared_buffers ≤ 512 МБ`, `effective_cache_size ≈ 1 ГБ`, `work_mem` малый,
  `max_connections ≤ 60`; отдельный `tbot`-role c `statement_timeout`;
- на проде — **один** бэктест-воркер, тяжёлые оптимизации и walk-forward — на dev-машине,
  загрузка истории на прод — только по необходимости (не более 24 мес. по списку инструментов);
- ретенция минутных свечей — **12 месяцев**, далее Parquet-архив в объектное хранилище
  (TZ §4.2); дневные — 5 лет;
- локальные дампы не хранить на разделе с БД; бэкапы — отдельный диск/объектное хранилище
  (OQ-10), шифрование до выгрузки;
- алерты диска (80/90%) и RSS процессов — обязательны (TZ §12.4), при росте очереди бэктестов
  — отказ от лишних запусков, а не от лимитов риска.

**Второй узел (схема B, OQ-12):** ВПС `rusiksoft.ru` (`176.32.39.234`, Ubuntu 24.04, хост
проекта `.Di`) — размещает только контейнер `tgbot` (без токенов брокера и доступа к БД).
Замеры связности: прод → узел B: 80/443 OK (ttfb ≈ 21 мс), **22 и типовой UDP WG — недоступны**
(фильтр узла B по источнику); значит управление узлом B ведётся с разрешённого источника
(домашняя сеть/VPN), а рабочий канал B ↔ прод строится поверх **TCP/443 с mTLS** после
открытия 443 на проде (OQ-13). Детали — `docs/tz/10 §10.7`, `docs/tz/08 §8.5.1`.

**Управление облаком (OQ-13):** канал управления — Yandex Cloud CLI
(`yc compute ssh --id fv48ibn5ff3ff5gd0e3v --identity-file <ключ>`). **CLI установлен
2026-11-19:** версия 1.47.0, пользовательская установка `~\yandex-cloud\bin\yc.exe`
(официальный скрипт ставит туда же; бинарник загружен напрямую из
`storage.yandexcloud.net/yandexcloud-yc/release/1.47.0/windows/amd64/yc.exe`), путь добавлен
в PATH пользователя. Не хватает одного шага: интерактивной авторизации `yc init` (OAuth в
браузере, выполняется владельцем аккаунта; без неё CLI отвечает
`failed to get credentials`). После авторизации применяется план из
`docs/runbook/yandex-sg.md`: дамп текущих правил → новая SG (22 из allowlist + 80/443) →
привязка к интерфейсу **без открепления существующей** → проверка снаружи → `ufw`/`fail2ban`.

**Что ещё требуется на площадке (порядок):** группы безопасности (80/443 из allowlist-подсетей
либо публично + прикладной allowlist) → `ufw default deny incoming` + `fail2ban` → ~~`chrony`~~
**(готово 2026-11-20: `chrony` 4.5-1ubuntu4.2 из репозитария Ubuntu, смещение 0.001 с, юнит
включён)** → ~~корневой сертификат НУЦ~~ **(готово 2026-11-20, см. выше)** → Docker Engine
из репозитариев дистрибутива + pull образов GHCR по digest → Caddy + сертификат на
`tbot.rusiksoft.ru` → мониторинг/бэкапы → только затем включение `engine` в `paper`,
затем боевого контура. Ключ SSH из каталога проекта **не должен** попадать в git
(`.gitignore` исключает `ssh-key/`; рабочая копия — `~/.ssh/tbot/`).
