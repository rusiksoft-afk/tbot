# 15. Границы разработки, правовая рамка, дисклеймеры

## 15.1 Правило «Always / Ask first / Never» (обязательно для исполнителя)

**Всегда делать (без согласования):**
- писать тесты вместе с кодом (не после), прогон `make lint && make test` перед каждым коммитом;
- на каждое изменение схемы — миграцию Alembic с `downgrade`;
- фиксировать любое архитектурное решение в `docs/adr/NNNN-*.md` (контекст → решение →
  последствия → ссылки на требования);
- логировать структурно, с маскированием секретов; любые новые поля в логах — через общий
  форматтер;
- сверять имена полей и enum-ы с актуальной версией контракта брокера перед использованием
  (обновление `docs/research/01-*.md` + секции `docs/tz/03`);
- вести `docs/changelog/` по вехам; обновлять `docs/acceptance/` после учений;
- держать `mypy --strict` и линтеры зелёными; удалять мёртвый код.

**Сначала согласовать (стоп-точка):**
- новая зависимость (кроме тестовых утилит из уже утверждённого списка) — с обоснованием и
  проверкой лицензии;
- изменение состав/семантика таблиц БД, не покрытое миграцией «расширения»;
- изменение риск-лимитов по умолчанию (§6.5) или потолков (уровни сетки, множитель);
- новый метод T‑Invest API в `broker_gateway` (в т.ч. «почитать полезное») — с оценкой лимитов;
- изменение CI/CD, состава образов, сетевых политик, портов, TLS;
- любое действие на прод-сервере (включая просмотр логов боевого контура) и **любой вызов
  боевого контура брокера** из кода/тестов/скриптов;
- изменение перечня разрешённых исходящих адресов;
- изменение политики ретенции данных и процедуры бэкапа;
- изменение перечня ролей и прав;
- исключение/ослабление любой проверки риск-гейта или любого из «красных» тестов §13.3.

**Никогда:**
- коммитить токены, ключи, пароли, ПДн, реальные номера счетов, дампы (в git, в CI-артефакты,
  в issue, в описания PR);
- хранить токен брокера в открытом виде (БД, YAML, переменные в compose, имя контейнера,
  аргументы командной строки, метки метрик, имена файлов);
- отключать проверку TLS (`InsecureChannelCredentials`, `verify=False`, `SSL_CERT_INSECURE`);
- вызывать `post_order`/`cancel_order`/`post_stop_order` вне `order-executor`
  (в частности из стратегий, веб-слоя, Telegram-слоя, скриптов);
- повторять мутацию после таймаута без сверки по клиентскому ключу (§7.4);
- использовать `float` для денег/цен, `datetime.now()` без часового пояса, «магические»
  коэффициенты в коде без комментария и теста;
- вызывать методы переводов/вывода средств (`CurrencyTransfer`, `PayIn` вне песочницы, операции
  с банковскими счетами) — в проекте их нет и быть не может;
- включать боевой контур изменением кода или «временным флагом» (только конфигурация +
  подтверждение 2FA + запись в аудит);
- правки сгенерированных gRPC-стабов и файлов, поставляемых SDK;
- обход/отключение egress-политики, IP-allowlist, rate limit, обязательности 2FA;
- «исправление» падающего теста через его удаление, `skip`, `xfail` или понижение порога
  покрытия без явного одобрения в PR;
- упоминание сторонних облачных торговых ботов-референсов (название, домен, «как у …»)
  в коде, комментариях, README, ADR, названиях веток, описаниях коммитов, именах тестов.
  Функциональные требования уже пересказаны своими словами в этом ТЗ — новых ссылок не нужно.

## 15.2 Ответственность и ограничения продукта (что обязано быть в UI и документации)

1. **Это инструмент автоматизации, не инвестиционная рекомендация.** Ни один сигнал, отчёт,
   сообщение в Telegram или элемент интерфейса не содержит рекомендации купить/продать
   конкретный инструмент конкретному лицу. Строка в подвале консоли и в первом запуске
   стратегии: «Решения принимаются автоматически по заданным правилам; система не является
   индивидуальной инвестиционной рекомендацией и не гарантирует доходность».
2. **Риск убытка.** При первом включении боевого контура пользователь подтверждает
   осознание рисков текстом (фиксация в `audit_log`); в карточке стратегии всегда видны
   максимальный возможный убыток по текущим настройкам (сумма и % капитала).
3. **Стратегии с усреднением имеют неограниченный хвост риска при непрерывном движении
   против позиции.** Поэтому в продукте жёстко ограничены уровни и множитель, обязан быть
   `max_drawdown_pct` и обязателен дневной лимит убытка (отключить `max_drawdown_pct` в
   `production` нельзя; в `paper` — можно с предупреждением).
4. **Полномочия токена.** Пользователь подтверждает, что действует от своего имени по своему
   брокерскому счёту, не передавал и не передаёт токен третьим лицам, и согласен, что система
   выполняет торговые операции автоматически. Система со своей стороны не запрашивает и не
   принимает токены с правом перевода (см. `REQ-credentials-04`) и хранит их в зашифрованном
   виде.
5. **Ограничения брокера, которые надо помнить** (уже отражены в требованиях): срок жизни
   токена 3 месяца; сделки свыше 30 млн ₽ через API недоступны; часть типов счетов не
   поддерживает торговлю через API; комиссии API не отдаёт (значения задаёт оператор);
   исполнение лимитных заявок и доступность инструментов могут меняться из-за биржевых
   ограничений, торговые статусы и расписания меняются — поэтому календарь только из API.
6. **Налоги.** Брокер выступает налоговым агентом по счетам физических лиц в РФ; система
   считает свою оценку P&L и комиссий, но не формирует налоговую декларацию. Отчёты помечены
   как «расчёт системы», сверка с брокерским отчётом — отдельная процедура
   (`docs/runbook/accounting-review.md`).

## 15.3 Персональные данные

- Состав хранимых ПДн минимален: логин, отображаемое имя, e-mail (опционально), хэш пароля,
  зашифрованный TOTP-секрет, хэши резервных кодов, Telegram `chat_id`/имя чата, IP и
  user-agent вестей аудита, параметры сессий. Номера счетов — технические идентификаторы,
  их тоже следует показывать замаскированно.
- Правовая рамка: обработка ПДн пользователей из РФ предполагает хранение и обработку на
  территории РФ (требование локализации баз ПДн) — поэтому прод-сервер размещается в РФ
  (§14.5). Нужны: текст согласия на обработку ПДн (показывать при создании аккаунта,
  хранить факт согласия с датой и версией текста), политика обработки, срок хранения
  (аудит — 5 лет, логи — 90 дней, рыночные данные — по ретенции §4.12), порядок удаления
  учётной записи (анонимизация: удаляем e-mail/имя, остаётся технический хэш и торговая
  история, если она требуется для отчётности), порядок уведомления пользователя при
  инциденте безопасности.
- Ответственного за организацию обработки ПДн и формулировки документов назначает владелец
  проекта (это юридическое решение, не техническое); техническая часть — перечисленные выше
  механизмы, шифрование, аудит, минимизация, отсутствие передачи третьим лицам.
- Если проект остаётся закрытым клубом без вознаграждения, это не создание финансовой
  организации и не приём денег: платёжные модули, оферты, кассы — вне объёма. Любая
  монетизация доступа требует отдельного юридического разбора **до** появления платёжной
  функциональности.

## 15.4 Требования безопасности к поставке кода

- Все репозитории приватные; доступ — только необходимые сотрудники; включена 2FA на GitHub
  (требование к аккаунтам, у которых есть доступ), токены GitHub с минимальными scope,
  срок жизни CI-токена — только на время сборки.
- В CI обязательны: `gitleaks` (проверка истории и diff), `pip-audit` (уязвимости
  зависимостей), `bandit` (статический анализ), сканирование образов (Trivy/Grype),
  подпись образов (cosign, опционально на M7), проверка лицензий зависимостей
  (Apache/BSD/MIT допустимы, GPL-совместимость проверяется).
- Зависимости пинятся с хешами; обновления — отдельными PR с заметкой в `docs/changelog/`;
  обновление `t-tech-investments` требует прогона contract-тестов и учения в песочнице.
- Запрещено: лок-файлы без хешей, установка из git-репозиториев в рантайме,
  самообновление кода на проде, динамическая загрузка кода из интернета.
- Артефакты CI (дампы, Coverage, скриншоты e2e) — без реальных данных: фикстуры с
  синтетическими значениями, «канареечные» токены в тестах, имена инструментов из тестового
  набора (например `TESTAAA`, `TESTBBB`), а не реальные тикеры в тестовых данных
  (реальные тикеры допустимы только в бенчмарках/бэктестах на стенде).

## 15.5 Критерии эскалации инцидента (operational)

| Уровень | Примеры | Действия |
|---|---|---|
| **S1** | подтверждённая компрометация токена/хоста; подозрительные сделки; несанкционированный вход; раскрытие ПДн | немедленный отзыв токена у брокера, отзыв всех сессий, kill-switch, остановка `web` (сохраняя логи), разбор по `runbook/compromised-token.md`, смена всех секретов, проверка цепочки аудита, при необходимости — уведомление пользователя и оператора брокера |
| **S2** | заявка в `unknown` >30 мин; расхождение позиций; потеря части истории; отказ БД | остановка затронутых стратегий, сверка, отчёт в `docs/incidents/` |
| **S3** | деградация задержек, лаг данных, 429, падение задания | автоматические алерты, плановый разбор |

Любой S1/S2 обязан приводить к записи в `docs/incidents/` (хронология, влияние, корень,
меры) и к задаче на устранение корня — без записи инцидент не считается закрытым.
