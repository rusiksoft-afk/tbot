# 08. Безопасность, аутентификация, 2FA, периметр

Модель угрозы (коротко, чтобы объём работ был обоснован): главный актив — **токен T‑Invest**
(даёт торговлю деньгами владельца счёта) и **доступ к веб-панели** (позволяет этим токеном
воспользоваться). Основные векторы: подбор пароля/перебор кодов 2FA, кража сессии (XSS,
MITM, закладку в браузере), компрометация хоста, утечка токена через логи/бэкапы/ошибки,
злоупотребление доверием Telegram-чата. Двухфакторная аутентификация (TOTP) и ограничение
периметра снижают
первые две; шифрование и аудит — остальные.

## 8.1 Пароли

- Хэширование: Argon2id (m=64 MiB, t=3, p=4), длина пароля ≥12 символов, проверка по
  списку типовых слабых паролей + против «пароль = логин/домен».
- Смена пароля — только с текущим паролем **и** TOTP; после смены все сессии, кроме текущей,
  отзываются; уведомление в Telegram.
- Восстановление: по почте (если задана) с одноразовой ссылкой 15 минут + обязательная
  повторная привязка TOTP; либо сброс администратором с записью в `audit_log` и уведомлением
  пользователю. Без второго фактора восстановления «по почте» сброс администратора требует
  TOTP администратора.

## 8.2 2FA TOTP (Google Authenticator и совместимые)

- RFC 6238, SHA-1, 6 цифр, шаг 30 с; допуск ±1 шаг (по умолчанию ±1, максимум ±2).
- Обязателен **для всех** пользователей и **для всех** входов (политика `mfa_required=true`,
  отключить нельзя). Реализация своя (библиотека `pyotp` допустима как зависимость с
  зафиксированной версией; собственная реализация предпочтительнее для аудита — решение через ADR).
- Сценарий входа: (1) логин+пароль → создаётся сессия в состоянии `auth_step='password'` с
  доступом только к странице ввода кода и к `/logout`; (2) ввод TOTP → `auth_step='full'`.
  Любая попытка доступа к остальным маршрутам на шаге (1) → 302 на страницу кода.
- Привязка: QR + ручной ввод секрета; обязательная проверка (пользователь вводит 2
  последовательных кода), иначе учётная запись не активируется. Секрет хранится
  зашифрованным (AES-256-GCM, KEK вне БД), в UI больше не показывается.
- Резервные коды: 10 шт. по 10 символов (алфавит без похожих знаков), хранятся хэшами
  (SHA-256), одноразовые, показываются один раз при генерации; повторная генерация
  аннулирует прежние; расход кода = шаг полной аутентификации + обязательное предупреждение
  «нужно восстановить 2FA» + алерт администратору + требование сгенерировать новые в течение
  7 дней (иначе учётная запись блокируется на вход, не на торговлю).
- Защита перебора: 5 неудачных кодов подряд → блокировка входа пользователя на 15 минут +
  уведомление; 3 неудачные попытки с одного IP за 5 минут → временный бан IP (nginx/fail2ban).
  Коды принимаются один раз (защита от повторного использования окна), попытки фиксируются в
  `totp_failures`.
- Системное время: chrony обязателен; расхождение >2 с → `R32`, генерация/приём TOTP
  приостановлены (вход невозможен, но торговля продолжается, если процесс `engine` уже
  аутентифицирован; UI показывает баннер).

## 8.3 Сессии и веб-безопасность

- Куки: `HttpOnly`, `Secure`, `SameSite=Lax`, путь `/`, случайный id 256 бит; idle-таймаут
  30 минут, абсолютный — 12 часов; после критичных действий (смена пароля, подключение токена,
  запуск в `production`) сессия пересоздаётся.
- CSRF: токен сессии во всех mutation-запросах (в т.ч. HTMX: заголовок `X-CSRF-Token`),
  проверка origin; `SameSite=Lax` как второй слой.
- CSP: `default-src 'self'; script-src 'self'; style-src 'self'; connect-src 'self';
  frame-ancestors 'none'; base-uri 'self'; form-action 'self'`. Внешние CDN запрещены
  (шрифты и JS — самохостящиеся). `Referrer-Policy: same-origin`, `X-Content-Type-Options:
  nosniff`, `Permissions-Policy` минимум, HSTS `max-age=63072000; includeSubDomains`.
- Вывод в HTML — автоэкранирование Jinja2 (autoescape=true везде), никакого `|safe` для
  пользовательских строк; числа формуются фильтрами, а не конкатенацией.
- Rate limit: `/login` — 10 запросов/мин/IP, `/totp` — 10/мин/сессия и 5/мин/IP, все
  mutation-эндпоинты — 60/мин/пользователь. Счётчик обязателен на уровне приложения (`T-102`, веха
  M1): веб-сервером выбран Caddy, а у официального образа встроенного ограничения частоты запросов
  нет, и образом с плагином мы не собираемся (иначе теряется публичный digest —
  `docs/runbook/ghcr-pull.md §1`). Формулировка «nginx `limit_req`» заменена решением заказчика от
  2026-11-20 (`docs/adr/ADR-003`); вместо неё обратный прокси обязан держать пределы размера и
  тайм-аутов запроса: `max_header_size`, `read_header`, `request_body max_size` и отказ от
  разведочных методов (`TRACE`). Прикладной счётчик от этого не отменяется: адрес клиента он обязан
  брать из `X-Forwarded-For`, проставленного прокси (наружу `web` не публикуется).
- Сессии видны пользователю (список устройств, отзыв по одной/всех), отзыв отражается
  немедленно (проверка `sessions.revoked_at` на каждом запросе).
- Файлы отчётов: выдаются одноразовой ссылкой (TTL 5 минут), имена — UUID, скачивание
  только владельцем, в CSV/PDF нет ПДн других пользователей и нет токенов/ключей.

## 8.4 Шифрование токенов и ключей

- Схема: DEK на запись (`credentials.token_cipher`, `totp_enrollments.secret_enc`) → AES-256-GCM
  с AAD (`credential_id` + `owner_id` + `kind`), DEK обёрнут в KEK; KEK в файле
  `/etc/tbot/keys/kek.json` (права 0400, владелец — пользователь сервиса) или в внешнем
  хранилище секретов; KEK не хранится в БД и не кладётся в образ.
- Ротация KEK: команда `make rotate-keys` — расшифровка/перезапись с новым `key_version`,
  обязательный бэкап перед операцией, идемпотентность, журнал.
- Проверка токена: read-only вызовы (`GetAccounts`, `GetInfo`/`GetUserTariff`) с последующим
  выводом состояния; признаки «токен даёт переводы» → отказ (`REQ-credentials-04`).
- Красное правило: токен не появляется в `repr()`, в логах (фильтр structlog маскирует поля
  `token`, `authorization`, `secret*`, значения по шаблону `t.[A-Za-z0-9.-]{16,}`), в
  исключениях, в трейсбеках Sentry-подобных отчётах, в метриках, в названиях процессов,
  в `ps aux` (не передаётся аргументом командной строки — только ENV/файл).
- Бэкапы: `pg_dump` шифруется (age/gpg) до выгрузки в хранилище; доступ к хранилищу —
  отдельный ключ с правом записи (object lock/WORM, если провайдер поддерживает).

## 8.5 Периметр и сетевая модель

- Вход наружу: только 443/tcp и 443/udp (Caddy: HTTPS и HTTP/3 — udp открыт решением заказчика от
  2026-11-20, `docs/adr/ADR-003`), 80/tcp (редирект на HTTPS и вызовы ACME HTTP-01) и 22 (SSH,
  ключевой доступ, `PermitRootLogin no`, `PasswordAuthentication no`). Всё остальное — closed
  (UFW default deny incoming).
- IP-allowlist: список CIDR в UI + nginx/Caddy `remote_ip` проверка; отдельный путь
  `/admin/security/allowlist`; emergency-переключатель «только VPN-подсеть».
- SSH: ключи, fail2ban (3 неудачи → 30 минут), опционально 2-й порт, аудит входа в
  `journal` + еженедельный отчёт администратору.
- Исходящие соединения (`engine`, `jobs`): `invest-public-api.tbank.ru`,
  `sandbox-invest-public-api.tbank.ru`, `api.telegram.org`, репозиторий образов (GHCR),
  NTP. У `tgbot` — только `api.telegram.org`. У БД — только из внутренних контейнеров.
  Реализуется egress-политикой (сетевой профиль compose + правило iptables/nftables по
  владельцу процесса), любые иные адреса → алерт `EGRESS_UNEXPECTED`.

### 8.5.1 Особенность прод-площадки: Telegram-egress (замерено 2026-11-19)

На прод-ВМ (Yandex Cloud, Москва) `api.telegram.org` и большинство DC-IP Telegram недоступны по
TCP/443, из 7 проверенных адресов жив один (`149.154.167.220:443`), внешнего IPv6 нет
(замеры — `docs/research/03 §3.4, §3.7`). **Базовый набор: A + C′; B — резерв** (уточнено
2026-11-19 после вопроса заказчика: контейнер на узле B не обязателен — `docs/research/03 §3.7.1`):
- **A (на проде):** `tgbot` ходит в Telegram по конфигурируемому пулу адресов (не только DNS),
  с health-check `getMe` и переключением на живой адрес. TLS не ослабляется: SNI и проверка
  цепочки обязательны, `verify=False`/самоподписанные цепочки запрещены, несовпадение имени в
  сертификате → переход к следующему адресу + алерт.
- **C′ (туннельный egress):** `tgbot` живёт на проде и идёт к Telegram через отдельный
  вход-прокси (SOCKS5/HTTP-CONNECT) на узле `rusiksoft.ru` (`176.32.39.234`): уникальная
  авторизация, вход доступен только с IP прода `153.51.172.30`, лимит соединений и квота
  объёма, исходящие только вовне. Строго **без перехвата TLS**: проверка цепочки и SNI
  обязательны, расхождение → разрыв, алерт `tg_tls_mismatch`, переход на A (`AC-telegram-07`).
  Через этот канал не проходят вызовы API брокера, ПДн и финансовая история — только обращения
  к Telegram API поверх сквозного TLS (факт фиксируется в TZ §15 как принятое решение).
- **B (резерв):** если `tgbot` всё же размещается на узле B — узел не хранит токенов брокера,
  KEK, сессий и не имеет доступа к БД; канал только HTTPS/443 с mTLS и IP-allowlist (SSH и
  типовой UDP WG с прод-ВМ к узлу B не проходят по замерам).
- Деградация предсказуема: при недоступности Telegram, прокси или узла B `engine` продолжает
  работать и держать лимиты, очередь уведомлений растёт на проде с лимитом, панель показывает
  состояние канала, критичные алерты S1/S2 дублируются вторым каналом (e-mail): при падении
  личной сервисной инфраструктуры узла B удалённое управление пропадает, и оператор обязан
  увидеть это немедленно (`tg_last_delivery_age_s`).
- Docker: образы из GHCR по digest (не по тегу `latest`), не-root пользователь в контейнере,
  `read_only` rootfs где возможно, `no-new-privileges`, drop capabilities, секреты через
  tmpfs-mount, отдельная сеть для БД без выхода в интернет.
- Обновления: только через CI (собранный образ + тесты), ручной запуск `make deploy`;
  на прод-сервере нет компиляторов и сборки (pull-only), чтобы снизить поверхность.

## 8.6 Разделение прав процессов (минимизация ущерба)

| Процесс | Что имеет | Чего не имеет |
|---|---|---|
| `web` | доступ к БД (роль с правами CRUD на таблицы пользователей/стратегий), KEK-доступ для шифрования токенов | торговые токены в открытом виде, сетевой доступ к брокеру |
| `engine` | доступ к БД, расшифровка токенов, gRPC к брокеру | доступ к файлам отзывов/отчётов, админские функции |
| `tgbot` | доступ к БД (уведомления/команды), токен Telegram-бота | доступ к брокеру, торговые токены (команды уходят в очередь `engine`) |
| `jobs` | доступ к БД (чтение рынка, запись истории), read-only токены брокера | торговые токены (кроме `SandboxPayIn` в песочнице) |

## 8.7 Аудит и обнаружение

`audit_log` (§4.1) обязателен для: вход/выход/неудачные попытки, привязка/отзыв 2FA,
расход резервного кода, создание/изменение/удаление пользователя и роли, подключение/ротация/
отзыв токена, изменение лимитов риска, старт/пауза/стоп стратегии, изменения kill-switch,
изменения IP-allowlist, экспорт отчётов, ручное редактирование в БД (через сервис), деплой.
Уведомления администратору в Telegram: вход нового пользователя (новый IP/устройство),
расход резервного кода, изменение лимитов риска, отзыв токена, включение kill-switch.
Ежедневная задача `integrity-check`: сверка цепочки хэшей аудита, проверка свободных мест,
проверка отсутствия секретов в артефактах (gitleaks по дампу логов за сутки).

## 8.8 Что обязано быть проверено тестами (краткая матрица)

| Проверка | Уровень |
|---|---|
| вход без TOTP невозможен ни для одного маршрута, кроме страницы кода | интеграционный |
| перебор 6-значных кодов заблокирован (5 попыток) | интеграционный |
| резервный код одноразовый | юнит + интеграционный |
| смена пароля отзывает сессии | интеграционный |
| CSRF обязателен для всех POST/PUT/DELETE (тест «без токена → 403») | интеграционный |
| XSS в полях (name, comment, reason) не исполняется | e2e (Playwright) |
| токен не встречается в дампе БД/логах (логирование сгенерированного «токена-канарейки») | интеграционный + `make secret-scan` |
| egress за пределы списка невозможен (тест на стенде с nftables-логов) | инфраструктурный |
| права БД не позволяют UPDATE/DELETE в `audit_log` | интеграционный |
| доступ `operator` к чужим данным → 403/404 без утечки | интеграционный |
