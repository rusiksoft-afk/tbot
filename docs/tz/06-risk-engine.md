# 06. Риск-контроль (`risk-gate`)

Принцип: стратегия формулирует намерение, **решение принимает риск-гейт**. Это единственный
модуль, который может разрешить мутацию. Его правила — детерминированный код с тестами,
а не конфигурируемый «на глаз» набор if в стратегии. Поток: `Intent` → проверки →
`Approved(decision_id, risk_snapshot)` / `Denied(code, reason, risk_snapshot)`; и то и другое
пишется в БД до обращения к брокеру (`REQ-arch-04`).

## 6.1 Классы проверок (обязательный минимум)

**A. Контекст и режим**
1. `R01 CONTOUR_REQUIRED` — контур стратегии явно задан и совпадает с контуром токена/счёта.
2. `R02 BOOT_INCOMPLETE` — boot sequence (`docs/tz/02 §2.5`) не завершён.
3. `R03 KILL_SWITCH_ENGAGED` — глобальный или пользовательский kill-switch включён.
4. `R04 STRATEGY_NOT_RUNNING` — состояние стратегии не `running`/`armed`.
5. `R05 STALE_DATA` — рыночные данные старше `max_price_age_ms` (или лакун в стриме) →
   торговля запрещена.
6. `R06 RECONCILE_DIRTY` — последняя сверка позиций/заявок не пройдена или есть
   `position_mismatches` по этому инструменту (изоляция).
7. `R07 QUARANTINED_INSTRUMENT` — инструмент в изоляции из-за неизвестной заявки/расхождения.

**B. Инструмент и биржа**
8. `R08 INSTRUMENT_NOT_ALLOWED` — инструмента нет в whitelist администратора.
9. `R09 INSTRUMENT_METADATA_MISSING` — нет `lot`/`min_price_increment`/валюты или метаданные
   старше 24 ч.
10. `R10 TRADING_STATUS_FORBIDDEN` — статус торгов не разрешает данный тип заявки.
11. `R11 OUTSIDE_SESSION` — вне торговой сессии/в клиринг/в `session_guard_min`.
12. `R12 PRICE_BAND` — цена вне допустимого диапазона (лимиты изменения цены, заданные
    биржей/конфигом; ±20% от последней цены как страховка).
13. `R13 SPREAD_TOO_WIDE` — спред/ликвидность хуже `max_spread_bps`.
14. `R14 TICK_SIZE_MISMATCH` — цена не кратна шагу после нормализации (баг — не ретраим).

**C. Объём и покрытие**
15. `R15 QUANTITY_NOT_LOT` — количество не кратно лотности или ≤0.
16. `R16 INSUFFICIENT_FUNDS` — покупка больше доступных средств (`GetMaxLots.buy_max_lots`,
    отдельно `buy_max_market_lots` для рыночных).
17. `R17 INSUFFICIENT_POSITION` — продажа больше позиции (при `allow_margin=false`).
18. `R18 MARGIN_NOT_ALLOWED` — сделка создаёт непокрытую позицию, а `allow_margin=false`.
19. `R19 MARGIN_UNSAFE` — маржинальная сделка приближает счёт к опасным порогам:
    `funds_sufficiency_level < margin_safety_min` (по умолчанию 1.35) либо
    `amount_of_missing_funds > 0`.
20. `R20 POSITION_LIMIT` — превышен лимит позиции по инструменту
    (`max_position_pct`, по умолчанию 5% капитала пользователя) или суммарный риск
    (`max_total_exposure_pct`, по умолчанию 30%).
21. `R21 MAX_ORDERS_PER_INSTRUMENT` — слишком много активных заявок по инструменту
    (по умолчанию 10).

**D. Убыток и темп**
22. `R22 DAILY_LOSS_LIMIT` — дневной убыток пользователя/стратегии достиг лимита
    (по умолчанию 3% от стартовой дневной эквити) → новые сигналы запрещены до следующего
    торгового дня (или ручной разблокировки с TOTP).
23. `R23 MAX_DRAWDOWN_STRATEGY` — просадка стратегии к вложенному капиталу ≥ `max_drawdown_pct`.
24. `R24 SLIPPAGE_GUARD` — ожидаемое проскальзывание (по стакану/последней цене) больше
    `max_slippage_bps` для рыночной заявки.
25. `R25 ORDER_RATE_LIMIT` — превышен темп заявок стратегии или общий бюджет API
    (см. `docs/tz/03 §3.2`), в том числе защита от «цикла самоподдержки» (стратегия шлёт
    заявки чаще `max_orders_per_min`).
26. `R26 DUPLICATE_INTENT` — повторяющееся намерение (тот же инструмент/сторона/объём/цена)
    в окне `dedup_window_s` (по умолчанию 5 с).
27. `R27 UNKNOWN_INFLIGHT` — по инструменту есть заявка в состоянии `unknown`.

**E. Целостность и безопасность**
28. `R28 INTENT_SCHEMA_INVALID` — намерение не прошло схему/типы (в т.ч. `Decimal`).
29. `R29 PARAMS_HASH_MISMATCH` — параметры стратегии изменились «в обход» UI (см. `REQ-strategy-engine-01`).
30. `R30 RISK_CONFIG_OUT_OF_RANGE` — значения лимитов вне разрешённого диапазона
    (`REQ-config-01`).
31. `R31 TOKEN_INVALID_OR_EXPIRED` — токен недействителен/истёк (по ответу брокера или по
    сроку).
32. `R32 CLOCK_SKEW` — расхождение часов > 2 с (критично и для TOTP).
33. `R33 DB_UNHEALTHY` — БД недоступна/в режиме только для чтения → мутации запрещены.
34. `R34 DISK_FULL` — свободное место на диске БД < 10% → только чтение.
35. `R35 MANUAL_HOLD` — оператор поставил ручной «стоп торговли по счёту» из UI/Telegram.

## 6.2 Приоритет и журналирование

Проверки выполняются в порядке A→E, первое неудовлетворённое условие даёт `Denied(code)`.
Каждое решение содержит `risk_snapshot`: значения всех проверявшихся метрик на момент решения
(эквити, дневной P&L, позиции, доступные лоты, статус торгов, возраст данных) — чтобы спор
«почему не торговали» закрывался записью, а не пересчётом задним числом.

`REQ-risk-gate-02` Ни одна проверка не может быть отключена конфигом пользователя. Отключаются
только явно помеченные как «эвристические» (R12, R13, R24), и только понижением строгости,
с записью в `risk_events`.
`AC-risk-gate-02` Тест: попытка выставить `R10` в `false` в настройках стратегии → ошибка
валидации; попытка сделать это через прямой запрос в БД → при следующем `decide` работает
константа ядра, а не строка из БД (проверяется тестом «изменение строки в обход сервиса не
влияет на ядро»).

## 6.3 Kill-switch

Три уровня: (1) глобальный (администратор), (2) пользовательский (оператор), (3) автоматический
(срабатывание R22/R23/R19). Включение: немедленно запрещает новые намерения всем стратегиям
соответствующей области; опции «снять активные заявки» и «закрыть позиции» — отдельные
действия со своими подтверждениями. Отключение — только вручную, с TOTP и указанием причины;
состояние отображается в UI крупно и в Telegram.

`REQ-risk-gate-03` Kill-switch исполняется за ≤2 с с момента нажатия (замеры в e2e-тесте).
`AC-risk-gate-03` Тест на mock-брокере: нажатие → все `PostOrder` после этого момента
отклоняются `R03`, открытые заявки отменены (если опция выбрана), событие записано.

## 6.4 Коды отказа — единый перечень

Коды R01…R35 выше — публичный протокол: показываются в UI (со ссылкой на объяснение), в
Telegram, в `strategy_events`, в метриках (`tbot_risk_denied_total{code=...}`) и в отчётах.
Новые коды добавляются только в конец перечня.

## 6.5 Лимиты по умолчанию (консервативный профиль, заказчик утвердил)

| Ключ | Значение | Диапазон настройки |
|---|---|---|
| `capital_max_pct_per_strategy` | 5% капитала пользователя | 1…10% |
| `capital_safety_factor` | 0.9 | 0.5…1.0 |
| `daily_loss_limit_pct` | 3% стартовой дневной эквити | 1…5% |
| `max_position_pct` | 5% | 1…10% |
| `max_total_exposure_pct` | 30% | 10…50% |
| `grid.levels_max` | 6 (потолок) | 1…6 |
| `grid.volume_mult_max` | 1.3 (потолок) | 1.0…1.3 |
| `grid.max_drawdown_pct` | 4% | 1…15% |
| `ta.risk_per_trade_pct` | 0.5% | 0.1…2% |
| `margin_safety_min` | 1.35 | 1.2…3.0 |
| `max_orders_per_min_per_strategy` | 12 | 1…30 |
| `max_active_orders_per_instrument` | 10 | 1…20 |
| `max_price_age_ms` | 3000 | 500…60000 |
| `dedup_window_s` | 5 | 0…60 |
| `flatten_on_disconnect_s` | 0 (выкл.; 30 — рекомендовано после обкатки) | 0…300 |

Повышение любого значения выше «верхней границы диапазона» недоступно оператору: только
изменение системной константы через PR + ADR + тест (см. `docs/tz/15`), либо режим
`expert` у администратора с двойным TOTP-подтверждением и обязательной записью в `risk_events`.

## 6.6 Маржинальная торговля (решение заказчика: флаг на уровне стратегии)

`REQ-risk-gate-04` Параметр `allow_margin` по умолчанию `false`. Его включение требует:
(1) явного действия в UI; (2) подтверждения TOTP; (3) предупреждения с перечнем рисков;
(4) записи `risk_events: margin_enabled` с параметрами; (5) обязательной проверки R19.
Для счетов ИИС торговля запрещена вообще (`docs/tz/01 §1.4`).
`AC-risk-gate-04` Тест: `allow_margin=true` без подтверждённого флага в БД → мутация
отклоняется `R18`.

## 6.7 Что делает риск-гейт при неопределённости

Если после `PostOrder` результат неизвестен (таймаут, обрыв), риск-гейт на весь период сверки
возвращает `R27` для этого инструмента, то есть «не торгуем, пока не разобрались». Это
предпочтительнее «быстро повторить». Полное описание процедур — `docs/tz/07`.
