# 05. Стратегии: требования, параметры, инварианты

Общее: стратегия — это **детерминированная** функция от `(MarketSnapshot, PortfolioSnapshot,
StrategyState, Params)` → набор `Intent | CancelRequest | Nothing` + объяснение. Никакой сети,
никакого времени «из стенных часов» (время передаётся в `StrategyContext.now_utc`), никаких
случайных величин без зерна (seed в `params`). Это позволяет гонять один и тот же код в
`paper`, `production` и в бэктесте без изменений.

Реестр стратегий (`strategy-engine`): `kind` → фабрика + JSON-Schema параметров + валидатор +
диапазоны (см. `docs/tz/06`). Регистрация новой стратегии не должна менять ядро.

## 5.1 Стратегия `grid` — сетка с усреднением (Long / Short)

Логика: набор лимитных уровней («таблица»), каждый следующий уровень отстоит от предыдущего на
шаг и больше по объёму на множитель; исполненные уровни формируют совокупную позицию со средней
ценой; при достижении целевой прибыли по позиции она закрывается, таблица перестраивается.
Ключевая особенность — управляемость объёма: количество уровней и множитель жёстко ограничены
риск-гейтом.

### Параметры (значение по умолчанию / диапазон / смысл)

| Параметр | Default | Диапазон | Смысл |
|---|---|---|---|
| `direction` | `long` | `long` \| `short` | направление первой таблицы; одновременные long+short по одному инструменту запрещены в M1 |
| `base_step_pct` | 1.0 | 0.2…10 | отступ первого уровня от опорной цены, % |
| `step_growth` | 1.0 | 1.0…2.0 | множитель расстояния между уровнями (геометрия шагов) |
| `levels` | 4 | 1…6 (жёсткий потолок системы 6) | количество уровней таблицы |
| `volume_mult` | 1.2 | 1.0…1.3 (жёсткий потолок 1.3) | множитель объёма следующего уровня (усреднение) |
| `order_lots_min` | 1 | 1…50 | минимальный объём уровня в лотах |
| `slice_max_lots` | 0 (выкл.) | 0…100 | разбиение крупного уровня на несколько заявок (скрытие объёма в стакане) |
| `take_profit_pct` | 1.2 | 0.3…10 | целевая прибыль относительно средней цены позиции, % |
| `take_profit_mode` | `avg_plus` | `avg_plus` \| `target_price` | как задаётся цель: от средней цены или явной ценой |
| `recenter_mode` | `on_price_move` | `off` \| `on_price_move` \| `always` | перестройка таблицы при уходе цены |
| `recenter_trigger_pct` | 2×`base_step_pct` | 0.2…10 | порог ухода цены от ближайшего уровня |
| `recenter_allow_if_filled` | `false` | bool | разрешать перестройку, если есть исполненные уровни |
| `max_drawdown_pct` | 4.0 | 1…15 | стоп-лосс по совокупной позиции таблицы (% от вложенного) |
| `stop_mode` | `stop_order` | `stop_order` \| `market_order` \| `off` (off только в `paper`) | способ аварийного выхода |
| `pause_rsi_low/high` | 25/75 | 0…100 с проверкой порядка | пауза новых таблиц при выходе RSI за коридор (защита от импульса) |
| `pause_move_pct_5m` | 3.0 | 0.5…15 | пауза при движении цены больше порога за 5 минут |
| `max_spread_bps` | 30 | 1…500 | не входить, если спред/ликвидность хуже |
| `min_price_age_ms` | 3000 | 500…60000 | отказ при устаревании данных (см. `market_data_lag`) |
| `session_guard_min` | 15 | 0…120 | не начинать таблицу в последние N минут сессии и первые N минут после открытия |
| `allow_margin` | `false` | bool | требуется явное подтверждение 2FA (см. `docs/tz/06 §6.6`) |
| `entry_order_type` | `limit` | `limit` \| `bestprice` | тип входных заявок |
| `exit_order_type` | `limit` | `limit` \| `market` | тип выходных заявок (market — с `max_slippage_bps`) |
| `commission_bps` | из конфига | 0…1000 | комиссия для внутренних расчётов (API не отдаёт) |
| `max_orders_per_min` | 12 | 1…30 | темп работы стратегии (поверх общего бюджета API) |

### Инварианты (проверяются ядром и тестами, нарушение = блокировка стратегии)

1. `levels ≤ 6`, `volume_mult ≤ 1.3` — системные потолки; конфиг пользователя не может их поднять.
2. Суммарный объём таблицы в деньгах ≤ `capital_allocated` × `capital_safety_factor`
   (по умолчанию 0.9), а `capital_allocated ≤ 5%` от капитала пользователя (консервативный
   профиль `docs/tz/06`).
3. Каждый уровень кратен лотности инструмента; уровень меньше одного лота не выставляется
   (иначе стратегия помечается `error` с причиной «капитал меньше одного лота»).
4. Цена каждого уровня нормализована к `min_price_increment` (покупка — вниз, продажа — вверх).
5. Уровни не пересекаются: для `long` цены строго убывают по номеру уровня, для `short` — строго
   возрастают; дистанция между соседними уровнями ≥ `tick`.
6. Одновременно по одному инструменту у одного пользователя активна одна стратегия (защита от
   самоконфликта); попытка создать вторую → 409 с указанием конфликтующей.
7. Заявки стратегии `grid` всегда несут `intent_id` и `client_key`; `grid_levels.order_id` обязан
   ссылаться на существующую заявку; «сирот» (заявок без уровня) быть не может.
8. При `direction=short` и `allow_margin=false` стратегия обязана проверять покрытие
   (`GetMaxLots.sell_max_lots`); продажа сверх покрытия отклоняется риск-гейтом.
9. Таблица не перестраивается, пока есть заявки в состоянии `unknown` по этому инструменту.
10. `grid_levels.state` переходит `planned → placed → filled|cancelled|superseded` без
    пропусков; каждое событие — в `strategy_events`.

### Поведение в специфических ситуациях (обязательное)

| Ситуация | Требуемое поведение |
|---|---|
| Рестарт ядра при активных уровнях | после `reconcile()` таблица считается по фактическим заявкам брокера; новые уровни не создаются, пока сверка не завершена |
| Гэп цены через несколько уровней | уровни внутри гэпа считаются «исполнимыми по рыночной цене» только при `recenter_mode=always`; иначе уровни переносятся, факт возможного исполнения фиксируется в журнале как `gap_skipped` |
| Остановка торгов/аукцион | новые заявки запрещены (`TRADING_STATUS_FORBIDDEN`), активные заявки снимаются до клиринга, если `cancel_before_clearing=true` (по умолчанию true за 5 мин до окончания основной сессии) |
| Выход за RSI/импульс | новые таблицы не создаются; существующие уровни остаются; событие `pause_by_volatility` |
| Достижение цели по позиции | снятие оставшихся уровней → закрытие позиции (limit/stop как задано) → `strategy_events: cycle_closed` → перестройка таблицы (если не включён `one_cycle_only`) |
| Сработавший `max_drawdown_pct` | состояние `blocked_by_risk`, все заявки сняты, позиция закрывается по `stop_mode`, требуется ручная разблокировка (TOTP) |
| Цена ушла, таблица не начиналась | `recenter` переносит уровни (`superseded` + новые `planned`), при `recenter_allow_if_filled=false` и наличии исполненных уровней — перестройка запрещена |
| Отказ брокера по заявке (`REJECTED`) | 1 повтор с исправленной ценой (если причина — цена вне диапазона), дальше — остановка стратегии с алертом |
| Истёкший токен / ошибка 401 | все стратегии контура → `blocked_by_risk`, заявки не создаются, алерт «нужен новый токен» |

## 5.2 Стратегия `ta` — индикаторная (тренд / возврат к среднему)

Набор индикаторов (`packages/indicators`, чистые функции, с тестами на эталонных рядах):
SMA, EMA, RSI (Уайлдер), MACD, ATR, Bollinger Bands; опционально — сверка с серверным
`GetTechAnalysis` брокера (расхождение > 1e-6 относительного → алерт «разные индикаторы»).

Параметры: `mode` (`trend` | `mean_reversion`), таймфрейм сигнала (`5MIN…DAY`), таймфрейм
исполнения, окна индикаторов (`ema_fast`, `ema_slow`, `rsi_period`, `macd`, `bb_period`,
`bb_dev`, `atr_period`), правила входа (логическая комбинация условий, фиксируется как
декларативная конфигурация, а не код), `stop_loss_pct` / `take_profit_pct` / `trail_atr_mult`,
`risk_per_trade_pct` (по умолчанию 0.5%, потолок 2%), `max_open_positions` (по умолчанию 1 на
стратегию), `confirm_on_closed_candle` (по умолчанию `true`; сигнала по незакрытой свече быть
не может), `stop_execution` (`broker_stop_order` | `synthetic`).

Обязательные правила:

- `REQ-strategy-ta-01` Расчёт индикаторов только по закрытым свечам; при расчёте используются
  только свечи с `ts + interval ≤ now_utc` (защита от заглядывания вперёд — общая с бэктестом).
- `REQ-strategy-ta-02` Размер позиции считается от риска на сделку:
  `lots = floor(risk_budget / (stop_distance × lot_size))`, с последующей проверкой доступных
  лотов через `GetMaxLots`. Если результат 0 лотов — `Nothing` с причиной `LOT_TOO_SMALL`.
- `REQ-strategy-ta-03` Стоп и тейк либо выставляются стоп-заявками брокера
  (`PostStopOrder`: `STOP_LOSS` + `TAKE_PROFIT`, `expiration_type=GOOD_TILL_CANCEL`, при
  `GOOD_TILL_DATE` — явная дата до конца сессии), либо сопровождаются локально; выбранный способ
  записывается в `params`, смешение способов в одной стратегии запрещено.
- `REQ-strategy-ta-04` При срабатывании стопа локального типа стратегия обязана снять
  противоположную заявку брокера (иначе остаток живёт независимо) — событие `stop_pair_removed`.
- `REQ-strategy-ta-05` Не более `max_orders_per_min` заявок в минуту, темп ограничивается и
  риск-гейтом, и общим бюджетом API.

## 5.3 Расширение: фьючерсы и валюта (веха M4+)

Требования к подготовке уже в M1, чтобы не переписывать ядро: `price_type=POINT` для
срочного рынка, `margin_attributes` (ГО/СО, `funds_sufficiency_level`) как обязательная
проверка перед заявкой, экспирация и ролловер (закрытие до экспирации, перенос объёма),
ликвидация/гарантийное обеспечение (`guarantee_for_futures`), отсутствие `FILL_OR_KILL` на
срочном рынке, валютная пара — своя специфика (целое число лотов, валюта расчётов, другой
календарь сессий). До готовности этих пунктов стратегия на фьючерсе/валюте не может быть
создана (валидация `kind`+`instrument_type` даёт отказ).

## 5.4 Реестр стратегий и свои стратегии (plugin contract)

`REQ-strategy-engine-02` Плагин стратегии — это пакет, реализующий протокол
`StrategyV1(name, params_schema, validate(params), on_candles(batch), on_order_event(ev),
on_position(ev), decide(ctx) -> list[Action])` и зарегистрированный в реестре явным списком в
конфигурации администратора. Плагин не имеет доступа к: сети, файловым путям кроме разрешённых,
переменным окружения, модулям `broker_gateway`/`order_executor`/`storage`, модулям `identity`.
Проверка — статический тест архитектуры + ограниченный импорт-хук в рантайме.
`AC-strategy-engine-02` Тест: тестовый плагин пытается импортировать `broker_gateway` →
запрет, стратегия помечена `error`, алерт.
`REQ-strategy-engine-03` Параметры плагина валидируются JSON-Schema; неизвестный параметр →
ошибка создания стратегии (не «игнорируем»). Версия схемы хранится в `params`.
