# 01. Пользователи, роли, сценарии, правила допуска

## 1.1 Роли

| Роль | Возможности | Ограничения |
|---|---|---|
| `admin` (владелец системы, 1–2 человека) | всё: пользователи, приглашения, одобрение, роли, IP-allowlist, глобальный kill-switch, системные настройки, подключение токенов и счетов, просмотр журналов | не может отключить собственное 2FA без второй учётной записи администратора (контроль «не остаться без доступа») |
| `operator` (владелец счёта) | свои стратегии, свои счета/токены, свои отчёты, Telegram-привязка, пауза/стоп своих стратегий, аварийное снятие заявок по своим счетам | не видит других пользователей; не меняет системные лимиты-константы; не создаёт пользователей |
| `viewer` (наблюдатель, например аудитор) | только просмотр своего/разрешённого набора страниц и отчётов, экспорт | ни одной кнопки изменения; ни одной торговой операции; вход всё равно с TOTP |

`REQ-identity-01` Система реализует ровно три роли; роли наследуются (viewer ⊂ operator ⊂ admin)
по принципам наименьших привилегий; проверка роли — на уровне сервиса, а не шаблона.
`AC-identity-01` Сценарий: `operator` пытается открыть `/admin/users` → ответ 403 без утечки
списка пользователей (ни имён, ни счётчиков в error-шаблоне). Проверка: интеграционный тест.

## 1.2 Допуск пользователей (закрытый клуб)

Порядок: `admin` создаёт приглашение (e-mail или логин + срок действия 14 дней, одноразовая
ссылка) → приглашённый устанавливает пароль (политика п. 1.5 `docs/tz/08`) → привязывает TOTP →
`admin` одобряет учётную запись (второй шаг, отдельная страница со списком ожидающих) →
доступ открыт.

`REQ-identity-02` Самостоятельной регистрации нет: маршрут «зарегистрироваться» отсутствует;
приглашение без одобрения администратора не даёт ни сессии, ни прав.
`AC-identity-02` Неприглашённый пользователь не может создать аккаунт ни одним из известных
путей (проверка: тест всех POST-маршрутов + ручной прогон списка маршрутов).
`REQ-identity-03` Приглашение: одноразовое, срок 14 дней, отзыв по действию администратора,
все попытки использования фиксируются в audit log (IP, user-agent, результат).

## 1.3 Сценарии оператора (пользовательские истории с критериями)

1. **Подключить счёт.** Оператор вставляет токен T‑Invest в форму; система проверяет токен
   (read-only вызовы), показывает найденные счета (тип, статус, валюта), предупреждает, если
   счёт не поддерживается (см. п. 1.4), требует явного выбора счетов, запрещаемых к торговле.
   `REQ-credentials-01`, `AC-credentials-01` (успешное подключение: в UI отображаются замаскированный
   токен, дата проверки, срок действия, список счетов; в БД — только шифртекст).
2. **Создать стратегию.** Мастер из 4 шагов: инструмент → контур (sandbox/paper/production) →
   параметры стратегии → профиль риска (выделенный капитал, лимиты) → предпросмотр → «запустить».
   Запуск в `production` требует подтверждения TOTP. `AC-strategy-engine-01`.
3. **Контролировать.** Список стратегий: статус, инструмент, контур, позиция, свободный лимит,
   P&L дня, количество активных заявок, время последнего события, индикатор «данные свежие?».
4. **Остановить.** «Пауза» (не создаются новые намерения, открытые заявки остаются), «Стоп»
   (снятие заявок стратегии, позиции по умолчанию остаются), «Аварийное закрытие позиций»
   (отдельная команда с двойным подтверждением и TOTP).
5. **Получить отчёт.** За период: сделки, комиссии, P&L по стратегиям, эквити, максимальная
   просадка; экспорт CSV/XLSX; скачанный файл содержит только данные пользователя.
6. **Проверить стратегию на истории** до запуска: форма бэктеста, таблица прогонов, метрики,
   график эквити, сравнение двух прогонов.
7. **Реагировать на инцидент.** Алерт в Telegram → страница состояния системы (лаг данных,
   состояние стримов, бюджет API, ошибки брокера) → действие (перезапуск стратегии, отзыв
   токена, смена IP-allowlist).

## 1.4 Правила по счетам и инструментам

| Тип счёта (enum API) | Торговля | Комментарий требования |
|---|---|---|
| брокерский (`ACCOUNT_TYPE_TINKOFF`) | разрешена | основной контур |
| ИИС (`ACCOUNT_TYPE_TINKOFF_IIS`) | **запрещена по умолчанию** | `REQ-credentials-02`: запуск возможен только явным флагом администратора + предупреждение о последствиях; по умолчанию стратегия не создаётся |
| «Инвесткопилка» / фонды / смарт-счета (`ACCOUNT_TYPE_INVEST_BOX`, `ACCOUNT_TYPE_INVEST_FUND`, смарт-счета) | запрещена | токен с доступом к одному счёту для них не выпускается, торговые операции недоступны |
| прочие (депозиты, ОМС, DFA, накопительные) | запрещена | показывать как «не для робота» |

`REQ-credentials-03` При подключении токена система сравнивает набор счетов с whitelist'ом
типов и не даёт выбрать запрещённый тип; попытка обойти (прямая подстановка account_id) даёт
отказ с записью в audit log.
`REQ-credentials-04` Токен с правом перевода (`transfer-access`) не принимается: перед сохранением
система выполняет read-only проверку и отказывает, если токен даёт переводы между счетами;
соответствующий метод API (`CurrencyTransfer`, `PayIn` вне песочницы) не вызывается никогда
(см. `docs/tz/15`).
`REQ-instrument-catalog-01` Стратегия может быть создана только для инструмента из списка
разрешённых (whitelist администратора: тикер/класс-код, тип инструмента, секция торгов,
доступность торгов), с известными лотностью, шагом цены и валютой; инструмент без этих данных —
отказ.

## 1.5 Ограничения масштаба (на что оптимизируем)

Расчётный масштаб: **3 пользователя, ≤15 активных экземпляров стратегий, ≤100 подписок на
инструменты** (суммарно по всем пользователям), при этом архитектура и лимиты API выдерживают
запас ×2 (30 стратегий, 200 подписок). Ограничения системы (из документации брокера), которые
нельзя превышать: до 32 стрим-соединений на котировки, 16 на каждый тип стрима ордеров, 11 на
каждый тип стрима операций, до 300 подписок в одном стриме котировок, до 100 запросов
подписки в минуту; суммарно ≤50 запросов/с и ≤1000 запросов/мин с IP (см. `docs/tz/03`).

`REQ-market-data-01` Менеджер подписок ведёт глобальный реестр активных подписок и соединений
и отказывает в новой подписке, если она превысит лимит брокера, с явной ошибкой для UI
(«достигнут лимит подписок»).
`AC-market-data-01` Сценарий: попытка создать 301-ю подписку свечей в одном стриме → отказ,
в UI объяснение, в метрике — счётчик отказов. Проверка: интеграционный тест на mock-сервере.

## 1.6 Что считается нарушением продукта

- Любая заявка, не прошедшая `risk-gate` (фиксация: заявка без записи `intents` → инцидент S1).
- Любая запись токена/пароля/ПДн в лог, в БД в открытом виде, в отчёт, в Telegram.
- Выход в интернет сверх разрешённого списка хостов (`docs/tz/08` п. 8.6).
- Изменение риск-лимита «по ходу» кодом без изменения конфигурации и audit-записи.
