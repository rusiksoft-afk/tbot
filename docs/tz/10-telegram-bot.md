# 10. Telegram: уведомления и управление

## 10.1 Режим и транспорт

- Один бот (один токен `BOT_TOKEN`), long polling (без исходящего вебхука ⇒ не нужен
  публичный вход для Telegram; при выборе вебхука — отдельный путь с проверкой секрета
  `X-Telegram-Webhook-Secret-Token` и белым списком адресов Telegram).
- Очередь отправки — таблица `notification_outbox` (см. §4.8) с экспоненциальным backoff;
  лимиты Telegram: ≤30 сообщений/с суммарно и ≤1 сообщение/с на один чат (при массовых
  событиях — агрегация).
- Формат: MarkdownV2 с экранированием (никакого пользовательского текста «как есть»),
  длина ≤3500 символов с многосообщением по границам строк; числа формуются как в UI.
- Приватность: в сообщениях — маска токена (`t.XY…9f`), последние 4 символа счёта (или
  внутреннее имя счёта), никаких ПДн третьих лиц, никаких ссылок с токеном сессии.

## 10.2 Привязка чата (обязательная процедура)

1. В веб-консоли оператор нажимает «привязать Telegram» → генерируется одноразовый код
   (8 символов, TTL 15 минут) и выдаётся инструкция: «отправьте боту `/bind <код>`».
2. Бот принимает `/bind`, проверяет код, показывает данные чата (id, имя) и требует
   **второго подтверждения**: оператор вводит в чат 6-значный TOTP (или резервный код) —
   защита от привязки чужого чата.
3. После подтверждения привязка активна; повторная привязка другого чата требует
   подтверждения в веб-консоли и отзыв прежней (уведомление на старый чат).
4. Команда `/unbind` отвязывает; отзыв делает и администратор (с уведомлением).

`REQ-telegram-01` Все команды бота работают только для привязанного `chat_id`, привязка
подтверждена TOTP, и пользователь активен (`state='active'`). Иначе — отказ без объяснения
причин («неизвестная команда» для неподтверждённых чатов, чтобы не раскрывать существование
системы).
`AC-telegram-01` Тест: неподтверждённый `/bind` → не привязан; неподтверждённая команда из
непривязанного чата → нет ответа с данными; попытка перебора кодов `/bind` → 5 попыток на
чат → кулдаун 15 минут + алерт администратору.

## 10.3 Уведомления (push)

Обязательные события (шаблон: код, время МСК, объект, что произошло, что нужно сделать):

| Код | Событие | Кому | Приоритет |
|---|---|---|---|
| `AUTH_NEW_DEVICE` | вход с нового IP/устройства | пользователю + админу | высокий |
| `AUTH_LOCKED` | блокировка входа | пользователю + админу | высокий |
| `TOKEN_EXPIRING` / `TOKEN_INVALID` | токен истекает (14/7/3 дня) / недействителен | владельцу счёта | высокий |
| `STREAM_DISCONNECTED` | стрим котировок/портфеля не восстановлен >60 с | оператору | высокий |
| `ORDER_REJECTED` | заявка отклонена брокером | оператору | средний (агрегировать) |
| `RISK_DENIED_BURST` | >10 отказов риск-гейта за минуту | оператору + админу | высокий |
| `KILL_SWITCH` | включение/выключение kill-switch | всем затронутым | высокий |
| `DAILY_LOSS_LIMIT` | достигнут дневной лимит убытка | владельцу + админу | высокий |
| `POSITION_MISMATCH` | расхождение позиции с брокером | оператору + админу | высокий |
| `ORDER_UNKNOWN` | заявка в состоянии `unknown` >30 с | оператору + админу | критический (дублируется) |
| `STRATEGY_BLOCKED` | стратегия в `blocked_by_risk`/`error`/`quarantined` | оператору | высокий |
| `EXEC_LATENCY` | p95 исполнения > целевого (`docs/tz/07 §7.7`) 10 минут | админу | средний |
| `SYSTEM` | диск >85%, БД недоступна, сбой задания, деплой | админу | средний/высокий |
| `MARKET_EVENT` | инструмент стратегии остановлен/возобновлён торги, делистинг, сплит | оператору | средний |

Суточный дайджест (по умолчанию 20:35 МСК, настраивается): эквити, P&L дня/недели,
P&L по стратегиям, число сделок и средний размер, комиссии, максимальная просадка,
число отказов риск-гейта по кодам, состояние токенов (срок), статус системных проверок.
Дайджест приходит, даже если торговля не велась (подтверждение «система жива»).

`REQ-notifications-01` Дедупликация по `dedup_key` (окно 10 минут) и агрегация однотипных
событий («12 отклонённых заявок SBER: R10 ×8, R13 ×4» с указанием, где посмотреть детали).
`REQ-notifications-02` Уведомления не должны влиять на торговый контур: при недоступности
Telegram торговля продолжается, очередь растёт с ограничением (старые низкоприоритетные
сообщения отбрасываются с фиксацией).

## 10.4 Команды чтения (без подтверждения)

`/status` — состояние ядер, стримов, бюджетов API, ближайших заданий, версия сборки.
`/pnl [день|неделя|месяц]` — сводка по пользователю.
`/positions` — позиции (маска счёта, инструмент, объём, средняя цена, P&L, доля капитала).
`/orders` — активные заявки (не более 20, далее «см. веб-консоль»).
`/strategies` — список стратегий с состоянием и P&L.
`/strategy <id>` — детали: уровни, лимиты, последние события, последние отказы риск-гейта.
`/alerts` — последние оповещения. `/limits` — текущие риск-лимиты (без возможности изменить).
`/help` — список команд и ограничений. `/version` — версия и дата сборки.
Команды доступны только в приватном чате (в группах бот не отвечает, либо отвечает
`/privacy`-заглушкой; требование — личная переписка, см. `REQ-telegram-01`).

## 10.5 Управляющие команды (с подтверждением)

| Команда | Подтверждение | Действие |
|---|---|---|
| `/pause <id>` / `/resume <id>` | inline-кнопка «подтвердить» | пауза/возобновление стратегии |
| `/stop <id>` | inline-кнопка + ввод 6-значного TOTP в чате (TTL 5 минут) | снятие заявок стратегии, позиции остаются |
| `/flatten <id>` | TOTP + ввод текстовой константы `ЗАКРЫТЬ` | снятие заявок и закрытие позиций стратегии рыночными заявками в рамках лимитов |
| `/cancelall [account]` | TOTP | снятие всех активных заявок области |
| `/kill` / `/kill off` | TOTP (+ второй админ-фактор для `off`) | глобальный kill-switch |
| `/strategy <id> params …` | **не поддерживается** в Telegram (только просмотр) | изменение параметров — только в веб-консоли |

Ограничения: `flatten` исполняется только в торговую сессию и при соблюдении лимитов
риск-гейта (он не «освобождает» от проверок); если исполнение невозможно — оператор получает
объяснение и список оставшихся заявок. Каждое действие дублируется в веб-консоль и `audit_log`,
а также отправляется в чат второго администратора.

`REQ-telegram-03` Подтверждающий TOTP в чате принимается один раз, действует 5 минут,
привязан к `command_id` (нельзя подтвердить другую команду).
`AC-telegram-03` Тест: код, выданный для `/stop A`, не подтверждает `/flatten B`; повторное
использование кода → отказ + алерт.

## 10.6 Защита от злоупотребления каналом

- Никаких ссылок «открыть панель» с токеном сессии в сообщениях; только обычный адрес домена
  и подсказка «войдите вручную».
- Файлы (отчёты) в Telegram не отправляются по умолчанию (финансовая история и ПДн):
  в чате — только сводка и указание, где скачать (решение зафиксировано, см. OQ-5).
- Бот не принимает текстовые «свободные» команды-намерения («купи SBER на 5 тысяч») — только
  фиксированный набор; это исключает prompt-style инъекции и случайные действия.
- Логи Telegram-обмена: `telegram_messages_log` без содержимого сообщений (мета + хэш),
  содержимое — только при включённой отладке и с автоматическим стиранием через 7 дней.

## 10.7 Транспорт к Telegram API на прод-площадке (схемы A, C′, B)

Основание — замеры `docs/research/03 §3.4, §3.7`: с прод-ВМ DNS отдаёт `149.154.166.110`,
до которого нет пути; из 7 проверенных адресов Telegram TCP/443 жив только
`149.154.167.220`. Значит полагаться на DNS нельзя, а один адрес — единственная точка отказа.
**Базовый набор: A + C′. Вариант B — резерв** (решение уточнено 2026-11-19 после вопроса
заказчика: контейнер на узле B не требуется, достаточно туннельного egress — `docs/research/03 §3.7.1`).

**A. Прямой транспорт с пулом адресов (на проде).**
- `TG_API_ENDPOINTS`: упорядоченный пул (имя + IPv4 известных DC). Обход по кругу с
  фиксированным приоритетом живого адреса;
- обязательная проверка сертификата с SNI `api.telegram.org`: совпадение имени и цепочки —
  условие использования адреса (защита от подмены адреса DC), никакой деградации до
  `verify=False`;
- health-check `getMe` по каждому адресу раз в 60 с; при N подряд ошибках адрес помечается
  `dead` на период backoff (30 с → 15 мин), живой выбирается автоматически;
- метрики: `tg_endpoint_rtt_ms{endpoint}`, `tg_endpoint_up{endpoint}`,
  `tg_endpoint_switch_total`, `tg_last_delivery_age_s`; алерты `TG_ALL_ENDPOINTS_DOWN`,
  `TG_NOTIFICATION_LAG` (TZ §12.4).
`AC-telegram-04` Тест (mock-транспорт): два адреса «живых», один «мёртвый» → трафик идёт по
живым, переключение и метрики корректны; при подмене имени в сертификате адрес не
используется и поднимается алерт.

**C′. Туннельный egress через узел `rusiksoft.ru` (`176.32.39.234`).** `tgbot` остаётся на проде.
Интерфейс для приложения — **локальный SOCKS5 на проде** (`socks5h://127.0.0.1:10800`), а
транспорт до узла B — **VLESS + TCP + TLS к существующему фронту `rusiksoft.ru:443`** под
отдельным выделенным пользователем (не общим личным). Вариант выбран как самый дешёвый из
проверенных: без нового слушателя, без nginx-location и без маскирующего пути.
(Ранее обсуждавшийся Shadowsocks-over-WebSocket за маскирующим путём остаётся запасным —
`docs/runbook/telegram-egress-proxy.md §4.1.) Реализованное состояние и проверки —
`docs/acceptance/tg-egress.md`; требования (без них схема не принимается):
- интерфейс приложения — локальный SOCKS5 на петлевом интерфейсе, с паролем
  (defense-in-depth); приложение обязано отдавать имя хоста прокси как есть
  (`socks5h`, SOCKS-команда с доменом): DNS прода возвращает недоступный адрес
  `149.154.166.110`, поэтому предварительный резолв убивает путь ещё до туннеля;
- ключ туннеля по сети не передаётся (в отличие от логина/пароля SOCKS5); если значение
  где-то засветилось — ротация до запуска, в чат/документацию/git оно не попадает;
- **выделенный пользователь обязателен**: маршрутизация на узле B привязана к пользователю,
  поэтому общий с личными клиентами вход нельзя использовать для торгового контура —
  правила и статистика перемешаются;
- маршрутизация на узле B — отдельное правило по пользователю с **явным** outbound-тегом
  (сначала `direct`, иначе один конкретный exit), расположенное выше общих правил;
  балансировщик выходов для нашего пользователя запрещён (плывущий исходящий IP ломает
  наблюдаемость и может провоцировать троттлинг) — на момент приёмки это единственное
  незакрытое требование (см. §10.6 и `docs/acceptance/tg-egress.md`, проверка 9);
- **запрет внутренних адресов**: для нашего пользователя отдельное правило на `blocked` для
  loopback/приватных/CGNAT-диапазонов, метаданных облака и собственного домена — иначе
  туннель становится путём к панели, БД и внутренним сервисам узла B (проверено: без правила
  через SOCKS принимались соединения к `127.0.0.1` и `169.254.169.254`);
- TLS-верификация не ослабляется: на узле B фронт с настоящим сертификатом Let's Encrypt
  (`Verify return code: 0` с прод-ВМ, закрепление отпечатка не требуется), а цепочка
  `api.telegram.org` проверяется при каждом соединении; расхождение → разрыв, алерт
  `tg_tls_mismatch`, переход на транспорт A; фронт согласует `alpn: ["http/1.1"]`, это
  указывается и в клиенте; `xtls-rprx-vision` работает только при прямом TLS до Xray, поэтому
  этот вход нельзя ставит за nginx без потери vision;
- через туннель идут **только** обращения к Telegram API: вызовы API брокера, БД и веб-панель
  остаются на прямом пути (первое правило маршрутизации на проде — по тегу SOCKS-входа);
- учётные данные (пароли SOCKS, токен бота) — файлами в `/etc/tbot/secrets/` на проде (600),
  конфиг туннеля `/etc/tbot-tunnel/config.json` (640, владелец `root:tbot-tunnel`); значения
  маскируются в логах, не передаются через чат/переписку и не попадают в git;
- **путь выбирается конфигурацией явно**: `telegram.transport = tunnel | direct`
  (`TBOT_TELEGRAM__TRANSPORT`), при `direct` приложение не использует прокси вовсе. Автоматического
  «сам определился» путь нет: у путей разные предупреждения в `/readyz` и разные метки в метриках;
- клиент туннеля на проде установлен постоянно как сервис `tbot-tunnel` (исключение из паузы
  T-011 согласовано заказчиком): Xray 26.11.9 с закреплённым дайджестом пакета, отдельный
  пользователь `tbot-tunnel` без оболочки, systemd-unit с жёсткими ограничениями;
- метрика `tg_endpoint_up{path="direct|tunnel"}`, `tg_egress_exit_ip` (IP, который видит
  Telegram — замеряется отдельно), задержка не нормируется жёстко: измерено **0.24–0.38 с**
  через туннель (медиана ≈ 0.27 с) — допустимо для кнопок управления (см. §10.5: задержка
  кода TOTP от транспорта не зависит), но не для чего-либо торгового;
- **вывод трафика обязан быть детерминированным:** в проверке 2026-11-19 выбор делал
  балансировщик узла B, и два замера подряд дали разные точки выхода — Амстердам (NL), затем
  Стокгольм (SE), оба в диапазонах Cloudflare (AS13335). То есть один и тот же бот для
  Telegram виден с разных IP из диапазонов CDN/публичных прокси — это типичный триггер
  анти-злоупотреблений (троттлинг, `429`, внезапные отказы) и помеха разбору инцидентов.
  Поэтому правило с явным outbound для нашего пользователя обязательно; при деградации
  проверяется прямой exit самого узла B. Фактический IP фиксируется в
  `docs/acceptance/tg-egress.md` и выводится в метрику `tg_egress_exit_ip`.
`AC-telegram-07` Тест: прокси возвращает подменённый сертификат (самоподписанный на
`api.telegram.org`) → соединение отклонено, событие `tg_tls_mismatch`, транспорт переключается
на A; при падении прокси очередь уведомлений не теряется, статус канала меняется ≤60 с.

**B (резерв). Второй узел как исполнитель `tgbot`.** Применяется, если понадобится изолировать
процесс управления от прод-хоста или если цепочка C′ перестанет ходить в Telegram:
- состав контейнера: только бинарь приложения + конфиг с токеном Telegram и клиентским
  сертификатом mTLS; **запрещены** доступ к БД, к KEK, к токенам брокера (`REQ-security-14`);
- канал к проду: HTTPS/443, mTLS (оба конца), IP-allowlist, ручки `/internal/tg/v1/`
  `poll-notifications`, `post-confirmation`, `heartbeat`; идемпотентность по `message_id` /
  `command_id`, повторная выдача уведомлений не дублирует сообщения (счётчик `delivered_at`);
  WireGuard в текущей конфигурации связности недоступен (замер — `docs/research/03 §3.7`);
- egress контейнера: только Telegram API и прод-узел; прочие адреса → алерт `EGRESS_UNEXPECTED`
  (TZ §8.5);
- изоляция от остального ПО узла B: отдельный контейнер, отдельный непривилегированный
  пользователь, без монтирования хостовых каталогов и без доступа к конфигам/БД чужих
  сервисов этого узла;
- провал B не влияет на торговый контур (`AC-tgbot-04`): `engine` продолжает исполнять
  стоп-лоссы и лимиты, очередь уведомлений копится на проде с лимитом и вытеснением старых,
  панель показывает «канал Telegram: деградация».
`AC-telegram-05` Тест: у ретранслятора B отключается канал к проду → уведомления не теряются
(после восстановления доставляются в исходном порядке, с пометкой о задержке), команды не
исполняются повторно, статус канала в панели меняется в течение ≤60 с.
`AC-telegram-06` Проверка безопасности: на узле B нет файлов с токеном брокера/KEK
(аудит-сканирование образа), контейнер не может установивить соединение ни с одним адресом,
кроме Telegram и прода (сетевой тест изнутри контейнера).

**Дублирование критичных алертов (S1/S2)** — второй канал (e-mail/иной согласованный), иначе
защитный стоп может остаться незамеченным при деградации Telegram. Порог и канал фиксируются
настройкой `ALERT_SECOND_CHANNEL` (см. также OQ-7 про отчёты).
