# 07. Исполнение заявок (`order-executor`)

Раздел описывает обязательное поведение при работе с брокером: идемпотентность, состояния,
сверка, восстановление. Реализация обязана пройти приёмочные учения (`docs/tz/13 §13.5`).

## 7.1 Диаграмма состояний собственной заявки

```
prepared ──sent──> new ──> partially_fill ──> fill
   │           │        │                    │
   │           │        └────> cancelled <───┘
   │           └─> rejected
   └─(исчерпан бюджет риск-гейта) → не создаётся
sent ──(таймаут/обрыв)──> unknown ──(сверка подтвердила наличие)──> new|partially_fill|fill|cancelled
                        unknown ──(сверка подтвердила отсутствие)──> rejected_for_retry (внутреннее)
```

`unknown` — обязательное состояние. Из него запрещены: повторная отправка с новым клиентским
ключом, отмена «наугад», любые новые намерения по инструменту (`R27`).

## 7.2 Правила выставления

1. До сетевого вызова: создан `Intent`, получено `Approved(decision_id)`, создан
   `client_key` (UUID, ≤36 симв.), записан в `orders` со состоянием `prepared`
   (`REQ-order-executor-01`).
2. Вызов `PostOrder` (или `PostOrderAsync` для малых объёмов, где задержка критична) с этим
   `order_id`. Параметры: `quantity` в лотах, цена нормализована к шагу, `price_type` по типу
   инструмента, `time_in_force` по стратегии, `confirm_margin_trade` строго равный
   согласованному флагу `allow_margin`.
3. Успех: сохраняются биржевой `order_id`, `order_request_id`, тип идентификатора, состояние
   `new`/`partially_fill`, ответные комиссии (`initial_commission`), `sent_at`.
4. Ошибка валидации (400/415): состояние `rejected`, повтор запрещён, алерт «баг/расхождение
   с контрактом» (такое не должно случаться в бою).
5. 401/403: стратегии контура в `blocked_by_risk`, алерт «токен/права».
6. 404: обновить каталог инструментов; если инструмент недоступен — `R08/R09` на 15 минут.
7. 429: бюджет исчерпан — очередь с backoff; если 429 повторяется ≥3 раз за минуту —
   `R25` и пауза стратегии.
8. 408/500/501/503/504 и сетевые обрывы: состояние `unknown` → раздел 7.4.

## 7.3 Замена и отмена

- `ReplaceOrder` используется, только если брокер возвращает корректную семантику замены;
  иначе сценарий «новая заявка → подтверждение приёма → отмена старой» (порядок обязателен,
  чтобы не остаться без заявки). Для `grid` — всегда через `superseded` уровень.
- `CancelOrder` для каждой активной заявки: одна попытка, затем сверка (`GetOrders`),
  затем повтор только если заявка по-прежнему активна. Не более 5 отмен в секунду на счёт.
- Массовое снятие («снять все заявки стратегии/счёта») реализуется как одна команда с
  итерацией и итоговой сверкой; UI показывает прогресс и результат по каждой заявке.

## 7.4 Сверка после неопределённости (главный протокол)

```
1. wait(backoff 0.5s, 1s, 2s)                     — даём брокеру «долететь»
2. GetOrderState(order_id=client_key, ORDER_ID_TYPE_REQUEST)
     найдено  → перейти в соответствующее состояние, синхронизировать события
     не найдено → шаг 3
3. GetOrders(account) → поиск по exchange id / по паре (uid, side, qty, price)
     найдено похожего кандидата → состояние unknown_kept, алерт оператору,
                                    торговля по инструменту остановлена до ручного подтверждения
     не найдено → заявка доказанно не принята
4. только в ветке «доказанно не принята» разрешён повтор:
     тот же client_key? — нет, если брокер требует уникальный ключ на попытку;
     решение фиксируется конфигурацией retry_policy и записью в order_attempts
5. любое решение — в order_events и order_attempts (сырой ответ/ошибка)
```

`REQ-order-executor-04` Шаг «повтор с новым ключом без доказанного непринятия» технически
невозможен: код `order-executor` не имеет пути, где `PostOrder` вызывается повторно при
состоянии `unknown`. Проверяется тестом с имитацией таймаута (`fault`-тест).
`AC-order-executor-04` Сценарий: `PostOrder` → таймаут через 2 с → mock возвращает
«заявка существует» на шаге 2 → итог: одна заявка в брокере, одна в БД, повторных вызовов
`PostOrder` не было (счётчик вызовов mock-сервера = 1).

## 7.5 Восстановление после рестарта процесса

При старте `order-executor` выполняет `reconcile()`:

1. загрузка всех заявок в незакрытых состояниях из БД;
2. `GetOrders` по каждому счёту; сопоставление: по биржевому id → по клиентскому ключу →
   по «отпечатку» (инструмент, сторона, лоты, цена, временное окно ±120 с);
3. найденные — обновить состояния; отсутствующие в брокере, но «открытые» у нас → проверить
   историю (`GetOperations`/`GetOrderState`), затем пометить `cancelled`/`rejected` с причиной
   `reconciled_absent`;
4. заявки брокера, которых нет у нас (ручные действия оператора в терминале) → импортируются
   как `external` и **не** трогаются стратегией, но учитываются в объёме позиции;
5. результат — `reconciliation_runs.result`; расхождения → `position_mismatches` + изоляция
   инструмента.

`AC-order-executor-05` Учение на песочнице: выставить 3 заявки, убить процесс (`kill -9`),
поднять заново, сравнить состояние с терминалом брокера — полное совпадение, новых заявок не
появилось, «лишних» отмен нет.

## 7.6 Частичные исполнения и учёт

Каждое событие частичного исполнения: обновление `filled_lots`, `avg_fill_price`, комиссий,
пересчёт `strategy_counters` и, для `grid`, состояния уровня и оставшегося объёма. Правило
остатка: если остаток уровня < `order_lots_min`, он либо доисполняется переносом в новый уровень
(если это разрешено параметром `carry_remainder`), либо снимается (по умолчанию снимается).

## 7.7 Задержки и целевые метрики исполнения

| Метрика | Цель (VPS в Москве) |
|---|---|
| `PostOrder` round-trip p50 / p95 | ≤ 300 мс / ≤ 900 мс |
| получение события стрима котировок → сигнал стратегии | ≤ 500 мс |
| сигнал → отправка заявки (без ожидания бюджета) | ≤ 200 мс |
| полная реакция «событие → заявка» | ≤ 1 с p95 |
| `reconcile()` после рестарта (10 счетов × 100 заявок) | ≤ 15 с |

Эти значения — целевые для наблюдаемости, а не гарантия брокера; при их нарушении — алерт
`LATENCY_DEGRADED`, но торговля не запрещается (кроме `R05` по возрасту данных).

## 7.8 Бумажный (paper) исполнитель

Тот же код жизненного цикла, но вместо брокера — внутренняя книга: лимитная заявка исполняется,
если цена достигла уровня (для покупки — `low ≤ price`, для продажи — `high ≥ price`) на закрытой
или тиковой свече, с моделью проскальзывания `slippage_bps` и проверкой доступного объёма по
объёму свечи (`volume × participation_cap`, по умолчанию 5%). Market-заявка исполняется по цене
следующей свечи + проскальзывание + спред из стакана (если стакан доступен в этот момент).
Комиссии — из модели тарифа оператора. Требование: paper-исполнитель даёт **пессимистичную**
оценку (не исполняется объём больше доступного по объёму свечи; нет «исполнения по лучшей цене
из двух тиков»).

`REQ-order-executor-06` Paper и production исполнители реализуют один интерфейс
`ExecutionBackend` и отличаются только классом; логика стратегий и риск-гейта не знает, где
она работает. Тесты: одни и те же сценарии прогоняются на обеих реализациях (параметризованные
тесты).
