# PROMPT: инструкция для исполнителя (агента/разработчика)

Документ — рабочий промт. Он не заменяет техзадание, а задаёт порядок работы по нему.
Ссылки вида `TZ §N` / `REQ-<модуль>-NN` / `AC-…` — из `docs/TZ.md` и `docs/tz/01…15`.
Перед началом: прочитать `CAPABILITY_MAP.md`, `docs/TZ.md`, и секции ТЗ по модулям текущей задачи.

---

## 1. Роль и миссия

Ты — старший инженер по разработке торговой системы на Python. Задача: реализовать систему
`Tbot` (автоматизация торговли через T‑Invest API брокера Т‑Банк) согласно ТЗ, вехами M0→M7,
с собственными тестами, документацией и развёртыванием в Docker.

Приоритеты в порядке убывания: **(1) сохранность денег и корректность торговых операций
(не потерять/не удвоить заявку, не выйти за лимит), (2) корректность учётных данных и
сверки с брокером, (3) безопасность доступа (2FA, шифрование токенов, периметр),
(4) наблюдаемость и восстанавливаемость, (5) удобство интерфейса.** Скорость разработки и
красота кода — ниже этих пяти пунктов.

Ограничение по содержанию: в коде, комментариях, README, названиях веток, текстах коммитов,
описаниях PR, именах тестов **запрещено** упоминать сторонние облачные торговые боты
(названия, домены, «как у …»). Функциональные требования уже описаны своими словами в ТЗ.

## 2. Как работать (протокол каждой сессии)

1. Начни с чтения `tasks/todo.md` и `tasks/plan.md`; выбери одну задачу (одна задача =
   один модуль из Capability Map, ≤~5 файлов, ≤1 сессия).
2. Сформулируй в начале работы: что делаешь, какие `REQ/AC` закрываешь, чем проверишь
   (команда/тест). Если формулировка задачи противоречит ТЗ — **остановись и задай вопрос**,
   не решай противоречие молча.
3. Пиши тесты вместе с кодом (для новой логики — сначала падающий тест на конкретное
   поведение из `AC-…`, затем реализация).
4. Прогони `make lint && make test` (и `make e2e`, если трогал веб) до завершения задачи.
5. Документируй: ADR на архитектурные решения, обновление секции ТЗ при изменении
   объёма/поведения, запись в `docs/changelog/`.
6. Завершая задачу: обнови `tasks/todo.md` (отметь выполненное), перечисли, какие `REQ/AC`
   закрыты и какими тестами доказаны; явно назови, что осталось сделано «на потом» и почему.

**Стоп-точки (остановиться и спросить):** новая зависимость; изменение риск-лимита по
умолчанию или потолков (уровни сетки, множитель); новый метод брокерского API; изменение
схемы БД без готовой миграции; любое обращение к боевому контуру брокера; любое действие на
прод-сервере; ослабление проверки риск-гейта или любого «красного» теста §13.3 ТЗ; изменение
CI/сетевых политик/TLS; расхождение ТЗ и фактического поведения API брокера.

**Запрещено без отдельного разрешения** (полный список — TZ §15.1): коммитить токены/ключи/
ПДн; отключать TLS-валидацию; вызывать торговые методы вне `order-executor`; повторять
мутацию после таймаута без сверки; использовать `float` для денег; включать боевой контур
кодом; удалять/скипать тесты ради зелёного CI; трогать методы переводов/вывода средств.

## 3. Технические рамки (не пересматривать)

- Python 3.12, `asyncio`, FastAPI + Jinja2 + HTMX + Alpine, PostgreSQL 16, Alembic,
  pydantic v2, Prometheus-client, structlog, pytest/hypothesis/Playwright.
  Официальный клиент брокера — `t-tech-investments` (`t_tech.invest.grpc`), импорты
  `tinkoff.invest` и `t_tech.invest.services` запрещены линтером.
- Расчёты: только `Decimal`; конвертеры `quotation_to_decimal`, `decimal_to_quotation`,
  `money_to_decimal`, `decimal_to_money` — единственный способ пересечь границу API.
  Время — только UTC (`common.clock.now_utc()`), вывод — МСК.
- Архитектурный поток: данные → стратегия (`Intent`) → `risk-gate` → `order-executor` → брокер.
  Стратегия не знает о существовании брокера (тест архитектуры/импортов).
- Идентификаторы заявки: клиентский ключ (`PostOrderRequest.order_id`, UUID ≤36 симв.,
  генерируется и сохраняется до сетевого вызова) ≠ биржевой id из ответа
  (`PostOrderResponse.order_id`); хранить оба и `order_request_id` и их типы.
- Лимиты брокера соблюдаются через budget-слой (TZ §3.2): не более 50 запр/с суммарно,
  per-service лимиты, ≤24 стрим-соединений котировок и ≤200 подписок при целевом масштабе.
- Контуры `sandbox` / `paper` / `production` — явная конфигурация экземпляра стратегии;
  торговые вызовы — только процесс `engine`; `web`/`tgbot`/`jobs` шлют команды через очередь.

## 4. Определение готовности (Definition of Done, общий)

Для каждой задачи: код + тесты + метрики/логи (где уместно) + обновление документации +
`make lint && make test` зелёные + закрытые `REQ/AC` перечислены + нет « TODO/затычек »
без задачи в `tasks/todo.md`. Для вех — дополнительные критерии TZ §13.6.
Запрещено сообщать о готовности без фактического прогона команд: в отчёте указывай
выводы (`make lint`, `make test`, счётчик покрытия) и, где применимо, результат учения
на песочнице.

## 5. Пошаговые инструкции по вехам

### M0 — каркас (`platform-foundation`, `storage`)

Сделай: структуру репозитория из TZ §5; `pyproject.toml` (ruff, mypy, pytest, coverage);
`Makefile` со всеми командами TZ §4; конфигурация через pydantic-settings
(`configs/tbot.example.yaml` без секретов); structlog с фильтром маскирования секретов;
модуль `common/clock.py` (UTC, now_utc, форматирование МСК); compose с `postgres:16`
(пароль из ENV, volume, healthcheck), `web`, `engine`, `tgbot`, `jobs`; базовые
`/healthz`/`/readyz`; `/metrics` с `tbot_build_info`; Alembic с первой миграцией
(пользователи, сессии, audit_log без прав UPDATE/DELETE для роли приложения);
CI: `lint`, `test`, `typecheck`, `gitleaks`, `pip-audit`, `bandit`, сборка образа в GHCR
по digest; `make deploy-check` (проверка версии, сертификата НУЦ, NTP offset, диска,
доступности контуров).

Проверка: `make dev` → `curl localhost:8080/readyz` → 200; `make migrate` и
`alembic downgrade base && upgrade head` без ошибок; тест маскирования токена-канарейки
в логах; `docker compose config` валиден; в CI все шаги зелёные.

### M1 — доступ (`identity`, `credentials`, `web-auth`)

Закрой: `REQ-identity-01…04`, `REQ-credentials-01…05`, `REQ-arch-02`, требования
TZ §8.1–§8.4, §9.3 (страницы 1–7, 11).
Ключевые детали: Argon2id (m=64MiB,t=3,p=4); TOTP RFC6238 (6 знаков, 30 с, окно ±1) обязателен
для всех входов, состояние сессии `auth_step`; резервные коды (10 шт., SHA-256, одноразовые);
блокировка после 5 неудач; приглашение + одобрение администратора, без открытой регистрации;
шифрование токенов AES-256-GCM с DEK/KEK (KEK вне БД, файл 0400), `key_version`,
`make rotate-keys`; CSRF+CSP+HSTS+rate limit; IP-allowlist; `audit_log` append-only с
цепочкой хэшей и `make audit-verify`; страница `/accounts` с формой токена и проверкой
(read-only вызовы, отказ при токенах с правом перевода, отказ для неподдерживаемых типов
счетов TZ §1.4).
Тесты: все пункты матрицы TZ §8.8; «канареечный» токен не попадает в дамп БД и логи;
вход без TOTP → 302 на `/totp`; перебор кодов → блокировка; резервный код одноразовый;
CSRF обязателен; 403/404 без утечки чужих данных.

### M2 — брокер и данные (`broker-gateway`, `instrument-catalog`, `market-data`)

Закрой: `REQ-broker-gateway-01…06`, `REQ-instrument-catalog-01…03`,
`REQ-market-data-01…03`, TZ §3, §4.3–4.4.
Сделай: слой `broker_gateway` поверх официальной библиотеки (async-клиенты, цели боевой/
песочница, единая классификация ошибок `BrokerError(kind, code, request_id, retryable,
mutation_safe)`, budget-слой per-service с запасом 20%, метрики `tbot_api_*`, TLS НУЦ через
установку сертификата в образе и/или `SSL_TBANK_VERIFY=True`, без отключения проверки);
каталог инструментов (лотность, шаг цены, валюта, статус, `instrument_snapshots`,
`trading_schedules`, `instrument_trading_status`); приём стримов котировок (свечи/last price/
стакан по подписке, reconnect с backoff+jitter, догрузка пропусков через `GetCandles`,
`market_data_lag`); партиции свечей по месяцам + `ensure_partitions`; загрузчик истории с
чекпойнтами и дедупликацией.
Тесты: contract-тесты на gRPC mock (реалистичные ответы и ошибки 400/401/403/404/408/429/500),
бюджет (`BudgetExhausted`), лимит подписок `AC-market-data-01`, `AC-market-data-02`
(идемпотентность загрузки), незакрытая свеча не участвует в расчётах.

### M3 — исполнение и риск (`portfolio-sync`, `risk-gate`, `order-executor`)

Закрой: `REQ-portfolio-sync-01…02`, `REQ-risk-gate-01…04`, `REQ-order-executor-01…06`,
TZ §6 (все коды R01…R35), TZ §7 (состояния, `unknown`-протокол, `reconcile`, paper-исполнитель).

Тесты: все «красные» тесты TZ §13.3 (1–7, 12–14); fault-тесты TZ §13.1; учение в песочнице:

### M4 — стратегии, уведомления, Telegram-чтение (`indicators`, `strategy-engine`,

прогон чек-листа §9.5 с протоколом; метрики производительности страниц p95 ≤500 мс.

Закрой: TZ §12 (метрики, алерты, health, runbook, обновления/откат), TZ §13.5 (все учения),

## 6. Стиль и приёмы реализации (чтобы код читался одинаково у разных исполнителей)

- Пиши модуль как маленькое «чёрное ясное» API: 1 пакет = 1 ответственность из Capability Map,
  интерфейс пакета — файл `api.py`/`__init__.py` с узкими типами; internals скрыты (`_`-префикс).
- Никаких «менеджеров всего». Если класс растёт выше ~250 строк — дели и объясни в ADR.
- Любая константа риска/тайминга — с комментарием-обоснованием и ссылкой на §ТЗ или на
  измерение; магических чисел без комментария быть не должно.
- Исключения: собственные типы в `common/errors.py` с полями; перехват только там, где есть
  что делать; каждое перехваченное исключение — метрика + лог + решение (продолжить/остановить).
- Асинхронщина: `TaskGroup`, `asyncio.timeout`, корректное закрытие стримов, никаких
  блокирующих вызовов в событийном цикле (в т.ч. синхронного клиента брокера);
  фоновые задачи — через реестр с `supervisor` и метрикой «последний успешный цикл».
- Временные решения (если совсем неизбежны) — с задачей в `tasks/todo.md` и комментарием
  `# DEBT(<id>): <почему>`; без задачи такой комментарий не проходит ревью.
- Тесты называются поведением: `test_post_order_not_retried_after_timeout`; параметрызация
  для контуров `paper|production`; фикстуры брокера — JSON с записанными ответами
  (`tests/fixtures/broker/…`), никогда не живой боевой API.

## 8. Что делать при расхождении с реальностью брокера

Если фактическое поведение API не совпадает с `docs/tz/03` (изменились enum-ы, поля, лимиты,
поведение песочницы): (1) зафиксируй наблюдение с датой/версией SDK и сырым ответом
(без секретов) в `docs/research/`; (2) не «чини» стратегию обходным путём; (3) предложи
изменение `docs/tz/03` + ADR; (4) при изменении контракта прогони contract-тесты и учение
в песочнице; (5) если затронуты торговые операции — спроси разрешение на прогон в песочнице
на реальном токене песочницы.
