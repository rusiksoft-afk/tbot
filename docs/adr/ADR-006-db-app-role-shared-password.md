# ADR-006: роль приложения в базе — общий пароль с владельцем схемы и компенсирующие контроли

**Статус:** принят (решения заказчика: 2026-11-20, ask `819fb013` — «переключать на роль
приложения, пароль общий»; 2026-11-21, ask `8d2be9bb` — «обход связки `migrate` ↔ `db_url`
вариантом Б, пароль остаётся общий»). Реализовано и применено на рабочей ВМ 2026-11-21, приёмка —
`docs/acceptance/t-009-identity-schema.md §3.7`. **Опасность этого ADR в том, чтобы его молча
«починили»:** следующая сессия, увидев общий пароль у роли приложения и роли-владельца, почти
наверное сочтёт это дефектом. Это не дефект — это выбранный заказчиком компромисс; изменения
только через новый ADR (см. «Что нужно от заказчика»).

> **Уточнено `ADR-018` (2026-11-22, ask `c7a6830e-9722-491d-9dbf-c8b291d3e84d`).** Из этого
> ADR меняется ровно один пункт — «миграции идут ролью приложения» (вариант Б в таблице
> «Альтернативы»). Миграции переведены на роль-владельца схемы: ревизии правят таблицы,
> созданные другой ролью, и под ролью приложения такой DDL отказывает (`42501 must be owner
> of table sessions` — реальный сбой деплоя 2026-11-22 на ревизии `0003`). Общий пароль,
> запрет второго DSN-секрета `db_url_owner` и все компенсирующие контроли ниже остаются в
> силе и здесь; меняется только то, кто именно делает DDL. Роль миграций задаётся переменной
> `TBOT_MIGRATION_DB_USER` у сервиса `migrate` (`deploy/compose.yaml`), пароль при этом
> тот же значение секрета `db_url`.

**Касается:** `deploy/postgres/roles.sql`, `packages/storage/base.py` (реестр
`APPEND_ONLY_TABLES`), `migrations/versions/*` (кто создаёт таблицы), `deploy/compose.yaml` и
`deploy/compose.prod.yaml` (секрет `db_url` у сервисов `web`, `engine`, `jobs`, `migrate`),
`deploy/vps/secrets-setup.sh` (`TBOT_DB_USER`), `tests/contract/test_db_roles.py`,
`tests/integration/test_postgres_roles.py`, `docs/runbook/postgres-roles.md`, задача `T-009`,
требование `REQ-identity-04` и критерий `AC-identity-04` (ТЗ §4.1, §8.4).

**Уточняет (не отменяет):**

- **ADR-004** — режимы внесения значений остаются в силе: пароль роли приложения —
  машиногенерируемое значение, его вносит агент скриптом; в `roles.sql` он не появляется (в файле
  прав секретов нет — это проверяет контрактный тест). Право `LOGIN` и пароль роли задаются
  отдельным шагом (`docs/runbook/postgres-roles.md §5`), а не файлом прав.
- **ADR-005** — политика прав файлов секретов не меняется: новых имён в `/etc/tbot/secrets` не
  появляется, набор монтируемых файлов прежний (`db_url` — `640 root:gid10001`).
- **ADR-002** — «быстрый откат» по digest не затрагивается: откат шага переключения не трогает
  данные (`docs/runbook/postgres-roles.md §6`).

## Контекст

Схема идентичности (`0002_identity_access`) и файл прав `deploy/postgres/roles.sql` созданы так,
чтобы журнал `audit_log` был защищён **правами роли**, а не триггером: критерий `AC-identity-04`
требует *находить* изменённую вручную копию дампа по цепочке хэшей, а не делать правку невозможной
внутри базы (обоснование — `docs/runbook/postgres-roles.md §1` про две роли и `§7` про запрет триггера).

Права были созданы и проверены в CI, но до 2026-11-21 приложение ходило ролью-владельцем. Замер
«до» из контейнера `web`, тем же путём к базе, которым ходит процесс (`load_settings()` +
`psycopg_dsn()`):

```
роль: tbot | superuser: True
UPDATE audit_log: РАЗРЕШЁН   DELETE audit_log: РАЗРЕШЁН   TRUNCATE audit_log: РАЗРЕШЁН
```

То есть `REQ-identity-04` на живой площадке не действовал физически: у приложения были права
владельца схемы и суперпользователя кластера, а у владельца `REVOKE` прав не отнимает.

Мешала деталь состава, выясненная замером, а не чтением ТЗ: секрет `db_url` смонтирован
**четырём** сервисам — `web`, `engine`, `jobs` **и `migrate`**, у которого
`command: ["alembic", "upgrade", "head"]` (`deploy/compose.yaml`). Поэтому перевод `db_url` на
роль приложения переводит на неё и миграции. Замер на ВМ под ролью приложения до варианта Б:

```
CREATE TABLE:    SQLSTATE 42501 (permission denied for schema public)
ALTER TABLE audit_log: SQLSTATE 42501
```

Значит первая же ревизия вехи M1 (`T-101…T-106` создают таблицы) на площадке упала бы. Заказчику
были заданы три варианта с ценой (ask `8d2be9bb`); они же разобраны в разделе «Альтернативы» ниже.
Выбран вариант Б и общий пароль.

## Решение

1. **Две роли, один DSN-секрет.** `tbot` — владелец схемы, суперпользователь кластера, приложением
   не используется. `tbot_app` — роль приложения и миграций: без прав кластера
   (`NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOREPLICATION/NOBYPASSRLS`), с `LOGIN` и с паролем,
   **равным значению `db_password`**. Все четыре сервиса берут её из одного секрета `db_url`
   (`TBOT_DB_USER=tbot_app`).
2. **Право `CREATE` на схему `public` выдано роли приложения** (суть варианта Б).
   `REVOKE CREATE ON SCHEMA public FROM PUBLIC` остаётся: право имеет только роль приложения и
   владелец базы, «посторонняя» учётная запись — нет.
3. **Компенсирующие контроли (обязательные, не опциональные):**
   1. **возврат владения** — п. 2.1 `roles.sql` делает `ALTER TABLE <t> OWNER TO CURRENT_USER`
      для каждой таблицы из реестра `APPEND_ONLY_TABLES`; журнал принадлежит владельцу схемы,
      поэтому `REVOKE` работает даже после того, как новую таблицу создало приложение;
   2. **явная выдача прав на журнал** — `GRANT SELECT, INSERT` + `REVOKE UPDATE, DELETE, TRUNCATE,
      REFERENCES, TRIGGER`: выдача не зависит от того, кто стал владельцем таблицы;
   3. **запуск файла прав только ролью-владельцем** — п. 0 `roles.sql` прерывает выполнение под
      `tbot_app` (`RAISE EXCEPTION`), иначе файл вернул бы владение журналу самому приложению;
   4. **цепочка хэшей и `make audit-verify`** (`T-109`) — механизм, который требует ТЗ: подделка
       обнаруживается постфактум, а не предотвращается триггером.
4. **Правило для каждой будущей ревизии с таблицей журнала:** имя в `APPEND_ONLY_TABLES`
   (`packages/storage/base.py`) + `ALTER TABLE … OWNER TO CURRENT_USER` в п. 2.1 + `REVOKE` в п. 4
   + повторный (идемпотентный) запуск `roles.sql` на площадке ролью-владельцем. Контрактный тест
   сверяет перечни внутри файла и реестр, но **не знает** о таблицах, которых ещё нет: пропущенный
   шаг означает «журнал принадлежит приложению, append-only не действует» — это пункт деплой-чека
   (`docs/runbook/postgres-roles.md §3`), а не автотест.
5. **Сознательно не сделано** (и не является недоделкой):
   - отдельный секрет `db_url_owner` для `migrate` и отдельный `db_app_password` — вариант А,
     отклонён заказчиком;
   - право `CREATE` у роли приложения **не** отзывается после миграций: тогда следующая ревизия
     снова упадёт, а «между миграциями» процесс всё равно остался бы с прежним набором прав до
     перезапуска;
   - триггер/политика RLS «запретить правку журнала» — противоречат критерию `AC-identity-04`
     (см. `docs/runbook/postgres-roles.md §7`).
6. **Откат** — `docs/runbook/postgres-roles.md §6`: `ALTER ROLE tbot_app NOLOGIN` + пересборка
   `db_url` с пользователем по умолчанию + `restart` сервисов (не `up -d`: содержимое секрета
   поменялось, а hash конфигурации — нет). Данные не затрагиваются.

## Альтернативы и почему от них отказались

| Вариант | Суть | Цена | Итог |
| --- | --- | --- | --- |
| **А. Второй DSN-секрет** | `db_url_owner` (роль `tbot`) монтируется только в `migrate`, `db_url` — роль приложения; плюс отдельный `db_app_password` | меняется перечень секретов площадки (TZ §14.9, `secrets-setup.sh`), монтирования compose, `scripts/deploy_check.py` и его тесты, контрактный перечень монтируемых файлов (связан с ADR-005); появляется ещё одно машиногенерируемое значение по ADR-004. Цена не ресурсная (машина 2 vCPU / 3.8 ГиБ), а число мест, где значения могут разойтись | отклонён заказчиком (ask `8d2be9bb`) |
| **Б. `CREATE` на схему роли приложения** | миграции идут той же ролью, что и приложение; границу заменяют контроли п. 3 решения | приложение получает право создавать объекты в схеме и становится владельцем новых таблиц; контракт «правок DDL нет» заменён на «DDL — только по своим объектам» | **принят** в части одного пароля и отказе от `db_url_owner`; часть «миграции идут ролью приложения» заменена `ADR-018` |
| **В. Отложить переключение** | права созданы и проверены (они уже созданы), приложение остаётся владельцем схемы до `T-101` | `REQ-identity-04` на площадке не действует неопределённо долго — замер «до» показал, что правки журнала разрешены; просрочка растёт с каждой следующей ревизией | отклонён: это приёмка прав на бумаге |
| Триггер или RLS «запретить правку журнала» | запрет на уровне таблицы, независимо от роли | противоречит `AC-identity-04` (нужно находить подделку копии дампа, а не делать её невозможной в базе); при восстановлении из дампа переносится хуже, чем владение и права | отклонён (`docs/runbook/postgres-roles.md §7`) |
| Отозвать `CREATE` после миграций | право есть только на время `alembic` | следующая ревизия падает ровно так же, как падала бы без права; между перезапусками процесс остаётся с прежним набором прав — сужение иллюзорно | отклонён как неработающий |
| Разные пароли без второго DSN-секрета | `tbot_app` со своим паролем, а `tbot` без права входа | вход владельца нужен файлу прав, миграциям и административным командам; без второго секрета это тот же вариант А в другой формулировке | неприменимо без варианта А |

## Последствия и риски

Что реально измеряется на площадке (замер 2026-11-21, роль приложения, живая база):

| Операция ролью приложения | Результат |
| --- | --- |
| `INSERT` в `audit_log` | проходит, id выдаёт база (прав на последовательность не нужно) |
| `UPDATE` / `DELETE` / `TRUNCATE audit_log` | отказ `SQLSTATE 42501` |
| `ALTER TABLE` / `DROP TABLE` / `CREATE INDEX` / смена владельца по объекту схемы | отказ `42501` |
| `CREATE TABLE` / `ALTER TABLE` / `DROP TABLE` **по своей** таблице | проходит (это и есть миграции) |
| вход под `tbot` (тот же пароль) | **возможен**: значение `db_password` носит и `tbot` (с ним `db_url` работал до переключения), и `tbot_app` (пароль взят из того же файла `/run/secrets/db_password`) |

- **Принятый остаток (главное).** Общий пароль означает: процесс, читающий свой DSN, знает и
  пароль роли-владельца `tbot`, а `tbot` — суперпользователь кластера. Значит отзыв прав — это
  **политика**, а не граница: защита от собственной ошибки приложения (баг, кривой ORM-запрос,
  скрипт «почистить журнал» под ролью приложения) реальна и измерима (`42501`), защита от
  соединения, которое сознательно берет другой пароль из того же секрета, — нет. Обнаружение —
  цепочка хэшей (`make audit-verify`, `T-109`) и аудит `pg_roles`/`pg_stat_activity`.
- **Владение новыми таблицами — у роли приложения.** Все таблицы, которые создадут ревизии M1,
  будут принадлежать `tbot_app`. Это нормально для бизнес-таблиц, но для таблиц журнала обязателен
  пункт 4 решения; иначе `REVOKE` повисает (у владельца права не отзываются).
- **Ротация пароля базы теперь касается двух ролей.** Значение `db_password` носят `tbot` и
  `tbot_app`: ротация = `ALTER ROLE tbot PASSWORD`, `ALTER ROLE tbot_app PASSWORD`, затем
  пересборка `db_url`; значение, зафиксированное в томе `pgdata` при `initdb`, при этом не
  перегенерируется (правило «сначала секрет, потом база»).
- **Цена варианта Б в проверках.** Контракт «приложение не имеет прав DDL» из тестов снят: вместо
  него — «приложение делает DDL только по своим объектам» (`test_postgres_roles.py`,
  `test_приложение_не_правит_чужие_объекты`).
- **Приложение не может выдавать права чужим объектам**: `GRANT` возможен только владельцу, а
  боевой DDL делает `alembic` ревизиями из git, каждая проходит job `миграции`.

- **Что заменил `ADR-018`.** Пункт «Владение новыми таблицами — у роли приложения» больше не
  действует: миграции идут ролью-владельцем схемы, поэтому и новые таблицы принадлежат ей, а
  `tbot_app` получает по ним полный DML через `ALTER DEFAULT PRIVILEGES` (п. 5 файла прав).
  Право `CREATE ON SCHEMA public` у роли приложения отозвано — `roles.sql` делает это явно,
  потому что на площадке право уже было выдано. Граница append-only (п. 4 решения) от этого
  не меняется: `audit_log` по-прежнему не принадлежит роли приложения.
- **Что осталось прежним.** Общий пароль, перечень секретов, режимы ADR-004/ADR-005, контроль
  `42501` на `UPDATE`/`DELETE`/`TRUNCATE audit_log` и вывод «отзыв прав — политика, а не
  граница». `ADR-018` не делает границу строже и не делает её мягче.

## Что нужно от заказчика

Ничего не ожидается: решение принято и применено, блокера нет. ADR нужен, чтобы следующий контекст
не менял модель молча.

Если жёсткая граница всё-таки потребуется — это **отдельное решение и новый ADR** (следующий свободный номер — ADR-009; ADR-007
и ADR-008 заняты счётчиком частоты запросов и выводом CSRF-токена), потому
что меняется не одна строка: перечень секретов площадки (TZ §14.9, `deploy/vps/secrets-setup.sh`),
монтирования в `deploy/compose.yaml`/`compose.prod.yaml` (у `migrate` появляется второй секрет),
проверки `scripts/deploy_check.py` и `tests/unit/test_deploy_check_secrets.py`, контрактные тесты
перечня монтируемых файлов (связаны с политикой `ADR-005`), плюс режим ADR-004 для нового
машиногенерируемого значения `db_app_password` и одновременная ротация `db_password` по пункту
«Ротация» выше. Состав и цена варианта А зафиксированы в разделе «Альтернативы» этого ADR.
