# ADR-003. Боевой контур на рабочей ВМ: деплой через sudo, Caddy без плагинов, HTTP/3, секреты файлами

Статус: принят (решения заказчика от 2026-11-20, ответы на шесть вопросов при разборе `T-713`).

## Контекст

`T-713` (Caddy + TLS на `tbot.rusiksoft.ru`) упёрся в шесть вопросов, которые агент решить не может:
разрешение на деплой живой ВМ, противоречие стоп-листа `AGENTS.md` и `docs/adr/ADR-001`, доступ к
Docker API на площадке, ограничение частоты запросов (в официальном образе Caddy его нет), набор
внешних портов (HTTP/3 и 80/tcp) и размещение секретов. Все шесть получили ответы 2026-11-20;
здесь они зафиксированы, потому что каждое меняет поведение контрактов и прогонов, а не только тексты.

## Решение

1. **Деплой на живую ВМ разрешён.** Репозиторий клонируется в `/opt/tbot` на `153.51.172.30`,
   образы тянутся **по digest** из `deploy/tbot.prod.env` (`docs/runbook/ghcr-pull.md`), сначала
   `migrate`, затем `up -d` (`postgres`, `web`, `caddy` — первый срез; `engine`/`jobs` включаются
   позже, в `paper` и боевом контуре по §14). Порядок зафиксирован в `docs/runbook/stand-deploy.md`.
2. **Стоп-лист `AGENTS.md` приведён к `ADR-001`.** Docker, `80/tcp`, `443/tcp`, `443/udp`, Caddy и
   Let's Encrypt на прод-ВМ разрешены; снят и пункт про «постоянный systemd-юнит туннеля» в том
   виде, в каком он блокировал приёмку `T-714` (юнит `tbot-tunnel` принят площадкой). Под запретом
   остаются: security groups Yandex Cloud (у агента нет `yc init`), изменение `ufw` сверх
   утверждённого набора, удаление томов `pgdata`/`caddy_data` и каталога дампов, ребут ВМ,
   `docker system prune -a`, и всё, что касается узла B (`176.32.39.234`).
   2.1. Отдельное согласование от 2026-11-20 (ask `5087f489`): **ребут ВМ выполнен в окне**
   17:09:54–17:10:55 UTC ради приёмки учений TZ §13.5. Запрет этого пункта на будущее сохраняется:
   каждое согласуется отдельно, молчаливого согласия из выполненного ребута нет.
3. **Доступ к Docker API — через `sudo`.** На площадке `rusiksoft` не состоит в группе `docker`, и
   добавлять его туда нельзя: это эквивалент root-доступа для любой процессной учётки. Все команды
   деплоя — `sudo docker ...` / `sudo docker compose ...`.
4. **Ограничение частоты запросов — на уровне приложения, Caddy остаётся без плагинов.**
   Официальный образ `caddy:2` пинится по digest; образ с плагином (`caddy-security`,
   `cloudflare/caddy-http`) означал бы собственную сборку и потерю публичного digest
   (`docs/runbook/ghcr-pull.md §1`). Формулировка ТЗ §8.3 про «nginx `limit_req`» заменена:
   счётчик `/login`, `/totp` и mutation-эндпоинтов обязателен в приложении (`T-102`, веха M1) и
   обязан брать адрес из `X-Forwarded-For`, который проставляет прокси. Прокси в этой модели держит
   пределы размера и тайм-аутов (`max_header_size 16KB`, `read_header 10s`,
   `request_body max_size 10MB`) и отбивает разведочные методы. Дополнительно `fail2ban`
   (`sshd`) и `ufw` остаются как есть.
5. **Периметр: `443/udp` открывается, `80/tcp` остаётся.** HTTP/3 включается, но по фиксированному
   порядку: сначала `443/udp` в облачной SG (делает только владелец аккаунта), затем правило `ufw`,
   затем `protocols h1 h2 h3` в `deploy/caddy/Caddyfile`. Пока UDP/443 не подтверждён замером
   снаружи, Caddy объявляет только `h1`/`h2`: `Alt-Svc: h3`, которое сеть не пропускает, уводит
   часть клиентов в тайм-аут вместо работающего HTTPS (находка 5 в
   `docs/acceptance/tls-edge.md §4`). `80/tcp` нужен и для редиректа на HTTPS, и для вызовов
   ACME HTTP-01.
6. **Секреты кладёт только заказчик** — скриптом `deploy/vps/secrets-setup.sh`
   (`read -s`, `umask 077`, `root:root 600`, `unset` после записи, без значений в argv и логах).
   Агент значения не запрашивает, не печатает и не передаёт: он проверяет только имена, размеры и
   права через `sudo bash deploy/vps/secrets-setup.sh --check`. Набор файлов: `db_password`,
   `db_url`, `telegram_token`, `telegram_socks_pass` (создан ранее, `T-714`) и `ghcr_token` —
   последний нужен только хосту для `docker login ghcr.io` и в контейнеры не монтируется.
   *Уточнение от 2026-11-20: режимы записи значений (в том числе агентом — машиногенерируемые
   значения и уже существующие у оператора) закреплены `docs/adr/ADR-004-secret-value-placement.md`;
   запрет печатать значения и требование `--check`-видимости остаются в силе.*

## Последствия

- Состав на площадке проверяется двумя независимыми слоями: `docker compose ... config` на самой
  площадке (compose там `2.40.3`, в CI `v5.1.3`) и `scripts/prod_compose_check.py` по разобранной
  JSON-модели. CI не заменяет проверку на ВМ — версии compose различаются.
- `443/udp` без подтверждения снаружи = осознанный временный разрыв: правила `ufw` и артефакты
  (`deploy/vps/ufw.rules`, `firewall.sh`) уже содержат udp, Caddyfile — ещё нет. Контрактный тест
  `test_caddyfile_pinned_tls_headers_and_443` запрещает `h3` ровно до подтверждения; переключение
  обязано быть отдельным коммитом вместе с записью приёма в `docs/acceptance/tls-edge.md`.
- Прикладной счётчик вместо прокси-ограничителя переносит ответственность на приложение: без `T-102`
  публичный вход не принимается по §8.3, и это надо держать в плане вехи M1, а не «потом».
- Ротация digest'ов обязательна: набор в `deploy/tbot.prod.env` обновляется одним коммитом после
  каждого зелёного прогона `Image`, предыдущий набор остаётся в истории как точка отката (§12.7).
