# ADR-019: репозиторий становится публичным; образы GHCR остаются приватными

**Статус:** принят. Решение заказчика от 2026-11-22 (ask `a973b66e-6f4e-4037-8764-8325cf62bcd3`,
вопрос «что делать с видимостью репозитория», ответ заказчика дословно: «Делаем public. Я понимаю
все риски беру ответственность на себя ip сервера это ерунда»). В том же ask заказчик отказался от
сокращения расхода Actions-минут («не чего не делаем») и выбрал отсутствие лимита расхода в
биллинге.

**Касается:** видимости `rusiksoft-afk/tbot` (аккаунт `rusiksoft-afk` — личный, не организация);
гигиены git-истории (`AGENTS.md`); учёта стоимости CI (`docs/HANDOFF.md §5`); `docs/runbook/ghcr-pull.md`
(путь `pull` не меняется).

**Ничего не меняет в:** модели секретов и их размещения (`ADR-004`, `ADR-005`), ролях базы и файла
прав (`ADR-006` в силе кроме пункта, заменённого `ADR-018`), digest-pinning и целях отката
(`ADR-002`), стоп-листе площадки, пороге подавлений (14) и составе CI-проверок.

## Контекст

Цикл тарификации Actions (01.11–30.11) был исчерпан: 2000 из 2000 включённых минут, заказчик
поднял планку до 3000. Замеры этого репозитория за цикл:

| величина | измерено |
|---|---|
| прогонов в цикле | 266 (132 `CI` + 133 `Image`) |
| прогонов на коммитах, меняющих только markdown | 170 (85 коммитов, 64%) |
| job-минут на прогон `CI` | ≈7,6 (тесты 2,7 · dev-стенд 1,3 · миграции 1,2 · lint+typecheck 0,9 · audit 0,5 · разбор площадки 0,4 · gitleaks 0,2 · broker-tls 0,2 · боевой состав 0,2) |
| job-минут на прогон `Image` | ≈3,6 (web 0,9 · engine 1,0 · tgbot 0,9 · jobs 0,8) |
| пара прогонов на один push | ≈11 job-минут |

То есть расход создало число пушей (схема «код → пересъёмка дайджестов → docs» = 3 пуша = 3 пары ≈
33 минуты на срез), а не стоимость проверок: остаток roadmap'а при одном пуше на срез стоил
≈50–70 минут. Заказчик выбрал снять ограничение способом, не требующим изменения конвейера,
— сделать репозиторий публичным.

Для публичных репозиториев GitHub-раннеры на Linux не тарифицируются; тарификация остаётся только
для раннеров под Windows/macOS (в этом проекте их нет) и для кэша свыше квоты плана.

## Решение

1. `rusiksoft-afk/tbot` переведён в `private = false` (`visibility = public`) исполнением
   `PATCH /repos/rusiksoft-afk/tbot` с `private=false`.
2. Пакеты `ghcr.io/rusiksoft-afk/tbot-{web,engine,tgbot,jobs}` **остаются приватными**: перевод
   пакетов в публичную видимость отдельным решением заказчика не принимался, площадка продолжает
   тянуть образы по digest с `ghcr_token` (`runbook ghcr-pull`).
3. Состав и порядок CI-проверок не меняются: тримы (`paths-ignore` в `Image`, `concurrency` у
   `Image`, подмножество job'ов на markdown-коммитах) заказчиком отклонены.

## Предполётный аудит (что проверялось до переключения)

История после публикации не отзываемая: зеркала и форки снимаются в тот же день, поэтому
проверялись все ревизии всех ссылок, а не только голова `main`.

- **Gitleaks в CI** (`job secret-scan`) и так гоняется по всей истории: `actions/checkout` с
  `fetch-depth: 0`, `gitleaks detect --source . --config .gitleaks.toml --redact --exit-code 1`.
  Allowlist в `.gitleaks.toml` узкий и открытый: плейсхолдеры вида `<…>`, слова
  `placeholder`/`canary`/`not-a-real`, синтетические значения фикстур и пять файлов-исключений;
  `regexTarget = "line"`.
- **Отдельный скан по всем 164 ревизиям** (`git grep` по девяти формам: токен Telegram,
  GitHub-токены `ghp_`/`github_pat_`, PEM-блок приватного ключа, DSN с паролем, JWT, AWS/Yandex
  ключи, SOCKS-учётка, `key=value`-присваивания секретов): 163 строки-совпадения, **все** — в
  `tests/unit/test_logging_masking.py` (канарейки проверки маскирования логов: `CANARY_PEM`,
  `CANARY_DB_URL` и т. п.). Вне канареек совпадений 0.
- Единственный PEM в дереве — публичный корневой сертификат (`deploy/ca/ru-trusted-root-ca.pem`).
- `deploy/tbot.prod.env` не содержит ни имён полей секретов, ни значений: значения монтируются
  файлами по `ADR-004`/`ADR-005`.
- **Репозиторных Actions secrets и переменных нет** (списки API пустые): конвейер использует один
  `GITHUB_TOKEN` (`contents: read`, `packages: write`). Значит публикация журналов прогонов не
  раскрывает организационных тайн — раскрывать нечего.
- Синтетические пароли в `ci.yml` и тестах (`ci-only-password`, `ci-stand-db-password`,
  `secretvalue`, `dev-db-password`) остаются в публичном дереве: это пароли одноразовых
  контейнеров тестового стенда, к боевым системам отношения не имеют.
- Issues в репозитории нет; два PR с нейтральными заголовками; `has_wiki = false`,
  `has_pages = false`, репозиторий не форк. Единственная дополнительная ветка на remote —
  `t712-perimeter-secrets`, и она является предком `main` (`git merge-base --is-ancestor` → код 0),
  то есть уникального содержимого не вносит. Тегов `v*` нет.

## Что стало публичным (замерено после переключения)

- `gh api repos/rusiksoft-afk/tbot` → `private = false`, `visibility = public`.
- Анонимный `git ls-remote https://github.com/rusiksoft-afk/tbot.git HEAD` без учётных данных
  отдаёт `401dda0…`; `https://github.com/rusiksoft-afk/tbot` отвечает 200.
- Публичными стали: весь код и тесты, `docs/TZ.md` и протоколы приёмки, `docs/HANDOFF.md` с
  адресами и топологией инфраструктуры — в дереве 98 упоминаний прод-ВМ `153.51.172.30`, 19 —
  узла B `176.32.39.234`, 26 — пользователя `rusiksoft`, 12 — имени файла деплой-ключа, 10 —
  `id` инстанса, 10 — hostname, 61 — домена; публичны также журналы и артефакты всех прогонов и
  вся история из 164 коммитов.
- **Образы публичными не стали.** Проверено зондом анонимного токена GHCR с контролем на заведомо
  публичных образах:

  | репозиторий образа | анонимный `GET /token?scope=repository:…:pull` |
  |---|---|
  | `home-assistant/home-assistant` (контроль) | 200 |
  | `actions/actions-runner` (контроль) | 200 |
  | `rusiksoft-afk/tbot-web` | 401 |
  | `rusiksoft-afk/tbot-jobs` | 401 |

  То есть публикация исходников не опубликовала слои образа: исходный код внутри образа анонимно
  не скачивается, `pull` по-прежнему требует `ghcr_token`, поведение площадки не изменилось.

## Следствия, которые нужно держать в голове

1. **Значение секрета, попавшее в git, считается скомпрометированным в тот же момент** — публичные
   репозитории сканируются ботами за секунды. `secret-scan` остаётся жёстким гейтом, подавлять его
   нельзя; при обнаружении значения в истории ротация обязательна и немедленна (режимы —
   `ADR-004`).
2. **Журналы прогонов и артефакты публичны.** В них и так нет боевых значений (пункт про пустые
   Actions secrets выше), но правило «не печатать значения в stdout» теперь действует для
   посторонних наблюдателей тоже.
3. **PR из форков получают минуты GitHub-раннера** без секретов и с `contents: read` — код чужих
   форков исполняется на раннере. Экономического риска нет (минуты бесплатны), остаётся риск
   «бесплатного вычислительного ресурса» и ожидания очереди; закрывается настройкой репозитория
   «require approval for pull requests from first-time contributors» — это действие оператора в
   UI, не изменение `.github/workflows`.
4. **Учёт минут теряет смысл как бюджетный лимит**, но остаётся как оценка длительности: пара
   прогонов ≈11 job-минут, markdown-коммит стоил столько же, сколько кодовый. Дисциплина «один пуш
   на срез» остаётся полезной просто потому, что ускоряет цикл проверки.
5. **Карта инфраструктуры в документах — принятое решение заказчика**, а не недоделка: править
   `HANDOFF §5` и ранбуки «ради секретности» без отдельного запроса нельзя — по этим текстам
   следующая сессия сверяет площадку, и обескровленные тексты стоят дороже, чем раскрытие IP
   (формулировка заказчика: «ip сервера это ерунда»).
6. **`tests/contract/test_no_forbidden_references.py` превращается из внутреннего правила в
   публичный щит**: упоминаний стороннего сервиса-аналога не должно быть ни в коде, ни в markdown —
   теперь это видно снаружи, тест обходит все `.md`, `.py`, `.yaml`, `.toml`.

## Что после переключения противоречит тексту техзадания

`docs/TZ.md` и `docs/tz/*` — контракт с заказчиком, без запроса они не правятся, поэтому
расхождение фиксируется здесь и в `docs/HANDOFF.md §4` (вопрос о поправке). Противоречат
публичной видимости: шапка `docs/TZ.md` («**Репозиторий:** приватный `rusiksoft-afk/tbot`»),
строка таблицы «Репозиторий | Только приватные репозитории `rusiksoft-afk`; никаких упоминаний
сторонних облачных ботов», строка «CI/CD | GitHub Actions (приватный репозиторий) + GHCR для
образов» и `docs/tz/15-boundaries-and-compliance.md` («Все репозитории приватные; доступ — только
необходимые сотрудники; включена 2FA на GitHub»). Вторая половина последней цитаты важна именно
теперь: при публичном репозитории 2FA аккаунта и запрет прямого push в `main` (защита ветки +
обязательный CI) — единственные контроли, которые держат поставку кода; заказчику это задано
отдельным вопросом.

Поправлен `README.md`: он называл проект «приватный monorepo» и утверждал «Код не начат; фаза
спецификации», что к этой дате неверно (развёрнут `web` + Caddy + PostgreSQL, схема `0004`) и
стало витриной проекта для постороннего читателя.

## Отклонённые варианты

- **Остаться приватным и ужать расход** (один пуш на срез + `paths-ignore` на несборочные пути у
  `Image` + `concurrency … cancel-in-progress` у `Image`): ≈300 минут в месяц без изменения состава
  проверок; отклонено заказчиком в том же ask.
- **Отдельный витринный публичный репозиторий** без TZ, приёмки, адресов и топологии, с контрактом
  на запрет прод-деталей: отклонено.
- **Self-hosted-раннер** (минуты GitHub не расходуются вообще): отклонено — требует отдельного
  Linux-бокса (набор проверок зависит от POSIX-прав, `docker compose` и сервиса Postgres; прод-ВМ
  2 vCPU под тяжёлые прогоны запрещена, узел B в стоп-листе) и переносит `GITHUB_TOKEN` и
  репозиторные секреты на ещё одну машину.

## Как проверить состояние сейчас

```bash
gh api repos/rusiksoft-afk/tbot --jq '{private, visibility}'
GIT_TERMINAL_PROMPT=0 git -c credential.helper= ls-remote https://github.com/rusiksoft-afk/tbot.git HEAD
for r in home-assistant/home-assistant rusiksoft-afk/tbot-web; do
  curl -s -o /dev/null -w '%{http_code} ' \
    "https://ghcr.io/token?service=ghcr.io&scope=repository:$r:pull"
done   # ожидается 200 (контроль) и 401 (наш образ: пакет приватный)
```

## Исполнение решений заказчика (второй ask от 2026-11-22)

Ответы на ask `1dc0e2a8-b664-458e-ab28-6b8b06be17fb` (три вопроса — поправка ТЗ, контроли
поставки кода, ротация учётных данных):

1. **ТЗ исправлено с явной пометкой** (выбран вариант «поправить с пометкой об
   изменении»). Исправлены четыре места: шапка `docs/TZ.md`, строки «Репозиторий» и
   «CI/CD» таблицы стека §2, `docs/tz/15-boundaries-and-compliance.md` §15.4; под шапкой
   ТЗ — пометка к редакции 1.0 со списком правленых мест и указанием, что требование
   «приватный» заменено более жёстким контролем секретов, а не отменено. Прочие секции
   ТЗ не тронуты, `tasks/todo.md` не тронут.
2. **Контроль поставки кода: только 2FA.** Защита ветки `main` (обязательные
   статус-проверки, запрет force-push) и одобрение PR от новых участников НЕ вводятся:
   заказчик выбрал `only_2FA`, а ранее по расходам Actions сказал «не чего не делаем».
   Следствие для рабочих процессов: `push` в `main` остаётся прямым, PR-процесс не
   вводится. Включает 2FA только заказчик в UI аккаунта; измерить состояние агенту не
   удалось — `gh api user` для `rusiksoft-afk` (id `261177050`) вернул
   `two_factor_authentication: null`, то есть для личного аккаунта это поле недоступно.
   Требование ТЗ §15.4 о 2FA остаётся открытым до подтверждения заказчика
   (`docs/HANDOFF.md §4`).
3. **Ротация — всем составом.** Выполнено агентом (машиногенерируемое, `ADR-004` режим 2):
   `db_password` + пересобранный `db_url` (с применением к обеим ролям — `tbot_app` и
   `tbot`-мигратору) и SSH deploy-ключ клона (новый read-only, старый отозван).
   Осталось за заказчиком (режим 1 `ADR-004`): `telegram_token` и `ghcr_token`.
   Процедура и замеры — `docs/runbook/secret-rotation.md`, состояние —
   `docs/HANDOFF.md §1.50`.

**Что этот ADR не разрешает:** не тронутая видимость пакетов GHCR (см. § «Открытые
вопросы» ниже), несжатый состав CI (запрет на тримы остаётся в силе), отсутствие
защиты ветки — то есть история коммитов в `main` правится только ordinary push'ем без
гейта, и `secret-scan` в `main` — единственный фильтр, который ловит секрет уже после
того, как он попал в публичную историю.

## Открытые вопросы, порождённые этим решением

Записаны в `docs/HANDOFF.md §4`: (а) — **закрыт частично**: `db_password`/`db_url` и
деплой-ключ SSH ротированы 2026-11-22, `telegram_token` и `ghcr_token` ждут заказчика
(`runbook secret-rotation §5`); (б) — **закрыт отказом**: одобрение PR от новых
участников не вводится (решение `only_2FA`); (в) — остаётся открытым: делать ли пакеты
GHCR публичными и снимается ли тогда `ghcr_token` с ВМ. Плюс открытый вопрос о правах
каталога `/etc/tbot/keys` (`700 root:tbot` против `700 root:root` в `runbook kek-keys §4`).
