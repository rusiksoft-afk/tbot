# ADR-005: права файлов секретов на хосте — доступ по группе контейнера

**Статус:** принят агентом 2026-11-20 как единственный выполнимый вариант; **ждёт подтверждения
заказчика** (правка TZ §14.9 wording — см. «Что нужно от заказчика»).
**Касается:** `/etc/tbot/secrets` (права и владелец файлов), `deploy/vps/secrets-setup.sh`,
`deploy/compose.prod.yaml`, `deploy/Dockerfile`, TZ §14.9, T-712/T-713,
`docs/runbook/secrets-on-host.md`, `docs/runbook/stand-deploy.md`.
**Уточняет (не отменяет):** ADR-004 — режимы внесения значений остаются в силе, меняется только
политика прав на записанные файлы.

## Контекст

Первый боковой запуск первого среза (2026-11-20, ВМ `153.51.172.30`): `postgres` поднялся и стал
`healthy`, а `docker compose … run --rm migrate` упал с

```
PermissionError: [Errno 13] Permission denied: '/run/secrets/db_url'
migrate_exit=1
```

при полностью зелёном `secrets-setup.sh --check` (5 файлов, все `600 root:root`, все по форме) и
зелёном разборе состава (`config --quiet`, `prod_compose_check.py` → 13/13 «ГОТОВО»).

Замеры на той же площадке, которые объясняют причину:

1. `docker compose -f … run --rm probe` с `-c 'id; ls -l /run/secrets/; test -r …'` на образе
   `tbot-web` по digest: внутри контейнера `uid=10001(tbot) gid=10001(tbot)`, а секрет примонтирован
   как `-rw------- 1 root root` → `VERDICT=NOT_READABLE`. Причина: `deploy/Dockerfile` заканчивается
   `USER 10001:10001` (_hardening из TZ §14.6_), а bind-маунт файлового секрета приносит на хостовые
   права, ничего не копируя.
2. Попытка задать доступ на стороне compose отклоняется парсером: `secrets.<имя>.uid/gid/mode`
   в compose **2.40.3** (версия площадки) →
   `validating …: secrets.db_url additional properties 'uid', 'gid', 'mode' not allowed`.
3. Копия `db_url` с правами `640` и группой `10001` в том же механизме монтирования даёт
   `VERDICT=READABLE`. Одновременно замер хоста: `getent group 10001` и `getent passwd 10001` пусты
   — учётной записи с таким uid/gid на хосте нет.

То есть буквальное сочетание требований TZ («файлы секретов — `600 root:root`» + «процессы без root,
секреты через файлы») на этой площадке невыполнимо: контейнер физически не может прочитать свой
секрет. CI этого не поймал, потому что в dev-стенде файлы секретов создаёт пользователь runner
(права «свои», читаемые), а `prod-config` job проверяет скрипт ввода, а не читаемость изнутри
контейнера.

## Решение

1. **Два класса файлов в `/etc/tbot/secrets`:**
   - **монтируемые составом** (`db_password`, `db_url`, `telegram_token`, `telegram_socks_pass`) —
     `640`, владелец `root`, группа — числовой `gid` процесса контейнера (`10001`);
   - **читаемые только хозяйственным инструментом** (`ghcr_token`: его читает `docker login
     --password-stdin` под root, в контейнеры он не монтируется) — `600 root:root`.
   Каталог остаётся `700 root:root`.
2. **Права ставит скрипт, а не оператор.** В `secrets-setup.sh` появляется `CONTAINER_GID=10001`,
   `HOST_READ_ONLY_NAMES=(ghcr_token)`, `MOUNTED_NAMES=(…)` и `apply_policy`; `write_file` больше не
   содержит «вечного» `chmod 600`. `--check` сверяет режим и `uid:gid` **числами** (`stat -c
   '%u:%g'`), потому что имени у группы на хосте может не быть.
3. **`--remed`** — отдельный режим: приводит владельца и режим существующих файлов, **не читая и не
   перезаписывая значения**. Это единственный безопасный способ перевести живую площадку на новую
   политику: пароль базы уже осел в томе `pgdata` при `initdb` (перегенерация = новый том и потеря
   данных), а внешние токены по ADR-004 при повторном вводе считаются скомпрометированными.
4. **Группа на хосте.** `ensure_container_group` создаёт группу `tbot` с `gid 10001`, если gid
   свободен; если занят — работает числовым gid (имя нужно только для читаемого `ls`).
5. **Контракт.** `tests/contract/test_vps_artifacts.py`: `CONTAINER_GID` обязан совпадать с числовой
   `USER` из `deploy/Dockerfile`; `MOUNTED_NAMES` обязан совпадать с набором файлов, которые
   монтирует `deploy/compose.prod.yaml`; `HOST_READ_ONLY_NAMES` = «имена скрипта минус монтируемые»;
   `--remed` не имеет права касаться содержимого файлов. В CI-прогоне (`prod-config`) добавлены
   проба «600 у монтируемого секрета — это ошибка прав» и прогон `--remed` со сверкой контрольных
   сумм содержимого.

## Последствия и риски

- Файлы монтируемых секретов становятся читаемыми для любой учётной записи с gid `10001`. На хосте
  такой учётной записи нет (замер `getent`), а созданная группа `tbot` не имеет пароля, не является
  логином и в состав какой-либо пользователя не добавляется. «Мир» не читает ничего, имена файлов
  по-прежнему скрыты каталогом `700`.
- Смена `USER` в образе потребует синхронно поменять `CONTAINER_GID` — иначе падает контрактный
  тест, а не живая площадка.
- Откат: вернуть `600 root:root` (значения останутся прежними), но боевой состав с таким откатом не
  стартует — откат имеет смысл только вместе с возвратом к схеме «секрет в env», которая запрещена
  TZ §14.6 и ADR-003.
- Задача **T-715** (в `tasks/todo.md`): проба читаемости секрета изнутри контейнера в CI. Настоящий
  дефект обнаружен только на площадке; офлайн-контракт проверяет согласованность чисел, но не факт,
  что процесс под uid 10001 читает файл.

## Что нужно от заказчика

Подтвердить формулировку TZ §14.9: вместо «`600 root:root`» — «права по ADR-005: `640 root:gid
контейнера` для файлов, которые compose монтирует в контейнер, `600 root:root` для файлов, которые
читает только хозяйственный инструмент». До подтверждения правка в TZ помечена как уточнение агента;
если заказчик требует остаться на `600 root:root`, единственный корректный путь — менять образы
(точка входа от root с последующим `setpriv`/`gosu`), что противоречит текущему hardening-профилю
TZ §14.6 и требует отдельного решения.
