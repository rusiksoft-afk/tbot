# ADR-024 — согласование схемы источника с правым элементом `X-Forwarded-Proto`

Дата: 2026-11-23. Статус: принят (задача `T-117`; найден на площадке при первом запуске после
завода первой учётной записи — срез `T-112`, `docs/adr/ADR-023-first-admin-bootstrap.md`).

## Контекст

Браузерный `POST https://tbot.rusiksoft.ru/login` возвращал `403`
`{"status":"forbidden","detail":"запрос отклонён"}` — отказ по проверке источника из `ADR-008`.
Замер на площадке (`docs/acceptance/prod-deploy-t112-first-account.md §8`): пять событий
`csrf_rejected path=/login detail="Origin='https://tbot.rusiksoft.ru'"` с
`2026-11-23T03:17:48.880597Z` по `2026-11-23T03:21:01.777692Z`.

Причина:

1. `_request_origin` в `apps/web/security/csrf.py` строил ожидаемый источник из ASGI-области
   запроса, то есть из `request.url.scheme`.
2. ASGI-схему правит `uvicorn` из `X-Forwarded-Proto`, но только когда пир соединения входит в
   `forwarded_allow_ips`; значение по умолчанию — `127.0.0.1`, а пирем является контейнер `caddy`
   (общая сеть `tbot_tbot-public`, подсеть `172.28.4.0/24`, адреса выдаются динамически). Значит
   ASGI-схема оставалась `http`.
3. `deploy/caddy/Caddyfile` заголовок ставит корректно (`header_up X-Forwarded-Proto {scheme}`), но
   приложение его не читает.

Дифференциальные пробы с наружного контура (пустая форма, чтобы не трогать учётную запись):

| Что послано | Код | Смысл |
| --- | --- | --- |
| `Origin: https://tbot.rusiksoft.ru` | `403`, 63 б | браузерный случай — отказ по источнику |
| `Origin: http://tbot.rusiksoft.ru` | `400`, 881 б | источник совпал с ASGI-схемой → дошёл до разбора формы |
| без `Origin` | `400`, 881 б | дальше решает `Sec-Fetch-Site`, его тоже нет → тоже форма |

Дефект не был виден раньше по трём причинам: в стенде разработки job `compose-smoke` не поднимает
`caddy` (проверка идёт внутрь контейнера `web` по `http://127.0.0.1:8080`), оффлайн-проверки веб-слоя
строят клиент на базе `https://testserver` (`tests/integration/web_support.py` — это осознанно, из-за
`Secure`-куки), и до завода `T-112` в базе не было ни одной учётной записи, поэтому ни одна
аутентифицированная браузерная мутация в бою не выполнялась.

## Рассматриваемые варианты

1. **Доверять `X-Forwarded-Proto` пиру прокси** — `forwarded_allow_ips` в `uvicorn.run`
   (`apps/web/main.py`). Отклонён: чтобы список не разъезжался, нужно фиксировать IPAM сети
   `tbot_tbot-public` (адреса `caddy` сейчас динамические). Кроме того `uvicorn`
   (`ProxyHeadersMiddleware`) меняет не только схему: при включённом доверии он выводит адрес
   клиента из `X-Forwarded-For`, то есть появляется второй путь трактовки адреса клиента, а он
   определяет идентификатор сессии и ключи счётчика частоты запросов (`ADR-007`, `ADR-009`).
   Правило «правый элемент добавляет наш прокси» пришлось бы дублировать в двух местах и
   сверять их между собой.
2. **Сравнивать только хост и порт, игнорируя схему.** Отклонён: это ослабляет принятый контур
   `ADR-008` и лишает его смысла ровно в том сценарии, ради которого он введён — смешанная
   http/https-среда и редирект `http → https` (замер: `http://IP/invite?token=…` даёт `308`,
   `docs/acceptance/prod-firewall.md §5`).
3. **Разобрать `X-Forwarded-Proto` в приложении по тому же правилу, что уже принят для адреса** —
   принят.

## Решение

Разбор `X-Forwarded-Proto` живёт в `apps/web/security/clients.py` — там же, где уже живёт единственная
точка разбора `X-Forwarded-For` (`ADR-007`):

- берётся **правый** элемент списка: его дописал наш прокси, левые элементы прислал клиент и они
  подделываемы;
- регистр не значим, вебсокетная пара `ws`/`wss` приводуется к `http`/`https`, потому что значение
  сравнивается с `Origin`;
- неизвестное или пустое значение даёт `None`, а не отказ: вызывающий остаётся на честной ASGI-схеме,
  и по испорченному заголовку нельзя ни получить доступ, ни устроить отказ в обслуживании;
- `apps/web/security/csrf.py` использует полученную схему так:
  `scheme = forwarded_scheme(request) or request.url.scheme`.

Сравнение источника (`ADR-008`) остаётся двухслойным и не ослабляется: `Sec-Fetch-Site: cross-site`
по-прежнему даёт отказ, несовпадение хоста даёт отказ, токен CSRF остаётся обязательным — проверка
источника была и остаётся вторым слоем, а не заменой токена.

## Последствия

- **Что держит безопасность.** Правый элемент дописывает наш `caddy`: в `Caddyfile`
  `X-Forwarded-Proto` ставится через `header_up`, то есть значение от клиента перезаписывается до
  того, как дойдёт до приложения. Инвариант «`web` наружу не публикуется» уже проверяется контрактными
  тестами деплой-артефактов (`ADR-011`) и ранбуками; при его нарушении правый элемент перестал бы
  быть доверенным — ровно как в `ADR-007` про адрес. Дополнительная компенсация: даже при полностью
  подставленном заголовке запрос обязан принести валидный CSRF-токен сессии.
- **Что меняется в поведении.** Все мутации (`/login`, `/logout`, `/mfa-enroll/*`, `/invite`,
  раздел администрирования) за TLS-терминатором начинают видеть наружную схему. До починки это был
  не «неудобный вход», а полное закрытие входа из браузера для любой учётной записи.
- **Где схема используется.** Кроме `csrf.py` схема в веб-слое не нужна: маршруты строят редиректы
  по относительным путям, журнал несёт только `path`. То есть решение точечное.
- **Что не делается в этом срезе.** `forwarded_allow_ips` не включается, IPAM сети `tbot_tbot-public`
  не фиксируется, `deploy/caddy/Caddyfile` не меняется. Отдельный кандидат в будущие срезы —
  прогон через `caddy` в job `compose-smoke` (сейчас там `postgres web engine jobs`, и класс дефектов
  «цепочка TLS-терминатор → приложение» в CI не покрыт); сделан не был, чтобы не расширять CI в
  срезе с дефектом.
- **Проверка.** Оффлайн-проверки — `tests/integration/test_web_csrf.py`, раздел «схема источника за
  TLS-терминатором»: браузерный `Origin` + `X-Forwarded-Proto: https` на клиенте с ASGI-схемой `http`
  даёт `400` (форма), а не `403`; отсутствие заголовка сохраняет `403`; правый элемент списка,
  регистр, `wss`, мусорное значение и `https://host:443` разобраны параметрически; чужой
  `Sec-Fetch-Site` и несовпадение хоста остаются `403`. Приёмка в бою — после деплоя через реальный
  контур, `docs/acceptance/prod-deploy-t112-first-account.md §9`.
