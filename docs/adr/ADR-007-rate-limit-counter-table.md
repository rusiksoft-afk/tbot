# ADR-007: прикладной счётчик частоты запросов живёт отдельной таблицей схемы

**Статус:** принят (решение заказчика от 2026-11-21, ask `fe0b025e` — «своя таблица счётчика»).
Схема реализована: `rate_buckets` в ревизии `0003_rate_counters` (проверки — офлайн-контракт
`tests/contract/test_rate_limits_schema.py` и живая база
`tests/integration/test_rate_buckets_db.py`). Не реализовано и входит во второй срез `T-102`: сам
механизм лимитов в `apps/web` (области, инкремент, отказ с `429`), регламент фоновой чистки старых
окон и `X-Forwarded-For` как источник адреса. Ревизия на площадку ещё не применялась (деплой
отложен тем же решением заказчика) — при следующем деплое обязателен `$COMPOSE run --rm migrate`. **Опасность этого ADR в том, чтобы счётчик молча переселили обратно в память
процесса**: память дешевле, но она не переживает рестарт контейнера и не согласуется между
процессами, а §8.3 требует счётчик на уровне приложения.

**Касается:** `migrations/versions/0003_rate_counters.py`, `packages/storage/models.py`
(`RateBucket`, `RATE_SCOPES`), `apps/web/security/` (второй срез `T-102`),
`tests/contract/test_rate_limits_schema.py`, `tests/integration/test_rate_buckets_db.py`,
`.github/workflows/ci.yml` (job `migrations`), `docs/HANDOFF.md §4`, задача `T-102`,
требование `REQ-security-02` (ТЗ §8.3).

**Связан с:** **ADR-003** — он убрал «nginx `limit_req`» и зафиксировал, что у официального образа
Caddy встроенного ограничения частоты запросов нет, а образ с плагином мы не собираемся (иначе
теряется публичный digest). После этого требования §8.3 про лимиты стало исполняемым только в
приложении. **ADR-006** — права роли приложения: `rate_buckets` не входит в реестр
`APPEND_ONLY_TABLES` и не требует правок `deploy/postgres/roles.sql`.

## Контекст

ТЗ §8.3 задаёт четыре лимита и прямо говорит, где их держать:

> `Rate limit: /login — 10 запросов/мин/IP, /totp — 10/мин/сессия и 5/мин/IP, все
> mutation-эндпоинты — 60/мин/пользователь. Счётчик обязателен на уровне приложения (T-102, веха
> M1) … Прикладной счётчик от этого не отменяется: адрес клиента он обязан брать из
> `X-Forwarded-For`, проставленного прокси (наружу `web` не публикуется).`

В §4.1 (модель данных) таблицы для таких счётчиков нет. Варианты размещения обсуждались в
`docs/HANDOFF.md §4` и сводились к трём: своя таблица, память процесса, отдельный Redis. Важные
факты площадки: процессов веб-уровня несколько (`web`, позже API-маршруты), рестарт контейнера
обычен (в том числе из-за смены digest'ов при деплое), `web` не публикуется наружу и получает
адрес клиента только из `X-Forwarded-For`.

Память процесса даёт ровно те дыры, против которых лимиты и написаны: после `docker restart`
счётчик обнуляется, а лимит «по IP» не действует для запросов, попавших в другой процесс. Для
`/login` это значит, что перебор паролей (уже ограниченный блокировкой учётной записи из `T-101`)
получает второй, более слабый контур — и он же остаётся единственным контуром против перебора
TOTP-кода по IP (`T-103`).

## Решение

Одна таблица счётчика, окно фиксированной длительности, одна строка на
(область, субъект, начало окна):

```
rate_buckets(
    scope          TEXT        NOT NULL,          -- закрытый перечень областей
    bucket_key     TEXT        NOT NULL,          -- субъект: IP из X-Forwarded-For (канонический
                                                  -- текст) либо строка UUID сессии/пользователя
    window_start   TIMESTAMPTZ NOT NULL,          -- начало окна, выровненное приложением
    window_seconds SMALLINT    NOT NULL,          -- длительность окна; для §8.3 всегда 60
    attempts       INTEGER     NOT NULL DEFAULT 0,
    CONSTRAINT pk_rate_buckets PRIMARY KEY (scope, bucket_key, window_start)
)
```

- **Области (`scope`) — закрытый перечень из четырёх значений** (`RATE_SCOPES`
  в `packages/storage/models.py`, он же питает CHECK): `login_ip` (10/мин/IP),
  `totp_session` (10/мин/сессия), `totp_ip` (5/мин/IP), `mutation_user` (60/мин/пользователь).
  Новые значения — только ревизией, молча «добавить область» нельзя: иначе список перестанет
  соответствовать перечню §8.3.
- **`window_seconds` ограничен значением `60`** — ровно тем, что требует §8.3. Пятиминутное окно
  из §8.2 («3 неудачные попытки с одного IP за 5 минут → временный бан IP») сознательно **не**
  заводится заранее: см. «Что нужно от заказчика».
- **PK составной**, суррогатный `id` (UUIDv7) отсутствует намеренно: у счётчика нет жизни вне
  ключа, а составной PK одновременно и уникален, и индексен для точечного поиска. Порядок
  колонок PK соответствует единственному запросу слоя входа: «счётчик по области, субъекту и
  текущему окну».
- **Внешних ключей нет** — тоже намеренно. `ON DELETE RESTRICT` (общее правило схемы для
  идентификаторов и доступа) привязал бы счётчики к строкам `users`/`sessions`: удаление
  пользователя упиралось бы в его же счётчики, а счётчики обязаны умирать по возрасту, а не по
  воле каскада. Целостность субъекта здесь не нужна: это операционные данные с короткой жизнью.
- **Индекс `ix_rate_buckets_window_start`** — под чистку: строки старше нескольких окон не нужны
  никому, их удаляет фоновый процесс (`jobs`), иначе таблица растёт всё время работы площадки.
  Регламент чистки входит во второй срез `T-102`, порог хранения — заметно дольше самого окна.
- **Права**: отдельного `GRANT` по `rate_buckets` в `deploy/postgres/roles.sql` не появляется —
  и на обоих путях это безопасно по разным основаниям. На площадке таблицу создаёт миграция, то
  есть роль приложения (`ADR-006`, вариант Б): она и есть владелец. В CI и на dev-базе таблицы
  создаёт роль-владелец `tbot`, а доступ приложению даёт уже существующая строка файла прав
  (`GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO tbot_app`), которая
  применяется после миграций. Что у роли приложения есть `SELECT`/`INSERT`/`UPDATE`/`DELETE` на
  счётчик — проверяется на живой базе (`tests/integration/test_rate_buckets_db.py`), потому что
  случайный `REVOKE UPDATE` или попадание таблицы в реестр append-only дали бы `42501` на первом
  же запросе `/login` и выяснилось бы это на площадке. Счётчик **не** входит в
  `APPEND_ONLY_TABLES`: журнал — неизменяемые записи, а счётчик по своей природе `UPDATE`-ется.
  Проверка формата `token_hash` из §8.3 (`0003` добавляет CHECK `token_hash ~ '^[0-9a-f]{64}$'`)
  живёт в той же ревизии по решению заказчика (ask `fe0b025e`: «в ближайшую новую ревизию»), чтобы
  не гнать отдельную миграцию ради одной проверки.

## Альтернативы и почему от них отказались

| Вариант | Суть | Почему не выбран |
| --- | --- | --- |
| Память процесса (dict/TTL) | Без схемы, без миграций, дешевле всего | Обнуляется при рестарте контейнера и не согласуется между процессами: лимит «10/мин/IP» перестаёт быть лимитом по IP. Дешевизна ценой невыполнимости требования §8.3. |
| Redis отдельным сервисом | Готовый TTL-счётчик, атомарные инкременты | Новый сервис в составе (TZ §14), новый секрет, бэкапы, мониторинг, образ; на ВМ 2 vCPU / 3.8 ГиБ это ещё один контейнер. Несоразмерно четырём счётчикам в минуту. |
| Счётчик в Caddy | Правило `rate_limit` у обратного прокси | Официальный образ Caddy встроенного ограничения частоты запросов не имеет (ADR-003), образ с плагином ломает публичный digest и процедуру `ghcr-pull`. Плюс §8.3 требует прикладной уровень и `X-Forwarded-For` от прокси. |
| Счётчик в `audit_log` | Уже есть таблица записей, писать «попытки» туда | Журнал append-only по правам (ADR-006), в нём нет быстрых агрегатов по окну и он не предназначен для `UPDATE`; смешение аудита и операционного состояния ломает обе таблицы. |
| Таблица с UUIDv7-PK и FK на `users`/`sessions` | Единый стиль PK со всеми таблицами проекта | FK с `RESTRICT` привязывает короткие по жизни счётчики к учётным записям и сессиям; суррогатный ключ не даёт никаких преимуществ при точечном поиске по трём колонкам. |
| Redis-подобное хранилище в Postgres (`pg_cron`/UNLOGGED) | Быстрая временная таблица без WAL | `UNLOGGED` теряет счётчик после аварийного рестарта Postgres — ровно та же дыра, что и память процесса; `pg_cron` — новое расширение на площадке. |

## Последствия и риски

- **Каждый лимитируемый запрос стоит запись в базу** (`INSERT … ON CONFLICT DO UPDATE`). На
  `web` это один дополнительный запрос на mutation-эндпоинт и на `/login`/`totp`; для текущих
  объёмов площадки (2 vCPU, 60 соединений) это приемлемо, но в Layers защиты это надо учитывать:
  лимит сам становится источником нагрузки. Второй срез `T-102` обязан писать счётчик один раз на
  запрос и не должен делать это на статике и `GET` вне лимитируемых путей.
- **Счётчик видит только то, что видит приложение.** Обход `web` (прямое обращение к другому
  сервису) мимо счётчика — отдельная тема периметра: наружу публикуется только Caddy, `web`
  наружу не публикуется (`ADR-003`), так что обход возможен только с самой машины.
- **Размер таблицы растёт между чистками.** При 4 областях и активном переборе это тысячи строк в
  час; индекс по `window_start` делает чистку дешёвой, но чистка обязана быть реализована — иначе
  «временные» строки остаются навсегда. Это часть второго среза `T-102`, а не опция.
- **`X-Forwarded-For` как источник адреса.** Заголовок проставляет наш же Caddy, `web` наружу не
  публикуется; если это утверждение когда-нибудь нарушится, счётчик по IP станет тривиально
  обходимым подделкой заголовка. Проверка «`web` не публикуется наружу» уже входит в контрактные
  тесты деплой-артефактов.
- **Пять минут и «бан IP» из §8.2 в этой таблице пока не хранятся.** Это осознанно: см. ниже.

## Что нужно от заказчика

Открытым остаётся только место исполнения §8.2: «3 неудачные попытки с одного IP за 5 минут →
временный бан IP (nginx/fail2ban)». Механизм, названный в этой фразе, в нашем стеке не работает:
nginx заменён на Caddy (ADR-003), а у Caddy встроенного ограничения частоты нет. Нужен вердикт,
кто держит бан: (а) приложение (та же таблица, окно 300 секунд, отказ во входе до истечения
срока), (б) `fail2ban` на хосте по логам приложения (тогда нужен jail и формат логов с адресом из
`X-Forwarded-For`), или (в) и то и другое. Пока ответа нет, в схеме остаётся окно `60` секунд, и
пятиминутный счётчик не заводится: расширять CHECK «на всякий случай» незачем.
