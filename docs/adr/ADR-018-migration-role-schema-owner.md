# ADR-018: миграции идут ролью-владельцем схемы; роль приложения права CREATE на схему не получает

**Статус:** принят. Решение заказчика от 2026-11-22 (ask `c7a6830e-9722-491d-9dbf-c8b291d3e84d`,
вопрос 1 «миграции 0003 падает на владении таблицами», выбранный вариант — «миграции идут
отдельной ролью-владельцем схемы, приложение остаётся ограниченной ролью времени выполнения»).

**Отменяет (в одном пункте):** `ADR-006` п. 2 и вариант «Б» там же — право `CREATE ON SCHEMA
public` у `tbot_app` и исполнение ревизий этой ролью. Остальное в `ADR-006` (общий пароль
`db_password`, отказ от второго DSN-секрета `db_url_owner`, компенсирующие контроли
append-only, guard запуска файла прав) остаётся в силе.

**Касается:** `deploy/compose.yaml` (сервис `migrate`), `migrations/env.py`,
`packages/common/config.py` (`migration_db_user`), `packages/common/db.py` (`migration_url`),
`deploy/postgres/roles.sql` (п. 2), `tests/contract/test_db_roles.py`,
`tests/integration/test_postgres_roles.py`, `docs/runbook/postgres-roles.md`, `AGENTS.md`,
приёмка `docs/acceptance/t-009-identity-schema.md` (§3.2.3).

## Контекст

Деплой среза `T-106` на живую ВМ остановился на шаге миграций:

```
sqlalchemy.exc.ProgrammingError: (psycopg.errors.InsufficientPrivilege)
  must be owner of table sessions
[SQL: ALTER TABLE sessions ADD CONSTRAINT ck_sessions_token_hash_format
       CHECK (token_hash ~ '^[0-9a-f]{64}$')]
```

Замер на площадке (тот же срез): все 10 таблиц схемы `public` — `app_meta`, `users`, `sessions`,
`totp_enrollments`, `totp_failures`, `backup_codes`, `ip_allowlist`, `invitations`, `audit_log`,
`alembic_version` — принадлежат роли `tbot`, а `migrate` соединяется ролью `tbot_app`. Причина не
случайна: `0001` и `0002` применялись в 2026-11-20, пока состав ходил ролью `tbot`; переключение
`migrate` на роль приложения (`ADR-006`, ask `8d2be9bb`) состоялось 2026-11-21, уже после создания
таблиц. `GRANT USAGE, CREATE ON SCHEMA public TO tbot_app` даёт право создавать новые объекты, но
не даёт прав на чужие: `ALTER TABLE` требует владения объектом.

То же ограничение бьёт по `0004` (`ALTER TABLE totp_enrollments ADD COLUMN last_used_step`) и по
следующей схеме `T-105` (правки `users`, `invitations`). То есть вариант Б `ADR-006` working
только для ревизий, которые создают таблицы, и отказывает на ревизиях, которые правят таблицы,
созданные до переключения ролей.

Ранее, 2026-11-21, тот же механизм дал другой сбой: без права `CREATE` первая же ревизия M1
падала с `42501 permission denied for schema public` (замер в `ADR-006`). Выбор тогда стоял между
«выдать приложению CREATE» и «ввести второй DSN-секрет»; выбран был первый.

## Решение

1. **Роль миграций — роль-владелец схемы (`tbot` на площадке).** `migrate` получает переменную
   `TBOT_MIGRATION_DB_USER` со значением `tbot` в `deploy/compose.yaml`; `migrations/env.py` строит адрес через
   `packages.common.db.migration_url(dsn, settings.migration_db_user)`, которая подменяет **имя
   пользователя** в DSN, сохраняя пароль из того же секрета `db_url`.
2. **Права приложения не расширяются, а сужаются.** Пункт 2 `roles.sql`:
   `GRANT USAGE ON SCHEMA public TO tbot_app` + `REVOKE CREATE ON SCHEMA public FROM tbot_app`.
   Отзыв именно явный: файл прав обязан приводить площадку к модели, а право `CREATE` на этой
   площадке уже выдано. Рантайм-роль получает `USAGE` и полный DML (п. 1 и п. 5), но не DDL.
3. **Секретов не добавляется.** Имя роли — не секрет: оно живёт в `deploy/compose.yaml`, нового
   файла в `/etc/tbot/secrets` нет, `ADR-004` не затрагивается, ротация `db_password` не
   требуется. Second DSN-секрет `db_url_owner` (вариант А `ADR-006`) по-прежнему запрещён.
4. **Порядок шагов на площадке зафиксирован:** `миграции` → `roles.sql` (роль-владелец) →
   приложение. П. 5 `roles.sql` (`ALTER DEFAULT PRIVILEGES`) настроен от роли `tbot`, поэтому
   таблицы, созданные миграциями, сразу получают `SELECT/INSERT/UPDATE/DELETE` для `tbot_app`;
   п. 2.1 возвращает владение таблицами журнала владельцу. Обратный порядок означает окно, в
   котором приложение не видит новую таблицу.
5. **Контроль ролей усиливается, а не снимается:** у `tbot_app` не остаётся никакого DDL в схеме —
   ни по чужим объектам (`42501`), ни по своим (нет права `CREATE`). Проверка
   `test_приложение_создаёт_таблицы_для_миграций` заменена на
   `test_приложение_не_делает_ddl_в_схеме`; контракт по файлу прав проверяет и выдачу `USAGE`, и
   явный отзыв `CREATE`, и отсутствие `GRANT ... CREATE ... ON SCHEMA`.

## Альтернативы и почему от них отказались

| Вариант | Суть | Цена | Итог |
| --- | --- | --- | --- |
| **А. Отдать владение бизнес-таблицами роли `tbot_app`** | `ALTER TABLE … OWNER TO tbot_app` по всем таблицам, кроме журнала | приложение получает `ALTER`/`DROP`/`TRUNCATE` по своим таблицам, `REVOKE` по ним не работает; границу append-only приходится держать точечно по каждой новой таблице журнала; ровно то, что `ADR-006` назван опасностью | отклонён заказчиком (вопрос 1, ask `c7a6830e`) |
| **Б. Временная передача владения под каждую ревизию** | перед `migrate` сменить владельца, после — вернуть | ручной шаг в каждом деплое, окно расширенных прав, ошибка шага = база в половинчатом состоянии | отклонено: тактика вместо модели |
| **В. Второй DSN-секрет `db_url_owner`** | вариант А из `ADR-006` | новый секрет (режим по `ADR-004`, монтирование, `deploy_check.py`, контрактные перечни), ротация `db_password`; при этом граница не появляется: пароль-то общий, процесс знает пароль владельца из `db_url` | отклонено и ранее, и сейчас |
| **Г. Отозвать `CREATE` после миграций** | право есть только на время `alembic` | отказ повторяется на ревизиях, правящих чужие таблицы; окно между запусками не сужается | отклонено (`ADR-006`), остаётся отклонённым |
| **Д. Роль миграций = владелец схемы (принят)** | `TBOT_MIGRATION_DB_USER=tbot`, пароль тот же | `migrate` — привилегированный процесс: он умеет менять схему и права. Он по-прежнему в профиле `tools` (не в постоянном контуре), не монтирует KEK и токены, а DSN лежит в файле с `640 root:gid10001`; граница «приложение не правит журнал» от этого не меняется | **принято** |

## Последствия и риски

- **Что измеряется на площадке после изменения:**

  | Операция | Роль | Результат |
  | --- | --- | --- |
  | `ALTER TABLE sessions ADD CONSTRAINT …` (`0003`) | `tbot_app` (до) | отказ `42501` (замер 2026-11-22) |
  | `alembic upgrade head` | `tbot` | проходит |
  | `CREATE TABLE` в `public` | `tbot_app` | отказ `42501` (после отзыва) |
  | `SELECT/INSERT/UPDATE/DELETE` по `rate_buckets` | `tbot_app` | проходит (п. 5 файла прав) |
  | `UPDATE/DELETE/TRUNCATE audit_log` | `tbot_app` | отказ `42501` |

- **Роль миграций шире, чем роль приложения.** Это осознанный выбор: процесс миграции обязан
  иметь DDL, иначе ревизии не применяются. Ограничение — операционное: `migrate` существует
  только в профиле `tools` (`deploy/compose.prod.yaml`), запускается человеком из `make migrate`
  или CI, не принимает сетевого трафика и не видит KEK/токены.
- **Риск неправильного порядка.** Если после ревизии не запустить `roles.sql`, новая таблица
  журнала окажется владеетелем приложения и `REVOKE` по ней не сработает. Это пункт деплой-чека
  (`docs/runbook/postgres-roles.md §3`), а не автотест: контрактные тесты не знают о таблицах,
  которых ещё нет.
- **Приёмка `ADR-006` не переписывается.** `docs/acceptance/t-009-identity-schema.md §3.4–3.5` остаётся замерной историей: там зафиксировано и то, что `CREATE` был выдан, и то, что до этого он отказывал. Новый замер 2026-11-22 (`CREATE` отозван, `alembic` под ролью-владельцем проходит) — в протоколе деплоя среза `T-106` и в указателе на него в §3.7 того же документа.
- **CI-проверка остаётся в силе**, но перестаёт быть доказательством: job `миграции` исполняет
  `alembic upgrade head` под ролью `tbot` и после изменения — это ровно та же роль, что на
  площадке, поэтому совпадение теперь настоящее, а не случайное.
