# ADR-008: CSRF-токен выводится из сессии (HMAC), а не повторяет значение куки

**Статус:** принят (решение заказчика от 2026-11-21, ask `fe0b025e` — «отдельный токен, выводимый
из сессии (HMAC)»). Реализация — второй срез `T-102` в `apps/web` (обязательная проверка
`test_csrf_required`, ТЗ §8.8). **Опасность этого ADR в том, чтобы «токен сессии» из §8.3 молча
реализовали как значение куки в скрытом поле**: это буквально соответствует формулировке ТЗ, но
обесценивает `HttpOnly`, то есть ломает ровно ту защиту, ради которой токен и нужен.

**Касается:** `apps/web/security/csrf.py` (второй срез `T-102`), `apps/web/security/sessions.py`
(чтение значения куки и идентичности сессии), шаблоны форм и подключение HTMX
(`hx-headers`/`<meta name="csrf-token">`), `tests/contract/test_sessions_contract.py`, будущий
`tests/contract/test_csrf_contract.py`, задача `T-102`, требование `REQ-security-02`
(ТЗ §8.3, §8.8, §9).

**Связан с:** **ADR-006** — из него следует, что приложение не хранит «ключ подписи» отдельно:
материал сессии (значение куки) известен процессу `web` ровно в том объёме, в каком он нужен для
поиска сессии по хэшу. **ADR-007** — лимиты частоты не относятся к проверке CSRF, но оба механизма
включаются на одном middleware.

## Контекст

ТЗ §8.3 формулирует CSRF одной строкой:

> `CSRF: токен сессии во всех mutation-запросах (в т.ч. HTMX: заголовок X-CSRF-Token), проверка
> origin; SameSite=Lax как второй слой.`

Матрица §8.8 требует проверку: запрос мутации без токена → `403`. Кука сессии при этом обязана
быть `HttpOnly`, её значение — 256 случайных бит, и в базе лежит только его SHA-256
(`T-102`, `sessions.token_hash`). Значение куки нигде не отображается: страница «мои устройства»
намеренно показывает только `id`, времена, шаг входа, IP и user-agent — никакого материала сессии
(проверяет контрактный тест).

Буквальное прочтение «токен сессии» = «значение куки» упирается в то, что заголовок
`X-CSRF-Token` для HTMX подставляет JavaScript, а JavaScript не видит `HttpOnly`-куку. Значит,
чтобы дослать буквально «токен сессии», её значение придётся напечатать в HTML. Тогда любой XSS
получает одновременно и CSRF-токен, и материал сессии: `HttpOnly` перестаёт что-либо защищать, и
украденного HTML достаточно для входа с чужой сессией. Это не гипотетика: §8.3 отдельным пунктом
требует `autoescape=true` везде и запрет `|safe`, то есть XSS considered.

## Решение

Токен выводится из пары (значение куки, идентификатор сессии) и **нигде не хранится**:

```
ключ      = HMAC-SHA256(key=b"tbot-csrf-v1", msg=<байты значения куки>)
токен     = base64url(HMAC-SHA256(key=ключ, msg=<строка id сессии>))   # 32 байта → 43 символа
```

- **`HttpOnly` сохраняет смысл.** Значение куки остаётся только в куке: в HTML попадает
  производный токен, по которому значение куки не восстанавливается (ключ не выводится наружу,
  HMAC необратим). XSS, получивший страницу, получает токен — но он и так мог бы слать запросы от
  имени пользователя; CSRF-токен защищает от запросов с **чужого** источника, где ни куки, ни
  токена нет.
- **Токен не хранится в базе и не имеет колонки.** Он выводится на лету из того, что процесс `web`
  уже знает: куки (нужна для поиска сессии по `token_hash`) и `sessions.id`. Проверяется сравнением
  `hmac.compare_digest` — обычное `==` здесь оставляет тайминг-канал.
- **Смена сессии автоматически меняет токен.** `rotate_session` (смена пароля, подключение токена,
  запуск в `production`) создаёт новую строку `sessions` с новым `id`, и старый токен перестаёт
  подходить сам, без отдельного «пересчёта CSRF». Это же закрывает §8.3 «критичные действия —
  сессия пересоздаётся» со стороны токена.
- **Имя версии входа в вывод (`tbot-csrf-v1`) зафиксировано в константе.** Сменить способ
  вывода — значит поменять константу и получить 403 на всех старых страницах; это ожидаемо и
  лечится перезагрузкой страницы, а не миграцией.
- **Перенос:** скрытое поле `csrf_token` в формах и `<meta name="csrf-token">` для
  `hx-headers="{'X-CSRF-Token': …}"` (HTMX). Значение — base64url без «=», поэтому экранирование
  Jinja2 (`autoescape=true`) его не портит и `|safe` не нужен.
- **Проверка:** на все `POST`/`PUT`/`PATCH`/`DELETE` (и на `GET`-эндпоинты с побочным эффектом их
  быть не должно), плюс проверка `Origin`/`Sec-Fetch-Site` и `SameSite=Lax` как второй слой
  (§8.3). Отказ — `403` без подробностей: по какому именно признаку отклонён запрос, странице
  незачем знать.
- **Токен — секрет уровня сессии:** не попадает в URL (мутации — только телом/заголовком), не
  попадает в `Referer` (в §8.3 уже стоит `Referrer-Policy: same-origin`), не попадает в логи
  запросов и в `audit_log` (тип записи о неудачной проверке — `AUTH_*`, но значение токена туда
  писать нельзя — это материал аутентификации).

## Альтернативы и почему от них отказались

| Вариант | Суть | Почему не выбран |
| --- | --- | --- |
| Буквально: значение куки в скрытом поле | Точное следование формулировке §8.3 | `HttpOnly` обесценивается: XSS получает материал сессии вместе с токеном. Экономит одну строчку кода ценой защиты, ради которой кука и made `HttpOnly`. |
| Двойная отправка (CSRF-кука + сверка с полем) | Отдельная не-`HttpOnly` кука с тем же значением, что и в поле | Требует вторую куку и второй материал сессии в браузере; поддоменную область и срок жизни надо настраивать отдельно, а выигрыш против HMAC-вывода — нулевой. |
| Синхронизатор: случайный токен, сохранённый в сессии | Случайное значение в колонке `sessions.csrf_token` | Новая колонка (и ревизия) ради состояния, которое выводимо из уже имеющегося материала; плюс токен лежит в дампе базы, то есть в дампе появляется ещё один секрет. |
| Только `SameSite=Lax` + проверка origin, без токена | Минимум кода | Противоречит §8.3 и матрице §8.8 («без токена → 403»); `Lax` не защищает от мутаций, прилетевших как навигация с формой, и не помогает в браузерах, где `SameSite` трактуется мягко. |
| Подпись на общем секретном ключе процесса (не связанном с сессией) | Ключ в секрете площадки, токен = HMAC(id сессии) | Один скомпрометированный ключ позволяет подписать токены для любых сессий сразу всех пользователей; вывод от значения куки не даёт такого «корня» и не требует нового секрета в `/etc/tbot/secrets`. |
| Токен в URL (`?csrf=…`) | Просто работает с HTMX без заголовков | Секрет утекает в `Referer` (пусть `same-origin` и смягчает), в историю браузера и в логи доступа Caddy. |

## Последствия и риски

- **Токен живёт ровно столько, сколько страница.** Долго висящая вкладка с формой после
  пересоздания сессии (смена пароля в другой вкладке) даст `403`. Это корректное поведение, но UI
  обязан объяснить его понятным сообщением, а не «внутренняя ошибка» — это часть среза `apps/web`
  (§9: внятные состояния, страница `/session-expired`).
- **Проверка токена обязана быть на всех мутациях, включая HTMX.** Типовая дыра этого дизайна —
  забыть эндпоинт, который принимает `X-CSRF-Token`, но не принимает поле формы. Второй срез
  `T-102` обязан покрыть это таблицей маршрутов в тесте: каждый мутационный маршрут без токена
  обязан дать `403`.
- **Вывод токена требует значения куки в момент рендеринга.** Это так и есть в middleware, который
  ищет сессию; но если когда-нибудь рендеринг формы уедет в процесс, где кука не читается (например
  генерация письма со ссылкой), вывод токена там невозможен — такие ссылки обязаны быть
  одноразовыми со своим TTL, как в §8.3 про файлы отчётов, а не «формой без CSRF».
- **HMAC-пары «ключ → сообщение» хватает, но это не KDF общего назначения.** Использованы два
  HMAC-SHA256 со строкой версии вместо `HKDF` (в Python 3.12, на котором собран образ, `hashlib.hkdf`
  нет). Для одного производного значения этого достаточно; если производных значений станет больше
  (например, отдельный ключ для шифрования токенов в §8.4), выводить надо уже через HKDF и отдельным
  решением, а не «по аналогии».
- **Матрица §8.8 «смена пароля отзывает сессии» получает второй смысл:** после смены пароля
  меняется и CSRF-токен, и материал сессии. Юнит-проверка этого уже есть (`T-102`, первый срез),
  интеграционная появится вместе с маршрутом смены пароля.

## Что нужно от заказчика

Открытых вопросов нет: вывод токена и способ переноса (`X-CSRF-Token` + скрытое поле `csrf_token`)
соответствуют §8.3, имена зафиксированы формулировками ТЗ. Если потребуется менять способ вывода
(например, перейти на HKDF или добавить время жизни токена), это делается новым ADR — поведение
для уже открытых страниц при этом меняется с «работает» на «403 до перезагрузки».
