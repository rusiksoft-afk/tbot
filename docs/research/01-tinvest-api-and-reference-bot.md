# Исследование: T‑Invest API (Т‑Банк) и референсный облачный бот

Дата: 2026-11-19. Источник фактов — официальная документация developer.tbank.ru/invest
(140 страниц, скачаны локально), репозиторий официального Python SDK
`opensource.tbank.ru/invest/invest-python` (project 238), страница и форум
референсного облачного бота (функциональные требования, не код).
Все числа и константы ниже — из документации, пересказаны своими словами.

## 1. Контур и протоколы

| Контур | gRPC | REST | WebSocket |
|---|---|---|---|
| Бой | `invest-public-api.tbank.ru:443` | `https://invest-public-api.tbank.ru/rest/tinkoff.public.invest.api.contract.v1.<Service>/<Method>` | `wss://invest-public-api.tbank.ru/ws/...` |
| Песочница | `sandbox-invest-public-api.tbank.ru:443` | `https://sandbox-invest-public-api.tbank.ru/rest/...` | аналогично |

Разделы API (сервисы): `UsersService`, `InstrumentsService`, `MarketDataService`,
`OrdersService`, `StopOrdersService`, `OperationsService`, `SandboxService`,
`SignalService`, плюс стримы `MarketDataStreamService`, `OrdersStreamService`,
`OperationsStreamService`.

Сервисы доступны и в gRPC, и в REST (кроме части отчётов — только gRPC).
REST отвечает теми же кодами: 400/401/403/404/408/415/429/500/501/503/504.

## 2. Лимиты (страница «Лимиты»)

Рекомендация брокера: суммарно не более **50 запросов/с** от робота; жёсткий
потолок по IP — **1000 запросов/мин**, свыше — бан. Лимитная политика
распространяется на все счета/токены пользователя.

Unary-лимиты (запросов в минуту на сервис):

| Сервис/метод | Лимит |
|---|---|
| Инструменты (суммарно) | 200 |
| Методы Bonds/Shares/Options/Futures/Etfs/GetAssets | 15 |
| Счета (Users) | 100 |
| Операции | 200 (формирование отчётов — 5) |
| Котировки (MarketData) | 600 |
| Стоп-ордера | 50 |
| Песочница | 200 |
| Ордера (суммарно) | 100 |
| Сигналы | 100 |
| Автоследование | 100 |
| `GetHistory` (REST) | 30 |
| `GetOrders` | 200 |
| `PostOrder` | 15/с (900/мин) |
| `CancelOrder` | 300 |
| `ReplaceOrder` | 300 |
| `PostOrderAsync` | 600 |
| `GetStopOrders` | 60 |

Стримы: котировки — 32 соединения, ордера — 16 на тип, операции — 11 на тип.
В одном стриме котировок — до **300 подписок** суммарно (свечи+стакан+лента),
подписка/отписка — не более **100 запросов/мин**. Счётчик стримов обновляется
раз в 2 минуты. Лимита на число активных заявок нет.

Троттлинг доставки в стримах: orderbook и свечи — 1 сообщение за 100 мс на
подписку; trades, last price, info — без ограничений.

## 3. Исторические данные (GetCandles)

Интервалы: 5с, 10с, 30с, 1, 2, 3, 5, 10, 15, 30 мин, 1, 2, 4 часа, неделя, месяц, день.
`limit` и максимальная глубина зависят от интервала: 1 мин — 2400 свечей на
запрос, диапазон «от 1 мин до 1 дня»; день — 2400, «от 1 дня до 6 лет»;
5с — 2500 и только последние 200 минут; месяц — 120 и до 10 лет.
Есть `candleSourceType`: все / только биржевые / с учётом торговли по выходным.
Оценка загрузки: 5 лет минутных свечей по одному инструменту ≈ 93 тыс. свечей ≈
39 запросов; при лимите 600/мин 200 инструментов загружаются за ~15 минут
с учётом пауз.

Есть серверный `GetTechAnalysis`: BB, EMA, RSI, MACD, SMA на интервалах от
1 мин до 1 месяца (по инструменту и диапазону дат) — можно использовать как
кросс-чек собственных индикаторов, но основной расчёт выгоднее вести локально.

## 4. Заявки (OrdersService)

`PostOrder` / `PostOrderAsync` / `ReplaceOrder` / `CancelOrder` / `GetOrders` /
`GetOrderState` / `GetOrderPrice` / `GetMaxLots`.

Поля `PostOrder`: `quantity` (в лотах), `price` (Quotation: units+nano),
`direction` (BUY/SELL), `accountId`, `orderType` (LIMIT/MARKET/BESTPRICE),
`orderId` — клиентский ключ идемпотентности в формате UID (≤36 симв.),
`instrumentId` (figi | instrument_uid | ticker_classCode),
`timeInForce` (DAY / FILL_AND_KILL / FILL_OR_KILL; FOK недоступен на срочном
рынке и в торговлю по выходным), `priceType` (POINT для фьючерсов и облигаций,
CURRENCY), `confirmMarginTrade` (по умолчанию false — согласие на непокрытую
позицию).

Ключевое различие имён: `PostOrderRequest.order_id` — клиентский ключ,
`PostOrderResponse.order_id` — биржевый номер,
`PostOrderResponse.order_request_id` — возвращённый клиентский ключ. Сверка
статуса: `GetOrderState(order_id, order_id_type=ORDER_ID_TYPE_REQUEST|EXCHANGE)`.

Стоп-заявки: `price`, `stopPrice`, `direction`, `expirationType`
(GOOD_TILL_CANCEL / GOOD_TILL_DATE + `expireDate`), `stopOrderType`
(TAKE_PROFIT / STOP_LOSS / STOP_LIMIT), `instrumentId`, `quantity`; отдельные
`GetStopOrders`, `CancelStopOrder`.

## 5. Токены и безопасность доступа

Виды токенов: read-only, full-access, transfer-access, токен с доступом к
одному счёту, sandbox-токен (к обычным методам не применяется — ошибка).
Токен выпускается только на https://www.tbank.ru/ в настройках Т‑Инвестиции,
показывается один раз, **срок жизни — 3 месяца**. Требуется отключённая функция
«Подтверждение сделок кодом». Сделки свыше 30 000 000 ₽ через API недоступны.
Для Инвесткопилки, «Счёта под ключ» и смарт-счетов токен на конкретный счёт
не выпускается. Токен передаётся в metadata каждого unary-запроса и в
стрим-соединениях.

TLS: сертификат выпускает НУЦ Минцифры; типовая ошибка валидации лечится
установкой корневого сертификата Минцифры либо (в официальном Python SDK)
переменной окружения `SSL_TBANK_VERIFY=True` — SDK поставляет сертификат в
пакете. Для Docker это обязательный пункт сборки образа.

## 6. Официальный Python SDK

Пакет `t-tech-investments` (v1.51.0, Apache-2.0, requires-python >=3.8) из
индекса `https://opensource.tbank.ru/api/v4/projects/238/packages/pypi/simple`;
репозиторий `opensource.tbank.ru/invest/invest-python`, зависимости: grpcio,
protobuf, cachetools. Импорты: `from t_tech.invest.grpc import Client,
AsyncClient, SandboxClient, AsyncSandboxClient`, request-модели из
`t_tech.invest.grpc.schemas`, финансовые конвертеры `quotation_to_decimal`,
`decimal_to_quotation`, `money_to_decimal`, `decimal_to_money` из
`t_tech.invest.utils`. Старые импорты `tinkoff.invest` и модуль
`t_tech.invest.services` — устарели. Сервисы доступны как атрибуты:
`users`, `instruments`, `market_data`, `market_data_stream`, `operations`,
`operations_stream`, `orders`, `orders_stream`, `stop_orders`, `sandbox`,
`signals`. Примеры: асинхронные стримы, загрузка всей истории свечей,
асинхронная выставка заявок, ретраи, автотесты.

Соседние альтернативы: `tinvest` 3.0.5 (community, py>=3.8,<4.0, github
daxartio/tinvest) — запасной вариант; `tinkoff-invest` 1.0.5 — легаси REST v1,
не использовать.

## 7. Правила безопасной торговой программы (резюме требований к архитектуре)

Поток данных: рыночные данные → стратегия → структурированное торговое
намерение → детерминированный RiskManager → подтверждение режима/параметров →
OrderExecutor → API. Стратегия не вызывает выставку заявки напрямую.

Обязательные проверки перед заявкой: явные режим (sandbox/production) и счёт;
однозначно найденный инструмент; разрешающий торговый статус; известные размер
лота и шаг цены; цена, нормализованная по шагу; количество в лотах > 0;
доступные средства/позиция; лимиты одной заявки, позиции и дневного убытка;
сохранённый до сетевого вызова ключ идемпотентности; отсутствие токена в логах.

Расчёты только через `Decimal`, деньги и цены не через `float`. Даты —
timezone-aware UTC. Не смешивать `figi` / `instrument_uid` / `ticker_classCode`.
Read-only запросы можно ретраить с backoff; мутации — только после сверки по
сохранённому ключу (таймаут не доказывает отказ в приёме). Аварийное завершение:
остановить сигналы, закрыть стримы, сохранить состояние для сверки. Отмена
заявок и закрытие позиций — разные операции. Песочница ≠ бэктест и не
доказывает доходность.

## 8. Референсный облачный бот (функциональные ориентиры)

Из публичного описания и инструкции (8+ тыс. комментариев в теме форума, ~10
лет на рынке, подписка $/мес, не зависит от оборота):

- Алгоритм «таблица макро-ордеров»: series лимитных заявок вниз от последней
  цены (Long) или вверх (Short); каждый следующий уровень дешевле/дороже на шаг
  и больше по объёму на множитель мартингейла; исполненные объёмы объединяются
  в единый «фикс-ордер» с целевой прибылью.
- «Подтяжка» таблицы: если цена ушла от таблицы на заданную величину (параметр
  или 2× шага), таблица переносится ближе к последней цене, пока нет исполнения.
- Защита от пампов/дампов: пауза создания/подтяжки таблицы при сильном движении
  (технический анализ, например RSI-коридоры вида «0–80», «20–100»).
- Long/Short; прибыль копится во второй валюте инструмента.
- Разбиение объёма (аналог iceberg), ручная корректировка комиссий, шаблоны
  пресетов в JSON, статистика и экспорт в CSV, уведомления в Telegram по chat id.
- Облачная multi-tenant модель: у каждого пользователя свои API-ключи, свой
  веб-доступ, работа 24/7, обновление «в фоне».
- Отдельная секция про безопасность ключей, ограничения прав ключа (info/trade),
  защиту от повторного воспроизведения запросов (nonce) на биржах с таким механизмом.

Перенос на MOEX/Т-Банк: «пара» → инструмент (лоты, шаг цены), «фикс-ордер» →
совокупная позиция со средней ценой и целевой прибылью, short на споте →
маржинальная сделка (`confirmMarginTrade=true`, ГО/СО, риск-отслеживание),
нет 24/7 → торговые расписания и статусы сессий, комиссии API не отдаёт →
ручная настройка тарифа/комиссии.

## 9. Что API НЕ даёт (значит это в ТЗ отдельным пунктом)

- Размеров комиссий пользователя: `GetUserTariff` отдаёт тарифные лимиты,
  комиссии задаются вручную в настройках стратегии (как в референсе).
- Расчёт налогов: брокер — налоговый агент, бот считает только свою оценку P&L.
- Гарантий исполнения лимитной заявки, очередей в стакане, точной задержки до
  биржи (публичный API через интернет: десятки–сотни мс). HFT/кололокация — вне
  области применения.
- Прямой поддержки «уровней мартингейла»: это уровень нашей стратегии.
- Песочница не эмулирует ликвидность и проскальзывание.

## 10. Тестовый сервер (данные из прошлого замера, 2026-11-18)

`192.168.1.40`, host `test`, Ubuntu 24.04.1 LTS, 4 ядра, RAM 2.9 ГБ,
диск 19 ГБ (~13 ГБ свободно), Docker 29.1.3 + compose v2, Node 18. Доступ по
SSH (`rusiksoft`). Годится для разработки и демонстрации (Postgres + 2–3
контейнера), тесен для массовой загрузки истории и бэктестов на сотни
инструментов.
