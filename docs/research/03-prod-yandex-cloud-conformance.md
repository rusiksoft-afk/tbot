## 3.4 Критический блок: Telegram из этой площадки частично недоступен

Замеры с ВМ (443 TCP connect):

| Хост/IP | Результат |
|---|---|
| `api.telegram.org` → `149.154.166.110` | **FAIL** (таймаут) |
| `api1/api2/api4.telegram.org`, `149.154.175.53`, `185.76.151.115` | **FAIL** |
| `149.154.167.220:443` | **OK** |
| IPv6 `2001:67c:4e8:f004::9` (легальный адрес `api.telegram.org`) | «Network is unreachable» — у ВМ нет внешнего IPv6 |
| Для сравнения: с домашней машины `api.telegram.org` | отвечает (HTTP 404 на `/`, 1.0 с) |
| `github.com`, `ghcr.io` | OK |

Правила на хосте (OUTPUT ACCEPT) этому не причиной — блокировка на уровне сети/провайдера или
на стороне Telegram для части диапазонов AS200350. **Требование «Telegram-бот» в текущем виде
на этой площадке не выполняется**: имя `api.telegram.org` приводит к IP, до которого нет пути,
а рабочий IP (`149.154.167.220`) не является тем, что возвращает DNS.

Варианты решения (задача **T-710**, нужно решение заказчика):

| Вариант | Суть | Плюсы | Минусы/риски |
|---|---|---|---|
| **A. Закрепление рабочего DC-IP** | в HTTP-клиенте бота явно указывать `api.telegram.org` → `149.154.167.220` (или несколько IP с health-check), TLS-SNI сохраняется | быстро, ничего не ставим | Telegram может менять состав адресов; нужен автоматический прощуп всех DC-IP и алерт; «костыль» против DNS |
| **B. Второй узел для `tgbot`** | процесс `tgbot` живёт на хосте, где Telegram доступен (домашний сервер/другая ВПС), к БД/очереди команд обращается по VPN-туннелю | надёжно, изоляция Telegram-процесса от прода | нужна стабильная VPN-связь (WireGuard), усложнение эксплуатации; ПДн уходят за пределы прода (согласовать) |
| **C. Наш исходящий прокси** | на отдельной ВПС (где Telegram доступен) поднять SOCKS5/HTTP-прокс с mTLS и пускать `tgbot` только через него | гибко, контроль | ещё один узел и юрисдикция; прокси видит Telegram-трафик (нужен mTLS + allowlist целей) |
| **D. Резервный канал уведомлений** | основной — e-mail/вебхук в другой мессенджер; Telegram остаётся «где работает» | не зависит от блокировки | требование «полное управление из Telegram» не выполняется |

Рекомендация: **A + B как постоянная схема**: A — для работы сразу (с автоматическим
выбором работающего DC-IP и алертом), B — как отказоустойчивый вариант, если Telegram
зачистит и эти адреса. D добавить как дублирование критичных алертов (S1/S2).
Решение фиксируется ADR, потому что меняет состав процессов и egress-политику (TZ §8.5).

приложения (TZ §8.5) поверх сетевой доступности.

## 3.6 Разность «есть / нужно» по мощностям

Целевой масштаб (TZ §1.5): 3 пользователя, ≤15 стратегий, ≤100 подписок.
Расчёт TZ §14.3 даёт: 4 vCPU / 8 ГБ / 100 ГБ NVMe. Текущая ВМ — **2 vCPU / 3.8 ГБ / 72 ГБ**:
это конфигурация «минимальная» из TZ §14.4.

Последствия текущей конфигурации:
- Postgres `shared_buffers` придётся держать ≤512 МБ, бэктест-воркер — 1, историческую
  ретенцию минутных свечей — не более ~9–12 месяцев;
- при одновременной загрузке истории + работе стратегий + веб-запросах вероятен uptime-риск
  из-за нехватки RAM (сейчас swap нет вообще);
- диск 72 ГБ выдержит 24 месяца истории + дампы с запасом, но без запаса на несколько
  локальных бэкапов и Parquet-архив.

Что предлагается (задача **T-011**):
1. Немедленно: добавить swap 4 ГБ (страховка от OOM при первых бэктестах) и настроить
   `vm.swappiness=10`.
2. До M3: увеличить конфигурацию до 4 vCPU / 8 ГБ (Yandex Cloud меняет конфигурацию
   остановленной ВМ; место на диске можно расширить отдельно, online, с `growpart`+`resize2fs`).
3. Бэкапы — на отдельный диск или объектное хранилище (не на тот же диск), шифрование до
   выгрузки (TZ §8.4).

### 3.7.1 Уточнение после вопроса заказчика: не контейнер, а туннель-egress (схема C′)

Вопрос заказчика: «зачем на `176.32.39.234` контейнер, если там уже есть ВПН-инфраструктура».
Ответ: контейнер и не обязателен. Правильнее использовать этот узел как **туннельный egress**
для процесса `tgbot`, живущего на проде:

```
tgbot (прод) → socks5h://127.0.0.1:10800 (локальный SOCKS клиента Xray на проде)
             → Shadowsocks 2022 (AES-256-GCM) over WebSocket/TLS → rusiksoft.ru:443
             → вход Xray на узле B (127.0.0.1:10800, тег in-10800-tcpudp)
             → явный outbound узла B → api.telegram.org
```

Почему это лучше варианта «контейнер на B» в нашем случае:
- исходящие узла B и его цепочка **уже доказанно** ходят в заблокированные сервисы — то есть
  путь к Telegram там заведомо есть, тогда как у «прямого» выхода узла B доступность Telegram
  не проверена (см. таблицу выше);
- не нужен SSH-доступ и размещение нашего кода на чужом узле: от узла B требуется только
  отдельный вход с своим путём и правилом фронта;
- прод **не обязан** принимать входящие: прод → B:443 работает уже сегодня (замер 21 мс),
  значит канал Telegram открывается до правок групп безопасности;
- ключ туннеля по сети не передаётся, TLS до `api.telegram.org` остаётся сквозным.

**Что уже сделано заказчиком (2026-11-19) и что это требует от нас:** на узле B создан вход
`in-10800-tcpudp`: `shadowsocks`, метод `2022-blake3-aes-256-gcm`, `listen 127.0.0.1:10800`,
транспорт `ws`, `security: none`, `sniffing: off`, `network: tcp,udp`. Замер с прод-ВМ показал
две вещи:
1. **Фронт:** `https://rusiksoft.ru/` → `200` (маска, 17228 Б), `/ws` → `404` (маска-заглушка),
   путь существующего xhttp-хаба → `400` (ответ хаба). При `wsSettings.path: "/"` наш вход за
   маской **недостижим**: нужен уникальный путь + `location ^~` с websocket-заголовками.
2. **Доверие TLS:** сертификат `rusiksoft.ru` на 443 — цепочка Let's Encrypt
   (`CN = YR2`, срок до 2027-02-12), `Verify return code: 0 (ok)` со штатным хранилищем Ubuntu
   на проде. То есть для туннельного пути закрепление отпечатка не нужно (в отличие от API
   брокера с корнем НУЦ — там задача T-709 остаётся).

Ещё один замер (2026-11-19, вечер): из прод-ВМ `rusiksoft.ru` резолвится в `176.32.39.234`,
на **прямом** 443 ALPN = `http/1.1` (без `-alpn` согласование не происходит), цепочка
Let's Encrypt валидна (`Verify return code: 0`, срок до 2027-02-12). Это открывает самый
дешёвый вариант C′: **свой пользователь на существующем входе 443 (VLESS+TCP+TLS)** — без
nginx-location, без нового пути и без новых публичных слушателей. Обязательные условия:
отдельный пользователь только для `tbot` (чужой, личный — нельзя: маршрутизация на узле B
привязана к `user`, и наш трафик уехал бы за чужими exit-правилами и в чужой статистике),
правила маршрутизации по этому имени пользователя выше общих и выше балансировщика
(запрет приватных диапазонов → `blocked`, затем явный outbound), `alpn: ["http/1.1"]`,
`serverName: rusiksoft.ru`. Ограничение варианта: `xtls-rprx-vision` работает только при
прямом TLS до Xray, то есть вход нельзя фронтить через nginx, не потеряв vision. Конфиг —
`docs/runbook/telegram-egress-proxy.md §4.2`.

Отдельно: `password` входа был прислан фрагментом конфигурации в переписку → считаем
скомпрометированным, обязательна ротация до запуска (новый ключ — только в конфиге узла B и в
секрет-файле проде). Значение нигде не сохраняется и не цитируется. Позже тем же способом в
переписку попал полный `ss://`-URI с двумя ключевыми сегментами (основной ключ входа и, по
всей видимости, отдельный ключ пользователя) — вывод тот же: **оба ключа меняются до
использования**. Порядок передачи секрета без чата: либо значения проставляются заказчиком
самому в файлах на узлах (конфиг Xray на проде с правами 600), либо передаётся только
непубличная часть (порт/путь), а ключ остаётся на узлах. В git ни ключи, ни полные URI не
попадают (`ss://…@…` содержит секрет), проверятся это gitleaks в CI.

Ещё по URI: в SS-2022 несколько ключей на одном входе означают режим «несколько
пользователей» — в Xray для этого используется поле `passwords` (сопоставление id→ключ),
а не одно `password`. Если версия панели/Xray этого не поддерживает, клиент с «вторым
ключом» не аутентифицируется: проверь по своей версии до того, как считать вход рабочим.

**Доступность порта входа (замер 2026-11-19 вечером).** Заказчик сообщил, что доступ открыт
tолько для `153.51.172.30`. Замер: TCP на `176.32.39.234:10800` **не устанавливается ни с
прод-ВМ, ни с домашней машины**, при этом `:443` доступен. Причина: вход слушает `127.0.0.1`,
поэтому правило на порту 10800 само по себе путь не создаёт — наружу нечего принимать.
Вывод: доступ надо реализовывать на фронте (443 + уникальный путь), а ограничение по IP —
внутри `location` (`allow 153.51.172.30; deny all;` с `error_page 403` на маску-404, чтобы
отказ не выделял путь среди прочих). Вариант «вывести вход на публичный порт» требует
`listen: 0.0.0.0` + TLS на самом входе: без TLS остаётся открытый WebSocket с SS-2022
(полезная нагрузка шифруется, но PFS нет, транспорт опознаётся DPI) + новый публичный
слушатель — не рекомендуем. Подробная конфигурация и проверка с двух сторон —
`docs/runbook/telegram-egress-proxy.md §2.1`.

Требования к схеме (без них она не принимается). Реализация по шагам, проверки и откат —
`docs/runbook/telegram-egress-proxy.md`.
1. интерфейс для приложения — локальный SOCKS5 на проде (петлевой интерфейс, с паролем);
   приложение отдаёт имя хоста прокси как есть (`socks5h`), потому что DNS прода выдаёт
   недоступный `149.154.166.110`;
2. на узле B — отдельный вход (свой тег, `127.0.0.1`) со случайным путём WebSocket и правилом
   фронта, переживающим перегенерацию конфига панелью; служебный SOCKS панели
   (`panel-egress`, `127.0.0.1:62790`, `noauth`) не используется;
3. маршрутизация на узле B — правило по тегу входа с **явным** outbound (сначала `direct`,
   при неудаче — один конкретный exit), выше общих правил; балансировщик `All` запрещён;
4. **запрет внутренних адресов** для нашего входа (`blocked` на loopback, `10/8`, `172.16/12`,
   `192.168/16`, `geoip:private` и собственный домен): иначе туннель становится путём к панели
   и БД узла B;
5. TLS-верификация не ослабляется: фронт с настоящим LE-сертификатом, цепочка
   `api.telegram.org` проверяется всегда; при расхождении — `tg_tls_mismatch` и переход на A;
   для WebSocket нужен `alpn: ["http/1.1"]` (h2 на фронте ломает рукопожатие);
6. через туннель — только Telegram API: первое правило маршрутизации на проде привязывает к
   туннелю исключительно трафик локального SOCKS-входа; вызовы API брокера идут напрямую;
7. клиент туннеля на проде — изменение прод-хоста, ставится только вместе с T-011
   (сейчас отложена заказчиком);
8. учётные данные — только в файлах с правами 600 (`/etc/tbot-secrets/telegram.env` на проде,
   конфиг клиента), маскируются в логах, не попадают в git и не передаются через чат.

Риски, которые нужно принять осознанно (фиксируем в ADR):
- канал управления торговлей зависит от личной сервисной инфраструктуры узла B: обновление
  панели, смена правил или падение узла B = потеря уведомлений и управления (торговля при этом
  продолжает работать по лимитам, но без удаленного выключателя) → обязателен второй канал
  критичных алертов (e-mail) и метрика `tg_last_delivery_age_s` на панели;
- метаданные обращений к Telegram уходят наружу через зарубежные точки цепочки (NL/SE/USA);
  содержимое осталось за сквозным TLS, финансовая история и ПДн не покидают прод. Факт
  выносится в раздел границ (TZ §15) как принятое архитектурное решение;
- задержка выше прямой (несколько хопов): для уведомлений и кнопок управления это приемлемо
  (сотни мс), для торговых вызовов API брокера прокси не используется вообще.

Сравнение вариантов (все три совместимы, применяются слоями):

| Вариант | Работает без правок SG? | Нужен доступ к узлу B? | Точка отказа | Что даёт |
|---|---|---|---|---|
| **A** — закрепление DC-IP на проде | да | нет | один живой адрес `149.154.167.220` | минимум зависимостей, работает сразу |
| **C′** — туннель-egress через узел B | да (прод → B:443 уже открыт) | только добавить вход-прокси | узел B и его цепочка | заведомо живой путь к Telegram без SSH и без чужого кода |
| **B** — контейнер `tgbot` на узле B | нет (нужен 443 на проде) | да, SSH + размещение | узел B | изоляция процесса управления от прода; избыточность пути |

Вывод: **базовый набор A + C′**, вариант B остаётся резервом на случай, если понадобится
изолировать процесс управления от прод-хоста или если цепочка B перестанет ходить в Telegram.

Требования к узлу B (минимум, чтобы не ослабить прода):
- контейнер `tgbot` без хостовых монтирований, отдельный непривилегированный пользователь,
  egress только Telegram + прод;
- на узле B нет токенов брокера, KEK, дампов БД, сессий панели;
- внутренний API прода (`/internal/tg/v1/*`) — mTLS + allowlist по IP узла B + rate-limit,
  ручки не доступны с других адресов;
- изоляция от существующего ПО узла B: никаких общих сетей/тома/сокетов, общий только
  исходящий интернет.
