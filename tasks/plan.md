# План внедрения (`tasks/plan.md`)

Основано на: `CAPABILITY_MAP.md` (модули и зависимости), `docs/TZ.md` + `docs/tz/01…15`,
`docs/PROMPT.md` (протокол работы). Задачи с критериями — `tasks/todo.md`.

## 1. Порядок и разрез по вехам

| Веха | Модули (capability map) | Что проверяем на выходе (checkpoint) |
|---|---|---|
| M0 (≈1–2 недели) | `platform-foundation`, `storage` | `make dev` поднимает всё; миграции up/down; health/metrics; CI зелёный (lint/test/type/gitleaks/pip-audit/bandit); `deploy-check` работает |
| M1 (≈2 недели) | `identity`, `credentials`, `web-auth` | вход только с TOTP; приглашения+одобрение; шифрование токенов + ротация KEK; аудит с цепочкой хэшей; IP-allowlist; TLS/HSTS; форма подключения токена с валидацией типов счетов |
| M2 (≈2–3 недели) | `broker-gateway`, `instrument-catalog`, `market-data`, `ops-observability`(база) | contract-тесты на mock; бюджет запросов и подписок; стримы с реконнектом и догрузкой; загрузчик истории с чекпойнтами; метрики брокера в Prometheus |
| M3 (≈3 недели) | `portfolio-sync`, `risk-gate`, `order-executor` | полный цикл в песочнице; коды R01…R35; `unknown`-протокол без дублей; `reconcile` после `kill -9`; paper/production за одним интерфейсом |
| M4 (≈3 недели) | `indicators`, `strategy-engine`, `strategy-grid`, `strategy-ta`, `notifications`, `telegram-bot`(чтение) | инварианты сетки на тестах; ≥10 торговых дней в paper; все коды оповещений; суточный дайджест; привязка Telegram с TOTP |
| M5 (≈2–3 недели) | `backtest` | манифест датасета; воспроизводимость; walk-forward; предупреждения; отчёт «paper vs backtest» |
| M6 (≈2–3 недели) | `web-console`, `telegram-bot`(управление) | все страницы §9.3; подтверждения TOTP; отчёты/экспорт; доступность (axe) + чек-лист §9.5 |
| M7 (≈1–2 недели) | `ops-observability`, эксплуатация | все учения §13.5 с протоколом; бэкап+`restore-verify`; алерты; боевой запуск на 1 инструменте с лимитами «минимум» |

Ориентировочный срок M0→M7 при последовательной работе одного исполнителя: **4–5 месяцев**;
при параллельных lanes (см. §3) — **3–3.5 месяца**. Оценка — для планирования, не обещание:
её двигают только открытые вопросы (OQ) и расхождения контракта API.

## 2. Ключевые зависимости (что блокирует что)

```
storage ─┬─ identity ─ credentials ─ web-auth
         ├─ broker-gateway ─ instrument-catalog ─ market-data ─┐
         ├─ portfolio-sync ─ risk-gate ─ order-executor ───────┤
         └─ notifications ────────────────────────────────────┴─ web-console
indicators ─────────────── strategy-engine ─ strategy_grid / strategy_ta ─┘
                              strategy-engine + market-data ─ backtest
```

Блокирующие точки: без `risk-gate` нельзя включать `order-executor` в боевом контуре;
без `backtest` нельзя включать `production` для новой стратегии (TZ §11.5);
без `ops-observability` (метрики + алерты + бэкапы) нельзя считать M7 пройденной.

## 3. Parallel lanes (что можно делать одновременно без конфликтов)

| Lane A | Lane B | Условие неконфликтности |
|---|---|---|
| `indicators` + её тесты | `identity`/`credentials` | разные пакеты, общих файлов нет |
| `web-auth` (шаблоны/страницы входа) | `broker-gateway` (gRPC-слой) | общий только `storage`-модели: контракты фиксируются миграциями заранее |
| `backtest` (движок, метрики) | `web-console` (страницы портфеля) | разные каталоги; API контракты — через модели `packages/storage` |
| e2e/dok-тесты фронтенда | fault-тесты `order-executor` | разные наборы тестов, разные CI-джобы |
| стенд-инфраструктура (compose, UFW, Caddy) | любой пакетный код | инфраструктура меняется отдельными PR |

Правило параллельной работы: одна задача = один пакет; при пересечении по миграциям —
миграции сериализуются (одна активная ветка с миграцией), иначе Alembic разойдётся.

## 4. Риски и как они снимаются

| Риск | Вероятность/эффект | Как снимается |
|---|---|---|
| Поведение песочницы брокера не совпадает с боевым контуром (исполнение, статусы) | ср / высокий | contract-тесты + учения; M3 проверяется и в песочнице, и на mock; «боевой» путь включается только после M5/M7; фиксация расхождений в `docs/research/` |
| Утечка токена (логи, дампы, CI) | нр / критический | шифрование + KEK вне БД, маскирование в structlog, тесты-канарейки, gitleaks в CI, шифрование дампов, egress-политика |
| Дублирование заявок при таймаутах | ср / критический | клиентский ключ + `unknown`-протокол + запрет автоповтора + регрессионные тесты §13.3(1,2) |
| Просадка стратегии с усреднением сверх ожиданий | ср / высокий | потолки уровней/множителя в ядре, дневной лимит убытка, `max_drawdown_pct` обязателен в production, kill-switch, боевой запуск с минимальными лимитами |
| Истёкший токен (3 месяца) в момент торговли | сз / средний | напоминания 14/7/3 дня, страница состояния, `R31` остановка, runbook ротации, проверка на `deploy-check` |
| Лимиты API при росте числа подписок | сз / средний | budget-слой, реестр подписок с резервом, метрики, алерты; масштаб ограничен целевым §1.5 |
| Разрастание истории → диск | сз / средний | партиции, ретенция, выгрузка в Parquet, мониторинг диска, расчёт §14.3 |
| Переобучение параметров | сз / средний | walk-forward, правило устойчивости ≤30%, предупреждение `FRAGILE`, стресс-периоды |
| **Недоступность Telegram API с прод-площадки** (замерено: `api.telegram.org` и 6 из 7 DC-IP не отвечают по TCP/443 с ВМ Yandex Cloud) | опр / высокий → **снимается схемой A + C′** | **A:** пул адресов Telegram с проверкой `getMe`, SNI/цепочки и алертом (живой адрес сейчас один — `149.154.167.220`, поэтому A один не надежен). **C′:** туннельный egress через узел `rusiksoft.ru` (`176.32.39.234`): SOCKS5/CONNECT с уникальной авторизацией, вход только для IP прода, квоты, **без MITM** (`AC-telegram-07`); прод→B:443 работает уже сегодня (21 мс), правки групп безопасности не нужны. **B (контейнер на узле)** — только резерв ради изоляции процесса управления. Плюс второй канал критичных алертов (e-mail) |
| **Недостаток ресурсов прод-ВМ** (2 vCPU / 3.8 ГБ / 72 ГБ при целевых 4/8/100) | опр / средний (OOM без swap, тесная ретенция) | **Решение OQ-11: расширение не делаем.** Ограничения становятся проектными: swap 4 ГБ (T-011), `shared_buffers ≤512 МБ`, один бэктест-воркер на проде, тяжёлые прогоны — на dev-машине, ретенция минутных свечей 12 мес. + Parquet-архив, дампы не на разделе БД |
| **Нет доверия к TLS брокера из коробки** (корень НУЦ отсутствует в ОС) | опр / высокий (соблазн `verify=False`) | T-709: корневой сертификат в хост и в образ + `SSL_TBANK_VERIFY`, тест доверия в CI, `deploy-check` валится без доверия |
| **Входящие 80/443 закрыты группой безопасности облака** | опр / средний (нет панели, нет сертификата LE) | T-708 + OQ-13: правила SG, затем ufw/fail2ban, сертификат через HTTP-01/ALPN |
| Компрометация веб-периметра | нр / критический | 2FA для всего, IP-allowlist, rate limit, fail2ban, CSP/HSTS, audit + уведомления о новых устройствах, дежурный порядок отзыва сессий |
| Расхождение собственного учёта с брокером | ср / высокий | `portfolio-sync` + `reconcile` + `position_mismatches` + изоляция + ежемесячная сверка (runbook) |
| Ошибка в индикаторах/округлении цен | сз / высокий | эталонные тесты индикаторов, property-тесты округления, сверка с серверным `GetTechAnalysis` |
| «Долгий» M0 из-за инфраструктурных мелочей | сз / низкий | M0 фиксируется чек-листом, не расширяется функциональностью |

## 5. Verification checkpoints (что обязательно прогонять на границах)

1. **M1 → M2:** security-ревью по матрице TZ §8.8 (все пункты закрыты тестами) + проверка
   отсутствия секретов в дампе и логах.
2. **M2 → M3:** contract-тесты против текущей версии `t-tech-investments` + прогон
   `test-live` в песочнице (получение каталога, истории, стримов, ошибок 401/429).
3. **M3 → M4:** учения «таймаут заявки», `kill -9` с заявками, «посторонняя заявка брокера»;
   отчёт в `docs/acceptance/`.
4. **M4 → M5:** 10 торговых дней в `paper` без срабатываний `R22/R23` по вине логики;
   сравнение `paper` и реальных рыночных событий.
5. **M5 → M6:** воспроизводимость бэктеста + walk-forward + `paper vs backtest` ≤25% расхождения
   (или объяснение).
6. **M6 → M7:** e2e + доступность + чек-лист §9.5 + учения §13.5 полностью.
7. **Перед боевым запуском:** `make deploy-check`, `restore-verify`, алерты «проходят» до чата,
   лимиты «минимум», разрешение владельца (письменно, прикладывается к `docs/acceptance/`).
