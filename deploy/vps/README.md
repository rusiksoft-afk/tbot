# Файлы хоста (`deploy/vps/`)

Это эталонные файлы конфигурации **хоста** боевого контура (рабочая ВМ `153.51.172.30`,
`docs/adr/ADR-001-stand-is-prod-vm.md`). Они не живут внутри контейнеров: их задача — чтобы
состояние площадки можно было пересобрать по репозиторию, а не «как-то настроено руками».

| Файл | Куда кладётся на площадке | Назначение |
| --- | --- | --- |
| `ufw.rules` | читает `firewall.sh` | список разрешённых входящих портов и политик (TZ §8.3, §14.5) |
| `firewall.sh` | `/tmp/tbot-ops/` | применяет правила и включает ufw; умеет `--revert` |
| `fail2ban-jail.local` | `/etc/fail2ban/jail.d/tbot.local` | бан источника за неудачные входы: 3 попытки / 10 минут → 30 минут, с ростом до 24 ч (TZ §8.3) |
| `docker-daemon.json` | `/etc/docker/daemon.json` | ротация логов контейнеров 50 МБ × 10 (TZ §14.6) и пул сетей Docker вне адресного пространства ВМ |

Применение (порядок важен: файрвол включается до запуска контейнеров):

```bash
scp deploy/vps/firewall.sh deploy/vps/ufw.rules rusiksoft@153.51.172.30:/tmp/tbot-ops/
ssh rusiksoft@153.51.172.30 'sudo bash /tmp/tbot-ops/firewall.sh'          # разбор без изменений
ssh rusiksoft@153.51.172.30 'sudo bash /tmp/tbot-ops/firewall.sh --apply'  # применить
# сразу проверить вход НОВЫМ соединением, текущее окно не закрывать
ssh rusiksoft@153.51.172.30 'sudo cp /tmp/tbot-ops/fail2ban-jail.local /etc/fail2ban/jail.d/tbot.local
  && sudo systemctl restart fail2ban && sudo fail2ban-client status sshd'
```

Что нужно держать в голове:

- **Docker и ufw.** Docker сам вставляет правила в `FORWARD`/`nat`, и опубликованный контейнером
  порт становится доступен снаружи независимо от правил ufw в цепочке `INPUT`. Поэтому «какой
  порт наружу» определяется тем, что опубликовано в compose-файле, а не только файрволом:
  в боевом составе публикуется только 80/443 Caddy, база не публикуется вовсе. Ограничения
  «куда контейнеру можно ходить наружу» настраиваются отдельной цепочкой `DOCKER-USER`
  (TZ §8.5, egress-политика) — она не относится ни к ufw, ни к compose.
- **`DEFAULT_FORWARD_POLICY`.** В `/etc/default/ufw` стоит `ACCEPT`: с `DROP` (значение Ubuntu
  по умолчанию) у контейнеров не работает исходящий трафик, и выглядит это как «брокер не отвечает».
- **Откат файрвола.** `sudo ufw disable` — правила остаются в памяти ufw, но перестают применяться;
  это аварийная команда, если новый SSH-вход не поднимается.
- **`/etc/tbot/secrets`.** Секреты боевого контура (токен Telegram, токен GHCR, пароли SOCKS) —
  только файлами с правами `600`, владельцем `root`. Они не попадают ни в git, ни в `docker run -e`,
  ни в compose-файлы, ни в логи (TZ §14.3); контейнеры читают их mount'ом `tmpfs`/read-only.
  Проверка: `grep -R "token\\|passw" deploy/ | grep -v "secrets/"` даёт только переменные без значений.
